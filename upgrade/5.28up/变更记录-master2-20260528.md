## P0 · dev 数据库切换到独立 supabase 项目（与线上彻底隔离）

### 起因

`master2` 上之前 dev 与线上**共用同一 supabase 项目**，但 `ENCRYPTION_KEY` / `JWT_SECRET`
分散在各自的 .env / Jenkins 凭据。具体踩坑：

1. 5/27 用户在线上更新「前哨coze平台主api」的 API Key 后，dev 这边 `decrypt()` 抛
   `decrypt failed with both keys` —— 因为 dev 的 `ENCRYPTION_KEY` 与 Jenkins 注入的
   不一致，密文按线上 key 加密、dev 解不开。
2. 反过来 dev 这边任一 provider 重填 key，DB 里的密文又变成 dev key 加密，线上立刻解不开。
3. 形成**反复来回**的死循环：哪边最后保存 key，只有哪边能用。
4. 5.6up [开场白展示方案](../5.6up/开场白展示-方案-20260506.md#L66) 早就写明 "dev `JWT_SECRET`
   必须与线上一致" —— 5.13up Fix 3 引入 `ENCRYPTION_KEY` 后扩成两个 key 都要对齐，
   实际上一直没对齐。

### 选项与取舍（拍板见 5/28 对话）

- A. dev 与线上 key 对齐：最快但 dev 出事 = 线上密钥暴露，否决
- B. **dev 用独立 supabase 项目**（已落地）：环境彻底隔离，新 DB / 新 key，dev 改任何东西线上零感
- C. 同项目独立 schema：DB 隔离但 storage / extension 共用，工作量比 B 还大，否决

### 落地

1. 新建 supabase 项目 `agent-portal-dev`，URL `https://ysgdmdqygbvfthzylhqn.supabase.co`。
2. 在新 DB 跑 [`setup-dev-db.sql`](../../setup-dev-db.sql)（按 [`supabase/MIGRATIONS.md`](../../supabase/MIGRATIONS.md)
   顺序合并 43 个文件：schema + rpc + v2~v40 + trial 系列）。**bundle 内修补两处 schema 锈病**：
   - schema.sql 末尾"高频索引"引用了 v7 / v15 / v3 / v8 才建的列/表 →
     bundle 里删掉这 6 条索引（v18 / v19 已覆盖），保留 `users_tenant_code_idx`。
   - v17 `ADD CONSTRAINT tenant_agents_tenant_code_fkey` 与 schema.sql 里 inline
     `REFERENCES tenants(code) ON DELETE CASCADE` 自动生成的同名约束冲突 →
     bundle 里加 `DROP CONSTRAINT IF EXISTS` 前置。
   - ⚠ 这两处都是 schema.sql 自带的 bug，**任何全新部署都会踩**（线上没事是因为
     线上库从老版本逐步迁移过来）。本期只在 bundle 内修，不动 schema.sql 原文件 ——
     真正修复待用户拍板（涉及"绝不修改已发布的 migration"约定）。
3. 在新 DB 启用 `vector` 扩展、建 `uploads` + `kb` 两个 private storage bucket
   （bucket 由 service role key 远程调 supabase Storage API 建，admin 不用在 UI 点）。
4. 改 [`agent-01/.env.local`](../../.env.local)：
   - `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`
     全切到新项目
   - `ENCRYPTION_KEY` / `JWT_SECRET` 重新本地随机生成（与线上完全独立，再也不用对齐）
   - 旧 `.env.local` 备份到 `.env.local.backup-20260527`（万一回滚用）
5. 加 `.gitignore` 规则忽略 `setup-dev-db*.sql` 和 `.env.local.backup-*`，避免一次性
   文件误进 git。

### 影响

- 从此以后 dev 改任何 provider key、跑任何迁移、删任何数据都**与线上零相关**。
- 线上 Jenkins 凭据、线上 supabase 库一字未动。
- dev DB 是空的（无 agent / provider / 用户 / 工作流），需要按需建测试数据。
- 默认账号 / DEMO 测试企业 / 4 个默认分类已建（schema.sql 种子数据）。

### 顺手交付的工具脚本

- `scripts/dev-check-coze-bots.mjs`（之前 5/27 写的，原本要检查"前哨coze主api"绑了哪些智能体）—— 留作日常 dev 工具，未来按 provider 维度健康检查能直接用。

## P1 · 厂商预设默认模型修正（5.27up follow-up）

### 起因

5.27up 把 LLM_PRESETS 各厂商 `defaultModel` 升到 2026/05 "最新"时，**几处 model ID
是按搜索结果产品名推断的，没在官方 API 文档实测**：

- 智谱 `glm-5`（产品名 GLM-5，但 bigmodel.cn 官方 model ID 列表里没找到此精确字符串）
- OpenAI `gpt-5.5-pro`（在 platform.openai.com 模型清单里找不到对应条目）

5/28 用户在 dev 新建「智谱api」provider 触发该坑：default `glm-5` → 测试连通时智谱
返"上游空响应"（实质是 model 不识别 + 上游异常被 stream parser 吞掉）。

### 用户拍板的口径

- **default 用免费 / 便宜模型**：API 管理「测试」按钮调用 default，纯为验连通性，
  不应消耗付费额度
- **新付费模型放进 `recommendedModels`**：搭建器创建智能体时由用户主动选
- **只用官方 API docs 实测确认过的 model ID**：搜索结果里没明确 API 暴露证据的不收录

### 修正后的预设（核实来源全部在 5/28 WebSearch 笔记里）

| 厂商 | 旧 default | 新 default | 新增 / 调整的 recommendedModels |
|---|---|---|---|
| OpenAI | `gpt-5.5` | **`gpt-4o-mini`**（兼容、最便宜） | 加 `gpt-5.4` / `5.4-pro` / `5.4-mini` / `5.4-nano`；**删 `gpt-5.5-pro`**（没找到证据） |
| 智谱 GLM | `glm-5` | **`glm-4-flash`**（免费） | 加 `glm-5.1`(长任务旗舰) / `glm-4.6`(200K) / `glm-4.5`；**删 `glm-5`**（未找到 API ID 证据） |
| 通义千问 | `qwen3.6-plus` | **`qwen-flash`**（便宜） | 加 `qwen3.6-flash`；`qwen3.6-plus` / `qwen3.7-max` 仍在推荐里 |
| DeepSeek | `deepseek-v4-flash` | 不变（已是便宜系列） | 不变 |
| 火山方舟 / Kimi / 文心 / 混元 | 不变 | 不变 | 不变 |
