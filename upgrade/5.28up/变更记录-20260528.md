## P0 · A · ingest 转后台异步（终结大文档卡死）

### 起因

[`lib/kb/ingest.ts:22`](../../lib/kb/ingest.ts#L22) 旧实现里 `extract → chunk → embedTexts → insert`
全程 sync await，被 `POST /api/admin/knowledge-bases/:id/documents` 路由 `await ingestDocument`
直接绑死在 HTTP 请求上。小文档（几页 PDF）20-30s 还能忍；几十页 / 几百页的产品手册必
HTTP 超时，文档卡在 indexing 状态、用户体感死机。

### 修法

[`app/api/admin/knowledge-bases/[id]/documents/route.ts`](../../app/api/admin/knowledge-bases/%5Bid%5D/documents/route.ts) `POST upload`：
- `await ingestDocument` 改成 `next/server` 的 `after(() => ingestDocument)` —— Next 15+
  稳定 API，响应发出后在同进程里继续跑，本地 / PM2 自部署无超时上限。
- POST 立即返回 `status: 'pending'` 的文档行。

[`app/api/admin/knowledge-bases/[id]/documents/[docId]/route.ts`](../../app/api/admin/knowledge-bases/%5Bid%5D/documents/%5BdocId%5D/route.ts) `POST reindex` 同步处理：
- 先 `UPDATE status='pending'` 给前端立即反馈"已排队"
- `after(() => ingestDocument)` 后台跑
- POST 立即返回 pending 行

[`app/admin/knowledge-bases/[id]/page.tsx`](../../app/admin/knowledge-bases/%5Bid%5D/page.tsx)：
- 新 effect：列表里任一文档在 `pending` / `indexing` 时**每 3s 轮询**列表，全部落到
  `done` / `failed` 终态时停。
- 上传后不再等"已索引 N 段"toast；改提示"正在后台索引…列表会自动更新"。
- 「重建」按钮 `pending` 也禁用（防并发跑同一文档撞库）。

### 取舍

- 选 `after()` 不选 `fire-and-forget`：`after()` 是 Next 官方文档的模式、有自己的
  执行上下文不被 GC，可观测性更好；fire-and-forget 在某些 deploy 形态会被中断。
- 不引入 BullMQ / Redis：当前规模没必要，PM2 自部署 + after() 已足够。
- 服务端不做 idempotency key（同文档并发 reindex）：前端按钮锁 + status 防点击足够；
  真要硬保证只能上 DB 行级锁，超出本阶段。

## P0 · C · chunk 级进度（前端轮询能看到 12/35）

### 起因

A 做完后前端轮询能拿到 pending → indexing → done，但 `indexing` 期间只显示"正在索引…"
spinner，**无法判断是卡住还是还在跑**。

### 修法 · 加列

**新 migration · [`migration_v40_kb_doc_total_chunks.sql`](../../supabase/migration_v40_kb_doc_total_chunks.sql)**：
```sql
ALTER TABLE kb_documents
  ADD COLUMN IF NOT EXISTS total_chunks INT NOT NULL DEFAULT 0;
```

- `chunk_count` 沿用"已完成数"语义（ingest 期间增长）
- `total_chunks` 新加，承担"总数"语义（chunkText 之后一次写入）
- 老数据 `total_chunks=0` → 前端回退"已完成 N 段"无总数显示
- ⚠ **必须先跑此 SQL 再发代码** —— 5.28up 后端 `select` 直接拉 `total_chunks`（[documents/route.ts:18](../../app/api/admin/knowledge-bases/%5Bid%5D/documents/route.ts#L18)、[knowledge-bases/[id]/route.ts:36](../../app/api/admin/knowledge-bases/%5Bid%5D/route.ts#L36)），列不存在 Supabase 直接 500。**上线顺序：跑 v40 → 部署代码**，不能反

### 修法 · ingest 分批

[`lib/kb/ingest.ts`](../../lib/kb/ingest.ts) 重构 step 4-5：

| 旧 | 新 |
|---|---|
| `embedTexts(all)` 一次拿所有向量 | 按 `KB_EMBED_BATCH_SIZE=64` 分批 |
| `insert(all rows)` 一次写所有切片 | 每批 `embed → insert → UPDATE chunk_count += N` |
| 前端只能看 0 → N（一跳完事） | 前端 3s 轮询能看到 0 → 64 → 128 → ... → N |

副作用：chunkText 之后立即 `UPDATE total_chunks=N + chunk_count=0`（重建场景必须清 0
避免显示残留旧值）。

### 修法 · 前端文案

[`app/admin/knowledge-bases/[id]/page.tsx`](../../app/admin/knowledge-bases/%5Bid%5D/page.tsx)：

```
old:  正在索引…
new:  正在索引… 12/35 段（34%）    ← total_chunks > 0 时
new:  正在索引… 已完成 12 段        ← total_chunks = 0 兜底
```

`KbDocument` 类型加 `total_chunks: number`。

### DOC_FIELDS 三处都加

`select` 列里加 `total_chunks`：
- [`api/admin/knowledge-bases/[id]/documents/route.ts`](../../app/api/admin/knowledge-bases/%5Bid%5D/documents/route.ts)
- [`api/admin/knowledge-bases/[id]/documents/[docId]/route.ts`](../../app/api/admin/knowledge-bases/%5Bid%5D/documents/%5BdocId%5D/route.ts)
- [`api/admin/knowledge-bases/[id]/route.ts`](../../app/api/admin/knowledge-bases/%5Bid%5D/route.ts)（详情页 GET）

## P1 · B · 答案引用可视化（KB 命中时显示"引用了 N 个片段"）

### 起因

5.20up 把 KB 切成"严格不补常识"模式后，答案可信度高了，但**用户看不到答案到底引用了
哪些片段**——既不知道是 KB 命中还是常识胡编，也无法对资料溯源。

### 修法 · 后端

[`lib/kb/types.ts`](../../lib/kb/types.ts) · `KbSearchResult` 加 3 个可选字段（向后兼容）：
```ts
id?: string;        // chunk id，前端做 React key
kb_id?: string;     // 已在 RPC 返回里，只是类型没声明
filename?: string;  // retrieve.ts 补查 kb_documents 后填
```

[`lib/kb/retrieve.ts`](../../lib/kb/retrieve.ts)：RPC 返回后批量查 `kb_documents` 拿
`id → filename` 映射、回填 `chunk.filename`。**单次查询**，失败不抛、只 warn（引用展示
是 nice-to-have，绝不阻断对话）。

[`app/api/agents/[id]/chat/route.ts`](../../app/api/agents/%5Bid%5D/chat/route.ts)：
- KB 检索成功 → 留 `retrievedChunks` 引用到外层作用域
- done 事件 payload 多带 `references` 字段：
  ```ts
  references: chunks.map(c => ({
    id, document_id,
    filename: c.filename ?? "未知文档",
    similarity: Math.round(c.similarity * 100) / 100,
    snippet: c.content.slice(0, 300),  // 截 300 字防 SSE 帧太大
  }))
  ```

### 修法 · 前端

[`app/agents/[id]/page.tsx`](../../app/agents/%5Bid%5D/page.tsx)：

- 加 `KbReference` 类型 + `Message.references?: KbReference[]` 字段
- done 事件解析：`if (obj.references?.length > 0) → 挂到 aiId 这条 message 上`
- 新组件 `KbReferencesPanel` —— 折叠面板，默认收起：
  ```
  📚 引用了 3 个知识库片段  展开 ▾
  ```
  展开后每段：📄 文档名 · 相似度 XX% · snippet（line-clamp-4）
- 渲染入口：assistant 气泡内 `aborted` 标签下方

### 不做持久化（拍板）

`references` 只挂在当前会话内存里，**刷新整页 / 切换会话仍然丢**。不入 `messages` 表，理由：
- 引用是"答案的辅助说明"，不是消息本身，丢不影响阅读
- 入库要 migration 加 `references JSONB` 列 + 改 messages select + 改 loadConversationMessages 解析，**不是 MVP 必需**
- 真有"历史对话回看引用"需求时单独开 PR

## 小B 复审收口（4 项）

复审发现 4 个问题，逐条改完：

### Fix 1 · B 引用面板被 loadConversationMessages 刷掉（覆盖回归）

**问题**：done 事件把 refs 挂到临时 `aiId`，紧接着 `loadConversationMessages` 用 DB
消息重建 state，DB 里没存 refs → 面板一闪而过。

**修法**：[`app/agents/[id]/page.tsx`](../../app/agents/%5Bid%5D/page.tsx) 加 `refsBySnippetRef`（useRef
持的 Map，键 = content 前 160 字 snippet）。done 事件除了挂到 aiId 也写入 ref；
loadConversationMessages 重建消息时按 snippet 反查 ref 把 refs 重新挂回。

**口径不变**：仍然不持久化、刷整页仍丢；只是同一会话内**重建消息数组**这条路径不
再吃掉 refs。

### Fix 2 · 知识库详情页轮询闪屏

**问题**：[`app/admin/knowledge-bases/[id]/page.tsx`](../../app/admin/knowledge-bases/%5Bid%5D/page.tsx) `load()` 总是 `setLoading(true)`，
3s 轮询期间页面周期性露出骨架屏 / "加载中…"。

**修法**：`load()` 加 `opts: { silent?: boolean }` 参数，silent=true 时不动 loading
state、错误也不弹（避免轮询中网络抖一下吓人）。轮询 effect 改 `load({ silent: true })`。
首次挂载 / 手动刷新仍走默认 silent=false。

### Fix 3 · reindex 服务端无并发保护（多 tab / curl 可绕过前端锁）

**问题**：前端按钮在 pending/indexing 时已禁用，但接口本身仍允许并发请求。两 tab
同时点重建 → 两个 `ingestDocument` 并发跑同一文档：都 `DELETE kb_chunks WHERE document_id`
→ 都 `INSERT` → 可能产生重复切片 / 互相清理。

**修法 · 原子状态翻转**（[`documents/[docId]/route.ts`](../../app/api/admin/knowledge-bases/%5Bid%5D/documents/%5BdocId%5D/route.ts) reindex POST）：
```ts
// 只允许从终态 (done/failed) 翻到 pending
const { data: flipped } = await db
  .from("kb_documents")
  .update({ status: "pending", ... })
  .eq("id", docId)
  .in("status", ["done", "failed"])
  .select("id");
if (!flipped?.length) return apiError("该文档正在索引中…", "VALIDATION_ERROR");
```
第一条请求成功（done→pending），并发的第二条因为 status 已经是 pending 不在 `["done","failed"]`
集合 → 0 行影响 → 直接 409 拒绝，不再 schedule 第二次 ingest。

**修法 · DB 层兜底**（**新 migration · [`migration_v41_kb_chunks_unique.sql`](../../supabase/migration_v41_kb_chunks_unique.sql)**）：
- 一次性去重旧重复行（保留 id 最大）
- 加 `UNIQUE (document_id, chunk_index)` 索引

未来即便其它路径误插重复切片，DB 也会直接拒绝；ingest 任何并发都不会污染数据。

### Fix 4 · 上线步骤文案错（"不跑 v40 也能跑"是错的）

**问题**：5.28up 后端 `select DOC_FIELDS` 已经直接拉 `total_chunks` 字段，列不存在 →
Supabase 整个 select 500。原 changelog 说"不跑 v40 也能跑" 是错的。

**修法**：上线步骤段改成"**必须先跑 v40 + v41 → 再发代码**"，强调顺序不能颠倒。

## P2 · 用户端一键进入管理后台（admin SSO 按钮）· 下午追加

### 起因

平台同一个人可能既是普通用户（用 user 身份在前台对话）又是 admin（管后台）。
当前要进管理后台必须知道 `/admin/login` 路径 + 重新输用户名密码。**痛点**：
- 多数 admin 已经在用户端登录了 —— 让他再输一遍密码体感很重
- 移动端打字麻烦更明显

### 设计要点

**架构基础（已具备，无需改）**：两套 cookie 互不冲突，**可以同时存在**：
- `ai_portal_token` — 用户态
- `ai_portal_admin_token` — 管理后台态
- middleware 进 `/admin/*` 时只看 admin cookie，颁 admin cookie 完全不影响 user cookie

**核心机制**：用户在前台已登录 → 后端**重新查 DB**确认仍是 admin → 颁发
admin cookie → 新 tab 打开 `/admin/dashboard`。

### 改动 3 块

#### 1. 后端 · `GET /api/me` 加 `isAdmin` 字段

[`app/api/me/route.ts`](../../app/api/me/route.ts)：

```ts
const isAdmin =
  user.role === "super_admin" ||
  user.role === "system_admin" ||
  user.role === "org_admin";
return NextResponse.json({ ...原字段, role, isAdmin });
```

只看 `users.role`；不查 `admins` 表 —— 那张表是系统内置账号（默认 admin），前台
登录通道只允许手机号 / 用户名，不会出现 admins 表用户。

[`lib/types.ts`](../../lib/types.ts) · `UserInfo` 加可选字段 `isAdmin?: boolean`。

#### 2. 后端 · 新 endpoint `POST /api/auth/elevate-to-admin`

[`app/api/auth/elevate-to-admin/route.ts`](../../app/api/auth/elevate-to-admin/route.ts) ·
**用户态已登录 → 颁 admin cookie**。

**安全设计（小B 复审重点）**：

| 检查 | 做法 | 复用 |
|---|---|---|
| ① user token 有效 | `getCurrentUser()` | lib/auth.ts |
| ② **重查 DB**（不信 JWT 里的 role —— 可能是几天前签的、中间被降权） | `SELECT id,phone,username,role,status,tenant_code FROM users WHERE id=...` | — |
| ③ status 必须 `active`（拒 deleted / disabled / cancelled） | 同 admin/login 79-88 | — |
| ④ role ∈ {super_admin, system_admin, org_admin} | 同 admin/login 91-94 | — |
| ⑤ org_admin 还要校验所属租户 `enabled` 且未过期 | 同 admin/login 97-109 | — |
| ⑥ 限流 | `checkLoginRate("elevate:" + userId)` | lib/rate-limit |

**JWT payload** 复用 admin/login 同款：
```ts
{ type: "admin", adminId: user.id, username: user.username ?? user.phone,
  role, tenantCode: role === "org_admin" ? user.tenant_code : null }
```

TTL 30 天，与 admin/login 完全一致。

**与 admin/login 的区别**：本接口**不需要密码** —— 用户态已经用密码登录过、user cookie
有效就证明身份；本接口只是"复用同一身份"翻一个 admin token 出来而已。

#### 3. 前端 · 顶栏右上角条件按钮

[`app/page.tsx`](../../app/page.tsx)：

- 加 `ShieldCheck` 图标 import
- 顶栏图标行（帮助 / 联系 / 设置 / 退出）里 contact 与 settings 之间插入按钮：
  ```tsx
  {user?.isAdmin && (
    <button onClick={enterAdmin} title="进入管理后台（新标签页）" aria-label="进入管理后台">
      <ShieldCheck size={20} />
    </button>
  )}
  ```
- **`user?.isAdmin && ...` 是渲染时判断 ——** 普通员工 DOM 里根本没这个按钮、F12
  也看不到。
- 新 `enterAdmin` 函数：
  ```ts
  await fetch("/api/auth/elevate-to-admin", { method: "POST" });
  window.open("/admin/dashboard", "_blank", "noopener,noreferrer");
  ```
- **必须先 await elevate 再 open** —— 否则新 tab 打开时 cookie 还没设上、middleware
  把它踢回登录页（实测踩过）。
- 失败弹错（`alert(error)`）：常见两种 —— "权限已被回收" / "组织已过期"。

### 边界与异常

| 场景 | 行为 |
|---|---|
| 用户中途被降权（role 改成 user）| `/api/me` 下次刷新返回 `isAdmin: false` → 按钮自动消失。如果用户没刷新还点了，elevate endpoint 重查 DB 也会拒绝（"该账号无后台访问权限"）|
| 组织被禁用 / 过期 | elevate 返回 403，弹"组织已被禁用/过期" |
| 已有 admin cookie 还点（重复 elevate）| 没问题，等于刷新 cookie；不需要先 check 是否已有 |
| 体验账号 / trial 用户 | `/api/me` 自身就拒 trial（403），所以 `isAdmin` 永远不会到达前端，按钮不会显示 |
| 同 IP 同账号被限流 | 后端 429 + "操作过于频繁，请 X 分钟后再试" |

### 没做的（按用户决策）

| 项 | 原因 |
|---|---|
| 按钮放在头像下拉里 | 用户选"顶栏独立按钮"，更显眼 |
| 仅 super/system_admin 可见，org_admin 不显 | 用户选"三种 admin 都能看到" |
| 短 TTL（2 小时） | 用户选"与 admin/login 同 30 天" |
| 按钮放在其它用户页（agents 详情 / settings / workflows）| 一期只在首页放；其它页面有自己的 header，留待后续按需扩 |

## 小B 复审第二轮收口（4 项）· 晚间追加

复审今天 master2 上的整波改动后又找出 4 个新风险点，逐条修：

### Fix 1 · 🔴 KB partial chunks 参与检索（数据正确性）

**问题**：5.28up A 把 ingest 改成分批 insert（每批 64 chunks）。如果第 2/3 批
embedding 失败，前 1 批已经落库的 chunks 不会回滚 —— fail() 只把文档标 `status=failed`，
不清 chunks。而 `match_kb_chunks` RPC（v39 版）只过滤知识库 `active`，**不过滤文档
`status='done'`**，于是失败 / 索引中文档的半截片段会被 chat 引用。

**双层修**：

- **DB 层**：新 [`migration_v42_match_kb_chunks_done_filter.sql`](../../supabase/migration_v42_match_kb_chunks_done_filter.sql)
  在 RPC 里加 `EXISTS (SELECT 1 FROM kb_documents d WHERE d.id=c.document_id AND d.status='done')`。
  签名 / 返回字段保持冻结契约不变。**🔑 上线必跑**。
- **代码层**：[`lib/kb/ingest.ts`](../../lib/kb/ingest.ts) 的 `fail()` 函数现在**主动 DELETE
  `kb_chunks` WHERE document_id**，再把文档 status 标 failed。这是双保险 —— RPC
  v42 的 status 过滤是兜底（防其它路径产生半截数据），fail() 主动清是源头。

### Fix 2 · 🔴 admin SSO 绕过"首次登录改密码"流程（合规漏洞）

**问题**：[`/api/admin/login`](../../app/api/admin/login/route.ts) 对 `first_login=true`
返回 `mustChangePassword=true`，后台登录页强制进改密码分支才能进 dashboard。但
[`/api/auth/elevate-to-admin`](../../app/api/auth/elevate-to-admin/route.ts) **没查
`first_login`，直接颁 admin cookie** → admin role + 仍是初始密码的人能从首页盾牌
一键进后台，绕过强制改密码。

**修法**：elevate select 多取 `first_login`；non-super_admin + `first_login=true`
→ 直接返回 FORBIDDEN，前端 alert "首次登录需先在管理后台修改初始密码，请直接打开
后台登录页"。与 admin/login 第 123 行 `mustChangePassword = role !== "super_admin" && first_login` 同口径。

### Fix 3 · 🟠 引用面板缓存 key 冲突（贴错引用）

**问题**：5.28up Fix 1 的 `refsBySnippetRef` 用 `content 前 160 字` 做 key。两个会话
或两条不同会话的回答开头相同（"你好。让我来帮你…"之类）→ 后写入的 refs 会覆盖
前一条，**切回看时显示错的引用来源**。

**修法**：key 前面加 `${conversationId}::` 前缀做隔离。done 事件写入时用 `obj.conversationId`，
loadConversationMessages 读取时用参数里的 `convId`。同会话内多条 assistant 消息
仍按 snippet 区分（160 字的差异已足够辨识）。

### Fix 4 · 🟡 reindex 冲突状态码 400 → 409（API 语义）

**问题**：5.28up Fix 3 reindex 并发保护时返回 `VALIDATION_ERROR`（HTTP 400）。但
"资源状态冲突"按 REST 语义应该是 409 CONFLICT。`lib/api-error.ts` 的 `STATUS_MAP`
里 `CONFLICT` 已经映到 409。

**修法**：把 `apiError(..., "VALIDATION_ERROR")` 改成 `apiError(..., "CONFLICT")`。
文案不变。功能性影响 0（前端只看 `data.error` 文字），但 HTTP 状态码语义化。

## 小B 复审第三轮收口（2 项）· 关后门

### Fix 1 · 🔴 admin/login 的 first_login 后门彻底关闭（合规闭环）

**问题**：R2 Fix 2 只挡了"前台 SSO 盾牌按钮"这一条路；后台正门 `/api/admin/login`
在 `first_login=true` 时**仍然先签发普通 admin cookie**、再返回 `mustChangePassword=true`。
[middleware.ts](../../middleware.ts) 只检查 admin cookie 是否有效、不管业务层是否完成
改密码 → 用户拿到 cookie 后手动访问 `/admin/dashboard` 仍能绕过强制改密码。

**修法 · 4 层闭环**：

1. [`lib/auth.ts`](../../lib/auth.ts) · `AdminPayload` 类型加 `firstLogin?: boolean` 字段。
2. [`app/api/admin/login/route.ts`](../../app/api/admin/login/route.ts) · `mustChangePassword=true` 时
   token payload 带 `firstLogin: true`。
3. [`middleware.ts`](../../middleware.ts) · admin token `firstLogin === true` 时所有
   `ADMIN_PROTECTED` 页面请求重定向到 `/admin`（强制走改密码页）。
4. [`lib/session.ts`](../../lib/session.ts) · `requireAdmin()` 加 `opts: { allowFirstLogin?: boolean }`，
   默认拒绝 `firstLogin=true` 的 token（FORBIDDEN）。仅 [`change-password`](../../app/api/admin/change-password/route.ts)
   传 `{ allowFirstLogin: true }` 豁免。
5. **闸门解除**：change-password 改完密码后**已有逻辑**会重签 token（字段列表写死，
   不含 firstLogin） + Set-Cookie 替换原 cookie → 新 token `firstLogin === undefined`
   → 全部检查放行。

**多层防御覆盖矩阵**（重点写给小B）：

| 攻击路径 | 旧实现 | R3 修复后 |
|---|---|---|
| 前台 SSO 盾牌一键进 | R2 Fix 2 已拒 | 仍拒（R2 修复保留）|
| 后台 `/admin/login` 拿 cookie 后改 URL 进 `/admin/dashboard` | ❌ 能进（漏洞）| middleware redirect → `/admin` |
| 拿 cookie curl `/api/admin/users` 等 | ❌ 能调（漏洞）| `requireAdmin()` 默认 FORBIDDEN |
| 调 `/api/admin/change-password` 改密码 | ✅ 能调（设计如此）| ✅ 仍能调（`allowFirstLogin: true` 豁免）|
| super_admin 是否受影响 | 不签 firstLogin | 不受影响（admin/login 已判 `role !== "super_admin"`）|

### Fix 2 · 上线步骤文案漏 v42

R2 Fix 1 加了 `migration_v42_match_kb_chunks_done_filter.sql` 但 changelog 上线步骤
