# 智能体搭建 · 模型选择融合方案

日期：2026-05-29
分支：待定（建议从 master2 拉 `feature/model-selector-merged`）
依据：用户提出"先选供应商再选模型不够好"，希望合成一步式模型选择

---

## 背景 / 痛点

当前 [`app/admin/agent-builder/[id]/page.tsx`](../../app/admin/agent-builder/%5Bid%5D/page.tsx) 「模型设置」分区是**两步**：

1. 第一个下拉：模型供应商 ←  从 DB `model_providers` 表拉已启用列表
2. 第二个下拉：模型名称 ← 按选中供应商对应预设（[`lib/model-providers/presets.ts`](../../lib/model-providers/presets.ts) · `recommendedModels`）展示

体验问题：
- 第一次接触的 admin 必须先理解"先选哪家厂商再选哪个模型"的两层概念
- 实际心智模型应该是"我想用 gpt-4o-mini" / "我想用 deepseek-v4-pro"——**直接挑模型**最自然
- 同一家厂商配了多个 provider（如同公司不同账号）时，二级下拉看不出来差异

---

## 方案

### 一句话

**两个下拉合成一个**，按供应商分组（`<optgroup>`），用户点开看到所有已接入厂商提供的模型；选中后自动把 `provider_id` 和 `model_params.model` 都补好。

### UI 结构

```
[ 选择模型 ─────────────────────────────────── ▾ ]
┌────────────────────────────────────────────────┐
│ ── DeepSeek 深度求索（ds-main）──               │
│   deepseek-v4-flash（2026/04 主力 · 便宜）     │
│   deepseek-v4-pro（强推理 / 代码 / Agent）     │
│   deepseek-chat（旧别名 · 2026-07-24 弃用）    │
│ ── 智谱 GLM（zhipu-main）──                    │
│   glm-5.1（长任务旗舰）                        │
│   glm-4.6（200K 上下文）                       │
│   glm-4-air（5.20up 知识库锁定）               │
│   glm-4-flash（default · 免费）                │
│ ── 通义千问 / DashScope（qwen-main）──         │
│   qwen3.7-max（2026/05 旗舰）                  │
│   qwen3.6-plus（2026/04 · 1M 上下文）          │
│ ── 字节豆包（doubao-ep1）──（手填模型名）       │
│   ✏ 自定义模型名（接入点 ID）                  │
│ ── OpenAI 兼容（relay-main）──（手填模型名）   │
│   ✏ 自定义模型名                                │
└────────────────────────────────────────────────┘
```

### 三个用户决策点（已拍板）

1. **没 recommendedModels 的供应商**（豆包接入点 ID / OpenAI 兼容自定义）
   → 仍显示分组标题 + "（手填模型名）"标记 + 一个"✏ 自定义模型名"option；
   选中后保留 `provider_id`，模型走下方手填框
2. **同一模型名跨多供应商**（两个 OpenAI 兼容 provider 都有 gpt-4o-mini）
   → 分组标题里加 provider_code 区分（如「OpenAI 官方（oa-main）」「OpenAI 兼容（relay-1）」），
   option 文本只显示模型名
3. **用户想用 recommendedModels 里没有的模型**（如 deepseek 新出 V5）
   → 保留下方"自定义模型名"输入框；
   → **加自动检测**：admin 手填后，旁边出现「测试该模型」按钮，点击调一次真实的 chat 探针，
     模型不存在 / 404 / 上游报错 → 标红警告 + 显示原始错误

## 技术设计

### 0. 前置 · `Provider` 类型补 `provider_code`（小B Fix 2）

[`app/admin/agent-builder/[id]/page.tsx:22`](../../app/admin/agent-builder/%5Bid%5D/page.tsx#L22) 的 `Provider`
类型当前没声明 `provider_code`，但 API 实际会返回（`/api/admin/model-providers` 的
`sanitize()` 不剔除它）。前端要用它做分组标题与底部提示文字，**必须先补字段**：

```ts
type Provider = {
  id: string;
  name: string;
  platform: string;
  provider_code: string;   // 5.29up 新增：分组标题 + 底部小字显示
  api_endpoint: string;
  default_model: string;
  enabled: boolean;
  has_api_key: boolean;
};
```

### 1. 推断 preset 的搭建器专用辅助（小B Fix 3）

[`presets.ts:318`](../../lib/model-providers/presets.ts#L318) 的 `inferPresetFromExisting`
按 endpoint host 找不到时，回落到「**该 platform 的第一个 preset**」——对 `platform="openai"`
来说就是 `openai-official`，**直接把 GPT 推荐模型套到 relay / 自定义 endpoint 上**。

方案不动 `presets.ts`（保留它给 API 管理页用的现有语义），而是在搭建器本地包一层
更严格的判断：

```ts
// 仅在搭建器内使用：endpoint host 匹配不上时不回落，明确返回 "custom"
// 需要从 presets.ts 额外 import：getPresetsByCategory、type ProviderPreset
function resolveProviderPresetForBuilder(provider: Provider):
  | { kind: "recognized"; preset: ProviderPreset }
  | { kind: "custom"; label: string }
{
  const ep = (provider.api_endpoint ?? "").trim().toLowerCase();
  if (!ep) return { kind: "custom", label: customProviderLabel(provider) };

  // 精确 endpoint 匹配
  const all = getPresetsByCategory("model");
  const exact = all.find(p => p.endpoint.toLowerCase() === ep);
  if (exact) return { kind: "recognized", preset: exact };

  // host 匹配
  try {
    const host = new URL(provider.api_endpoint).host.toLowerCase();
    const byHost = all.find(p => {
      if (!p.endpoint) return false;
      try { return new URL(p.endpoint).host.toLowerCase() === host; } catch { return false; }
    });
    if (byHost) return { kind: "recognized", preset: byHost };
  } catch {}

  // 关键差异：host 找不到 → 视为"自定义端点"，**不**回落到该 platform 的第一个 preset
  // （避免 OpenAI 兼容自定义 endpoint 错套上 GPT 推荐模型）
  return { kind: "custom", label: customProviderLabel(provider) };
}

function customProviderLabel(provider: Provider): string {
  if (provider.platform === "openai") return "OpenAI 兼容（自定义）";
  // 防御：未来若 category=model 支持非 openai/zhipu 或 zhipu 代理 endpoint，
  // 不要误标成 OpenAI 兼容。
  return `${provider.name || provider.platform}（自定义）`;
}
```

`recognized` 走预设模型清单；`custom` 走"手填模型名"分支。这条逻辑只在搭建器用，
不动 `presets.ts` 全局语义。

### 2. 数据装配

```ts
type ModelOption = {
  groupKey: string;
  groupLabel: string;      // 例 "DeepSeek 深度求索（ds-main）"
  optionValue: string;     // `${provider_id}::${model_value}` 或 `${provider_id}::__custom__`
  optionLabel: string;
};

function buildModelOptions(providers: Provider[]): ModelOption[] {
  return providers
    .filter(p => p.enabled && p.has_api_key)
    .flatMap(provider => {
      const r = resolveProviderPresetForBuilder(provider);
      // 分组标题永远带 provider_code 区分（同一家厂商可能多 provider）
      const presetName = r.kind === "recognized"
        ? r.preset.label.split("（")[0]
        : r.label;
      const groupLabel = `${presetName}（${provider.provider_code}）`;
      const groupKey = provider.id;

      // custom 分支：仅一条"自定义模型名"
      if (r.kind === "custom" || (r.preset.recommendedModels?.length ?? 0) === 0) {
        return [{
          groupKey,
          groupLabel: `${groupLabel} · 手填模型名`,
          optionValue: `${provider.id}::__custom__`,
          optionLabel: "✏ 自定义模型名",
        }];
      }

      // recognized 分支：preset 模型 + 末尾一条"自定义"逃生口
      return [
        ...r.preset.recommendedModels!.map(m => ({
          groupKey, groupLabel,
          optionValue: `${provider.id}::${m.value}`,
          optionLabel: m.label,
        })),
        {
          groupKey, groupLabel,
          optionValue: `${provider.id}::__custom__`,
          optionLabel: "✏ 自定义模型名",
        },
      ];
    });
}
```

渲染前按 `groupKey + groupLabel` 归并成 optgroup；上面的 helper 返回平铺选项只是为了让
`composeValue` / 测试逻辑复用同一套 value 规则。

### 3. onChange · 切换 provider 时正确处理 `__custom__`（小B Fix 4）

**问题**：从 A 供应商切到 B 供应商的"自定义"时，若直接"不动 model_params.model"，
旧的 A 模型名会被带到 B 上去（B 大概率不识别这个 model_id → 上游 400 / 报"model not found"）。

**修法**：onChange 时**永远清空**旧 `model`，custom 进入时不写新 `model`（留给手填框接管）。
若事件值为空（没有可用供应商 / 占位项），同步清空 `provider_id`：

```tsx
<select
  value={composeValue(draft.provider_id, draft.model_params?.model)}
  onChange={(e) => {
    if (!e.target.value) {
      patchDraft(d => ({ ...d, provider_id: null, model_params: { ...d.model_params, model: undefined } }));
      return;
    }
    const [providerId, modelOrCustom] = e.target.value.split("::");
    patchDraft(d => ({
      ...d,
      provider_id: providerId,
      model_params: {
        ...d.model_params,
        // 切到具体模型 → 写新值；切到自定义 → 显式清空，让手填框从空开始
        model: modelOrCustom === "__custom__" ? undefined : modelOrCustom,
      },
    }));
  }}
>
  {/* render optgroups（同上） */}
</select>
```

### 4. composeValue · 用 `resolveProviderPresetForBuilder` 而不是 `providers.find` 拿 preset（小B Fix 1）

```ts
function composeValue(providerId: string | null, model?: string): string {
  if (!providerId) return "";
  const provider = providers.find(p => p.id === providerId);
  if (!provider) return "";
  const r = resolveProviderPresetForBuilder(provider);
  // 兼容老 draft：旧数据可能只存 provider_id、不存 model。
  // 此时若 provider.default_model 仍在 preset 清单里，就让 select 显示这个具体模型，
  // 不要误落到"自定义模型名"并触发空值校验。
  const effectiveModel = (model?.trim() || provider.default_model || "").trim();
  // 仅 recognized 分支才检查 model 是否在 preset.recommendedModels 里
  const matched = r.kind === "recognized"
    && effectiveModel
    && r.preset.recommendedModels?.some(m => m.value === effectiveModel);
  return matched
    ? `${providerId}::${effectiveModel}`
    : `${providerId}::__custom__`;  // 不在 preset 或 custom 分支 → 落到自定义
}
```

### 5. 下拉关闭后展示当前供应商（小B Fix 5）

原生 `<select>` 关闭后只显示 option 文本，不显示 optgroup。两个 provider 都有
gpt-4o-mini 时，admin 看不出**当前用的是哪家**。

在 select 下方加一行小字明确：

```tsx
{selectedProvider && (
  <p className="text-[11px] text-gray-500 mt-1">
    当前供应商：<code className="font-mono">{selectedProvider.name}（{selectedProvider.provider_code}）</code>
  </p>
)}
```

### 6. 自定义模型名"测试该模型"探针 + 必读 `data.success`（小B Fix 6 + 7）

**扩展 [`/api/admin/model-providers/[id]/test`](../../app/api/admin/model-providers/%5Bid%5D/test/route.ts) endpoint**：

- 现状：用 provider 默认模型发一条 `请只回复"连接成功"四个字。`，验证 endpoint+key 通
- 改动：接受 query string `?model=xxx`；如提供则优先写入 `modelParams.model`，
  覆盖 `provider.default_params.model` / `provider.default_model`
- 兼容性：不传 `?model` 时行为完全不变（API 管理页"测试"按钮不受影响）

**前端 UI**：

```
[ 自定义模型名（手填）] xxx-v5   [ 测试该模型 ]
                                ✓ 连接成功（200ms）
                          或    ✗ The model `xxx-v5` does not exist
```

```ts
async function probeCustomModel() {
  const name = customModelInput.trim();
  if (!draft.provider_id) { setProbeResult({ ok: false, msg: "请先选择供应商" }); return; }
  if (!name) { setProbeResult({ ok: false, msg: "请先输入模型名" }); return; }
  setProbing(true);
  try {
    const res = await fetch(
      `/api/admin/model-providers/${draft.provider_id}/test?model=${encodeURIComponent(name)}`,
      { method: "POST" },
    );
    // ⚠ 小B Fix 6：失败时该 endpoint 仍返 HTTP 200 + { success: false, error }
    //   不能只看 res.ok，必须读 data.success
    const data = await res.json();
    if (!res.ok) {
      setProbeResult({ ok: false, msg: data?.error ?? `HTTP ${res.status}` });
    } else if (!data.success) {
      setProbeResult({ ok: false, msg: data?.error ?? "未知错误" });
    } else {
      setProbeResult({ ok: true, msg: `连接成功（${data.latency_ms}ms）` });
    }
  } finally {
    setProbing(false);
  }
}
```

### 7. 自定义模型名为空 · 保存/发布前校验（小B Fix 7）

豆包 / OpenAI 兼容自定义 provider 自身 `default_model` 可能也为空，**这时 admin 选了
"自定义模型名"但忘了填，发布后运行时 model 字段就空了**——后续测试/对话会落到兜底或直接
被上游拒绝，体感像智能体坏了。

**修法**：保存 draft（不论"保存草稿"还是"发布"）前的前端校验加一条；但要兼容旧 draft
只依赖 `provider.default_model` 的合法场景，所以校验的是 **effective model**：

```ts
function validateBeforeSave(): string | null {
  // ... 现有校验
  // 5.29up 新增：draft model 和 provider default_model 都为空 → 拦
  const selectedProvider = providers.find(p => p.id === draft.provider_id);
  const model = String(draft.model_params?.model ?? "").trim();
  const providerDefaultModel = String(selectedProvider?.default_model ?? "").trim();
  if (draft.provider_id && !model && !providerDefaultModel) {
    return "请填写模型名（或在「模型选择」里挑一个预设模型）";
  }
  return null;
}
```

不打真实 API、不走探针——只做"非空"硬校验。探针是 admin 主动想验时才点。

后端发布接口也补同口径兜底：[`app/api/admin/agent-drafts/[id]/publish/route.ts`](../../app/api/admin/agent-drafts/%5Bid%5D/publish/route.ts)
在合并 `provider.default_params + draft.model_params + provider.default_model` 后，如果仍没有
`mergedModelParams.model`，返回 `VALIDATION_ERROR`，避免绕过前端直接发布空模型。

## 边界 / 异常

| 场景 | 行为 |
|---|---|
| Provider 没启用 / 没 has_api_key | filter 掉，下拉不显示 |
| Provider 列表为空（一个都没建）| 下拉 disabled + 占位文本"请先去 API 管理新建供应商" |
| 编辑老 draft，已存模型不在最新 preset 里（如 preset 升级删了某模型）| `composeValue` 返回 `${providerId}::__custom__`，下方手填框显示原值 |
| 编辑老 draft，只存了 `provider_id`、没存 `model_params.model` | 若 `provider.default_model` 在 preset 里，`composeValue` 显示该具体模型；否则落到自定义，但保存校验会允许非空 `provider.default_model` 兜底 |
| 切换不同供应商 | model_params.model 显式清空（小B Fix 4 修正），切到具体模型时写新值 |
| 用 KB 智能体 + 选了 glm-4-flash 的 provider | 5.20up 已有的"绑 KB 不能用 flash"前/后端校验**完全保留**，本方案不动 |
| 自定义 OpenAI 兼容 endpoint（relay）| `resolveProviderPresetForBuilder` 返回 `custom`，不再误套 GPT 推荐模型（小B Fix 3）|
| 选了"自定义模型名"但忘了填模型，且 provider 自身也无默认模型 | 保存/发布前端校验 + 发布后端校验拦下（小B Fix 7），不打 API |
| test endpoint 失败时返 HTTP 200 + success:false | 探针前端**只信 `data.success`**，不只看 `res.ok`（小B Fix 6） |
| 模型清单变化（厂商上新 / 下架 / 改 ID）| 这是 `presets.ts` 的维护项；老 draft 引用的模型 ID 即便从 preset 里删了也仍能保存（落自定义）|

## 模型清单维护说明（小B 备注）

`presets.ts` 里 9 家厂商的 `recommendedModels` 是**会随时间变化的维护项**——厂商上新
（如 deepseek 出 V5）/ 下架 / 改 ID 都会出现"清单跟官方文档对不上"。

本次方案让"清单过时"的代价显著降低：
- 即便清单里没列某个新模型，admin 选「自定义模型名」手填 + 点「测试该模型」
  就能立刻验证；不必等清单更新
- 老 draft 引用的模型即便被 preset 删了也仍能正常工作（落到自定义分支）

建议**每月**或**厂商发新模型公告时**手动同步 `presets.ts`；不需要每次都进 changelog 单列。

近期已对 9 家官方文档抽查过来源（OpenAI Models/Pricing、DeepSeek API Docs、
阿里百炼文本生成、智谱模型概览等），主线模型 ID 现状正确。
