## P0 · 工作流接力 + 知识库联动两个 bug 叠加导致"角色彻底混乱"

### 现象（用户截图复现）

工作流第 3 步「见功 (openai)」，绑了知识库的经验萃取智能体：

| 轮 | 用户 | AI 回复 | 期望 |
|---|---|---|---|
| 1 | "你好" | "你好，我在。你可以直接把要处理的资料发给我，我来帮你继续整理。" | 应该用"经验萃取智能体"的口吻招呼 |
| 2 | "整理什么?" | "知识库中没有找到相关资料，无法回答该问题。" | 应该按经验萃取流程引导用户讲案例 |
| 3 | @参考: 知识库入库（智谱）"你不是能做经验萃取吗?" | 正确按经验萃取角色给出方法 ✅ | — |

第 1 句完全是上一步「知识库入库」智能体的口吻；第 2 句被 KB 空命中硬规则吐回；
第 3 句因为用户显式 @ 了参考、且 wfCtx 已不再发送（首条已发过一次），才恢复正确角色。

### 根因（两个 bug 叠加）

#### Bug 1 · 工作流跨步骤上下文压过了 agent 自己的 system_prompt

[`app/api/agents/[id]/chat/route.ts`](../../app/api/agents/[id]/chat/route.ts) 旧逻辑把 `workflowContext`（上一步整段对话）直接拼成 user message 前缀：

```
【上一步工作记录】\n{wfCtx}\n\n【当前问题】\n{userContent}
```

LLM 把"上一步对话"当作最近且最具体的指引，**比 agent 自己 64 字的 system_prompt 抢眼得多**，
于是用上一步的口吻接力。旧代码的注释还自带辩白："拼入 userContent 而非 system 消息，
兼容 Coze/Dify/Yuanqi 等不支持 system role 的平台"——但当前 agent 是 openai 平台、
完全支持 system role，被这个兼容方案一刀切伤到。

#### Bug 2 · 5.20up 的 KB 空命中 fallback 无差别触发

[`lib/kb/prompt.ts`](../../lib/kb/prompt.ts) + [`app/api/agents/[id]/chat/route.ts`](../../app/api/agents/[id]/chat/route.ts) 配合：

| 场景 | 5.19up | 5.20up | 副作用 |
|---|---|---|---|
| KB 命中 ≥ 1 | 注入硬规则 + 资料 | 同 | — |
| KB 命中 = 0 | 不注入 | **注入硬规则**，模型必答"没找到相关资料" | 闲聊 / 短追问被误伤 |
| KB 检索抛错 | 不注入 | 注入"知识库不可用" | 同上 |

5.20up 改动的初衷正确（防模型用常识冒充知识库答案），但没考虑"用户在做闲聊
/ 工作流接力 / 短澄清"这类非知识查询场景。

### 修复（落地）

#### Bug 1 修：A1+A2 组合（按平台分流）

[`app/api/agents/[id]/chat/route.ts`](../../app/api/agents/[id]/chat/route.ts) 改 wfCtx 注入策略：

- **openai / 智谱**（可靠支持 system role）→ wfCtx 单独成一条 system 消息，明确标记
  "仅作背景参考，不是要扮演的角色"，与 agent 自己的 system_prompt 同级。
- **其它平台**（coze / dify / yuanqi / qingyan）→ 保留 user message 拼接（兼容这些不可靠 system role 的平台），但前置 boundary 段告诉模型 wfCtx 只是背景。

两条路径的 boundary 文案都引用 `agent.name`，让模型清楚自己当前是哪个角色。

#### Bug 2 修：B2+B3 组合（识别非知识查询、跳过 KB）

新增 [`lib/kb/intent.ts`](../../lib/kb/intent.ts) · `isMetaOrChitchatMessage(msg, historyLength)`，
任意一条命中即视为"非知识查询"：

① 极短（≤4 字符）且不含问号 → 寒暄 / 感叹 / 确认（"你好" "谢谢" "好的" "嗯"）
② 寒暄开头（"你好" "您好" "在吗" "hi" 等）
③ 元能力提问（"你能..." "你是..." "你会..." 等，问 agent 自身而非 KB 内容）
④ 已有对话上下文 + ≤6 字符 → 多为追问 / 反问 / 澄清（"整理什么?" "再说一下?"）

`chat/route.ts` 调用处：`skipKbForThisTurn = wfCtx !== null || isMetaOrChitchatMessage(...)`，
命中则整体跳过 KB 检索（顺带省一次 embedding 调用）。其中 `wfCtx !== null` 这一支是 B3
（工作流接力首条豁免），`isMetaOrChitchatMessage` 是 B2（闲聊豁免）。

`test-chat/route.ts`（草稿测试聊天）同步加 B2 闲聊豁免（无工作流，不需 B3），保持
与正式 chat 同口径（5.19up 已确立的原则）。

### 语义变化（重要 · 写给小B 复审）

| 场景 | 5.20up 行为 | 5.21up 行为 | 备注 |
|---|---|---|---|
| 工作流接力首条 + 绑库 | wfCtx 拼 user 前缀 + KB 检索 + 空命中硬规则 | wfCtx 走 system（openai/zhipu）+ 跳过 KB | 角色保持正确，不被 KB 拦截 |
| 闲聊 "你好" + 绑库 | KB 检索 + 空命中硬规则 → "没找到相关资料" | 跳过 KB，模型按 system_prompt 自答 | 招呼回正常 |
| 元能力提问 "你能做什么?" + 绑库 | KB 检索 + 空命中硬规则 → "没找到相关资料" | 跳过 KB，模型按 system_prompt 答 | 自我介绍能正常给出 |
| 真实知识查询（≥7 字符 / 含问号 / 不寒暄）+ 绑库 + 命中 | KB 严格答题 | 同 | 不变 |
| 真实知识查询 + 绑库 + 空命中 | "没找到相关资料"硬规则 | 同 | 不变 —— 这是 5.20up 想要保留的行为 |
| 真实知识查询 + 绑库 + 检索抛错 | "知识库不可用"硬规则 | 同 | 不变 |
| 未绑库 | 不注入 | 同 | 不变 |
| 非 openai/zhipu 平台 | 跳过 KB | 同 | 不变 |

**潜在副作用 / 已知误伤**：

- 知识查询型短消息（如 "客户管理"、"怎么注册" 这种 4 字以内、第 2 轮以后的短问句）
  会落入"短追问"规则被跳过 KB —— 用户多打几个字、加个问号、或重新开会话都能触发 KB。
  权衡：这种短问句歧义性高（既可能是知识查询、也可能是澄清），不让 KB 强行注入硬规则
  比误伤工作流接力 + 闲聊更可接受。
