## P1 · API 管理厂商预设扩到 9 家（OpenAI + 7 家国内主流）

### 起因

API 管理「新增大模型 API」对话框里只有 2 个厂商（OpenAI / 智谱 GLM），admin 接 DeepSeek
/ Kimi / 通义千问 / 文心一言 等都得自己查 endpoint URL 手填，"为啥不能一键选?"。
方案：建一个 ProviderPreset 目录，下拉里直接出现各家厂商，选中后 endpoint / 默认模型
/ 默认参数自动填好。

### 设计要点

- **0 adapter 改动** —— 几乎所有 LLM 厂商都提供 OpenAI 兼容协议，统一走 `platform="openai"`
  分发到 [`lib/adapters/index.ts`](../../lib/adapters/index.ts) 的 `openaiCompatibleStream`；
  只有协议不通用的（智谱 GLM、扣子、Dify、元器、清言）才单独占 platform 值。
- **0 DB schema 改动** —— preset code 仅前端用，不入库；DB 里 `model_providers.platform`
  仍是 adapter 分发用的真实值（"openai" / "zhipu" / ...）。
- **0 后端 API 改动** —— `/api/admin/model-providers` 接收的 payload 字段完全不变。
- **后退兼容老数据** —— 编辑现有 provider 时按 `(platform, endpoint host)` 反查 preset，
  匹配上就给下拉填默认值；匹配不上落到该 platform 首个 preset（如 OpenAI 兼容自定义）。

## P2 · 表单「默认模型」字段：先移除、后回滚（最终保留）

### 第一版尝试：移除字段（已回滚）

初次想法：admin 不该在 provider 层设默认模型，agent 自己选 —— 把字段从弹窗里删了，
`formFromPreset` 不再带 `preset.defaultModel`，新建入库为 `""`。

### 回滚原因

测试阶段发现 **非 OpenAI 兼容厂商上线即 404**：

- `chat/route.ts` 兜底逻辑：`agent.model_params.model → provider.default_model → "gpt-4o-mini"（仅 openai 平台）`
- 新建 provider 默认无 model → 如果 agent 也没设 model，**openai 平台**会兜底
  `gpt-4o-mini`（看上去能用，实际是错的厂商 + 错的模型，第三方中转 / 千问 / DeepSeek 等
  都不认这个名字 → 上游 404）
- 「测试连通性」按钮也会因为 default_params 没 model 而打不通

### 最终状态：字段保留，按预设默认值预填

[`app/admin/model-providers/page.tsx`](../../app/admin/model-providers/page.tsx)：

- 弹窗里**保留**「默认模型」文本输入。
- `formFromPreset` 重新用 `preset.defaultModel` 填表（如 DeepSeek 预设 → `deepseek-v4-flash`、
  智谱 → `glm-5`、千问 → `qwen3.6-plus`），admin 可改。
- 切换厂商预设的 onChange 走与 endpoint 一样的"用户没手改过就覆盖、改过则保留"逻辑。
- `openEdit` 老数据兜底：DB `default_model` 为空（第一版尝试期间新建的 provider 入库为 ""）
  时，用反查到的厂商预设默认模型补上 —— 避免老数据带病。

### 教训

"强制 agent 显式选" 这条规则是对的，但实现路径错了——不应该砍掉 provider 默认值
（影响 admin 测连通 + 服务端兜底链），而应该在 agent 搭建器引导用户选择（这块已经
在 P4 的「模型名称」下拉里做了）。

## P3 · 防重复提交统一 hook · `useSubmitGuard`（一刀切）

### 起因

用户反馈："点新建草稿，启动慢一点就会一次性生成 3 个"。这是经典的**重复提交（Duplicate
Submission）**问题——React state setter 是异步的，`setCreating(true)` 与 `<Button disabled>`
渲染之间存在 1-50ms 窗口（dev 冷编译时拉到秒级），用户连点会发出多个 POST、各生一条行。
后台所有「新建 / 复制 / 保存」按钮都有同一隐患。

### 设计：A + B 两层（C/D 暂缓）

| 层 | 名字 | 实现 | 防御 |
|---|---|---|---|
| **A** | **useRef 同步锁** | `locked.current = true` 在 onClick 第一行同步生效 | 连点 |
| **B** | **客户端幂等键（Idempotency Key, Stripe 同款）** | 客户端生成 UUID 塞 `Idempotency-Key` header；成功清空、失败保留 | 连点 + 网络重试 + 未来服务端去重的抓手 |
| C | 服务端去重缓存 | 60s 窗口内同 key 返回旧结果 | 跨 tab、A/B 都被绕开 |
| D | DB UNIQUE 约束 | 加列 + UNIQUE INDEX | 终极兜底 |

本次只做 A + B（一刀切），C/D 等真有 incident 再上。

### 新增 hook · [`lib/hooks/use-submit-guard.ts`](../../lib/hooks/use-submit-guard.ts)

```tsx
const guard = useSubmitGuard();
async function create() {
  await guard.submit(async (idempotencyKey) => {
    const res = await fetch("/api/...", {
      method: "POST",
      headers: { "Content-Type": "application/json", "Idempotency-Key": idempotencyKey },
      body: JSON.stringify({ ... }),
    });
    // 业务逻辑（toast / router.push / loadList / ...）
  });
}
<Button onClick={create} loading={guard.loading}>新建</Button>
```

行为细节（写给小B 复审）：
- `submit` 第一行同步置 `locked.current = true`，并发 submit 直接 return undefined（A）。
- 首次 submit 生成 UUID 缓存在 `keyRef.current`；成功后清空（下次新意图换新 key）。
- **失败时保留 key** —— 用户重试是同一意图，未来服务端做去重时可识别"这是同一次的重试"。
- `loading` 给 `<Button loading={...}>` 用，与原 `useState` 行为对齐。
- 服务端**当前不消费 `Idempotency-Key`** —— 本次只把客户端那一层做对；服务端去重（C）
  作为未来 incident 触发后才上的方案。

只覆盖**会产生新行 / 副作用不可逆**的 POST，PATCH（天然幂等）不带 Idempotency-Key：
