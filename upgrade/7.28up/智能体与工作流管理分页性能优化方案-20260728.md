# 7.28up 智能体与工作流管理分页性能优化方案

> 日期：2026-07-28  
> 状态：R2 修订稿，待正式通过  
> 评审结论：方案主体通过；R2 补齐 v61 RPC 调用安全和超旧上限 oracle 两项开发前阻断  
> 适用项目：`agent-01`  
> 目标页面：`/admin/agent-center`、`/admin/workflows`

## 1. 结论

当前两个页面都有分页控件，但数据访问方式并未全部做到“只查询当前页”：

| 页面 | 当前主列表 | 进入页面时的额外加载 | 主要问题 |
|---|---|---|---|
| 智能体管理 | 前端传 `page/pageSize` | 旧路径最多扫描 2000 个智能体及其关联数据 | `ADMIN_AGENT_CENTER_V2` 未开启时，后端全量扫描、逐条鉴权、内存分页 |
| 工作流管理 | 工作流主表已使用数据库 `.range()` 分页 | 最多加载 2000 个智能体候选、组织树、标签统计和全部工作流权限行 | 首屏被非首屏必需数据阻塞；统计和权限查询仍有大范围扫描 |

7.28up 不把“增加分页按钮”作为目标，而是把以下规则落实到数据库和接口层：

1. 列表接口只返回当前页数据。
2. 搜索、筛选、权限过滤必须先于分页，并尽量在数据库完成。
3. 首屏不加载编辑弹窗、选择器和权限弹窗才需要的数据。
4. 查询次数不能随智能体或工作流总量线性增长。
5. 所有新路径均通过 Feature Flag 灰度，保留短期回滚能力。

---

## 2. 优化目标

### 2.1 用户体验目标

- 进入智能体管理和工作流管理时，列表骨架尽快出现，不等待全量候选数据。
- 切换分页、标签、状态和搜索条件时，只刷新列表区域。
- 打开“绑定智能体”选择器后再加载候选，支持搜索和连续翻页。
- 快速连续输入搜索条件时，不出现旧请求覆盖新结果。
- 删除当前页最后一条记录后，自动回到有效页，不出现空白页。

### 2.2 技术指标

以接近生产的数据量进行验证：

- 智能体：至少 2000 条，建议补充 10000 条档位。
- 工作流：至少 1000 条，建议补充 5000 条档位。
- 工作流步骤：平均每个工作流 5～10 步。
- 权限：覆盖超级管理员、系统管理员、组织管理员、自定义管理员。

验收目标：

| 指标 | 目标 |
|---|---:|
| 普通列表接口 P95 | ≤ 800ms |
| 翻页/筛选接口 P95 | ≤ 500ms，复杂权限场景可放宽至 800ms |
| 接口错误率 | < 0.1% |
| 智能体列表返回条数 | 永远不超过 `pageSize` |
| 工作流列表返回条数 | 永远不超过 `pageSize` |
| 首次进入工作流页的智能体候选请求 | 0 次 |
| 非超级管理员逐智能体鉴权查询 | 0 次 |
| 业务查询次数与总记录数的关系 | 基本固定，不随总量线性增加 |
| 数据库扫描行数 | 单独采集；准确 `total` 和统计聚合允许随数据量增长，但不得回传全量明细到 Node.js |
| 响应大小 | 按接口记录 P50/P95；列表响应只包含当前页及必要统计 |

- 不改变现有角色、权限键和资源可见性语义。
- 不改变工作流执行、会话、聊天和步骤编排业务规则。
- 不为了性能删除分类统计、引用数、会话数等现有展示字段。
- 不在未经等价验证时直接删除旧接口路径。

## 4. 总体实施路线

建议分四个阶段完成：

1. **阶段 A：补齐 7.23up 上线门禁**  
   执行 v57～v59、索引与等价测试，灰度启用智能体中心 SQL 分页。
2. **阶段 B：工作流首屏减载**  
   首屏不再请求全量智能体候选和组织树，工作流步骤直接返回已绑定智能体摘要。
3. **阶段 C：候选智能体服务端分页**  
   新增轻量分页 RPC/API，选择器打开后按需搜索。
4. **阶段 D：工作流列表 SQL 化**  
   统计、权限范围、分页和跨页定位统一在数据库完成，移除 5000 ID 扫描。

阶段 A、B 是本轮最高优先级。阶段 C 完成后，工作流页进入时的主要全量查询即可消除。阶段 D 用于进一步稳定大数据量和复杂权限场景下的 P95/P99。

### 4.1 开发前门禁

以下门禁未通过前，不得开始阶段 C、D 的正式开发或生产放量：

1. **绑定目标鉴权与摘要脱敏门禁**
   - 新增、修改步骤绑定时，服务端重新校验目标智能体存在且 actor 具备 `agent.read`。
   - 工作流响应中的智能体摘要使用同一权限口径批量过滤。
   - 摘要不返回 `external_url`、API 地址、密钥、模型参数等非列表必需字段。
   - Picker 只负责候选展示，绝不作为写接口的授权边界。
2. **Picker 契约版本门禁**
   - 旧 `/api/admin/agents/picker` 契约在滚动发布期间保持不变。
   - 分页能力使用新路径或显式版本参数，旧标签页不能静默退化为只能看到前 20 条。
   - Feature Flag 只控制版本化接口背后的实现路径，不能代替请求契约版本控制。
3. **v61 RPC 调用安全门禁**
   - `admin_workflow_page` 使用 `SECURITY INVOKER`。
   - 撤销 `PUBLIC/anon/authenticated` 执行权限，只授权 `service_role`。
   - SQL 内所有表、视图和函数使用 `public.` 等明确 schema 限定。
   - 权限参数只能由登录后的 Node.js 根据 actor 构建，禁止客户端直接传入或透传。
4. **工作流统计口径门禁**
   - 冻结 `stats_base` 和 `page_base` 的定义。
   - 冻结关键词、标签、未分类、多标签和 `focusId` 语义。
5. **分层 oracle 门禁**
   - 旧实现上限以内，旧、新接口必须严格等价。
   - 超过旧实现 2000/5000 条上限时，改用独立 SQL、预置期望 ID 集或确定性夹具作为 oracle。
   - 超上限用例必须明确断言旧实现的已知错误与新实现的正确结果，不能让旧缺陷阻断修复。
6. **缓存安全门禁**
   - 不使用无法感知跨管理员权限变更的长期浏览器候选缓存。
   - 写接口每次重新鉴权，不信任前端缓存结果。
7. **目标环境门禁**
   - 仓库只能确认 v57～v59 和验证脚本已存在；目标数据库迁移、索引是否执行必须单独验收。
   - 当前本地 `.env.local` 未设置 `ADMIN_AGENT_CENTER_V2`，本地默认仍走旧路径。

## 6. 阶段 B：工作流页面首屏减载

### 6.1 当前问题

工作流页面进入时，`loadReferenceData()` 会并行请求：

- `/api/admin/agents/picker`
- `/api/admin/wf-categories`
- `/api/admin/org-tree?purpose=picker`

其中智能体候选最多返回 2000 条；非超级管理员还会逐条执行权限判断。虽然工作流主列表已经分页，但页面的 `loading` 会等待这些参考数据完成，因此用户仍然感觉“进入页面很卡”。

### 6.2 目标加载顺序

首次进入页面只加载：

1. 当前页工作流列表；
2. 工作流标签字典。

以下数据改为按需加载：

| 数据 | 触发时机 |
|---|---|
| 智能体候选 | 打开“绑定智能体”选择器时 |
| 组织、部门、小组树 | 打开新增、编辑或权限范围弹窗时 |
| 工作流详细步骤扩展信息 | 打开详情或展开工作流时；当前页需要展示的摘要除外 |

工作流列表请求完成后即可结束主列表 loading，不再等待智能体候选和组织树。

### 6.3 当前页已绑定智能体摘要

当前工作流页面依靠全量 `agents` 数组，将 `workflow_steps.agent_id` 转换为智能体名称。取消全量候选后，需要让工作流列表接口直接返回当前页步骤所需的智能体摘要。

建议将当前步骤结构扩展为：

```ts
type WorkflowStepAgentSummary = {
  id: string;
  agent_code: string;
  name: string;
  platform: string;
  agent_type: string;
  published_from_draft_id: string | null;
};

type WorkflowStep = {
  id: string;
  agent_id: string | null;
  agent: WorkflowStepAgentSummary | null;
  // 其余现有字段保持不变
};
```

由于服务端使用高权限数据库连接，禁止把 `workflow_steps` 直接外键关联出的所有 `agents` 字段原样返回。正确处理顺序为：

1. 查询当前页工作流及步骤，收集非空 `agent_id`。
2. 使用与 Picker、绑定写接口一致的 `agent.read` 权限口径，批量计算 actor 可读的智能体 ID。
3. 只对可读 ID 查询上述最小摘要字段。
4. 不可读、已删除或不合法的 ID 一律返回 `agent=null`。
5. 前端展示绑定名称、来源和跳转链接时优先使用 `step.agent`，不再依赖全量候选列表。

摘要默认不返回 `external_url`。如果后续确有跳转外链的产品需求，必须单独评审字段暴露范围和链接权限，不能随列表摘要自动放开。

兼容规则：

- 智能体已删除或无权读取摘要时，`agent=null`，仍显示原有“绑定信息不可用”兜底。
- 更新步骤绑定成功后，使用选择器返回的智能体摘要更新本地状态。
- 刷新后以后端返回值为准。

### 6.4 绑定写接口重新鉴权

当前 Picker 返回了某个候选，不代表后续写入时该 actor 仍然有权读取该智能体。新增或修改绑定必须在服务端重新鉴权。

需要修改：

- `app/api/admin/workflows/[id]/steps/route.ts`
- `app/api/admin/workflow-steps/[id]/route.ts`

当请求包含非空 `agentId` 时，服务端依次执行：

1. 校验工作流更新权限和创建者层级规则。
2. 查询目标智能体是否存在。
3. 使用当前 actor 调用统一的 `agent.read` 校验。
4. 只有校验通过后才写入 `workflow_steps.agent_id`。

错误语义：

- 智能体 ID 格式错误：`400 VALIDATION_ERROR`。
- 智能体不存在或当前 actor 不可读：对客户端统一返回 `404 NOT_FOUND` 和相同错误文案，避免通过 403/404 差异探测智能体是否存在。
- 服务端审计日志可以记录内部真实原因，但不得把存在性差异返回给客户端。
- `agentId=null` 表示解除绑定，仍只要求工作流更新权限。

建议抽取统一服务端 helper，例如：

```text
lib/agent-binding-access.ts
```

该 helper 同时服务于新增步骤、修改步骤和未来的批量绑定入口，避免不同写接口出现权限口径漂移。Picker 结果、前端隐藏和本地缓存均不能替代此校验。

### 6.5 拆分页面加载状态

将当前单一 `loading` 至少拆为：

```ts
listLoading
categoryLoading
pickerLoading
orgTreeLoading
mutationLoading
```

这样打开权限弹窗或加载下一页候选时，不会让整个工作流列表重新进入全屏加载状态。

工作流列表请求还要增加 `AbortController` 或请求序号，只允许最新的翻页、搜索和筛选响应写入状态。删除当前页最后一条工作流时，与 Agent Center 保持一致：当前页大于 1 则加载上一页，否则刷新当前页。

## 7. 阶段 C：绑定智能体选择器改为服务端搜索与分页

### 7.1 新接口契约

旧前端依赖 `/api/admin/agents/picker` 一次返回最多 2000 条，并读取 `capped/totalCount`。同一路径直接改成只返回第一页会导致滚动发布期间的旧标签页静默退化。因此旧接口暂时保持原契约，分页能力使用新路径：

```http
GET /api/admin/agents/picker/page?q=&page=1&pageSize=20
```

参数：

| 参数 | 规则 |
|---|---|
| `q` | 可选；匹配名称、编号、平台，服务端转义特殊字符 |
| `page` | 默认 1，最小 1 |
| `pageSize` | 默认 20，最大 50 |

响应：

```json
{
  "contractVersion": 2,
  "data": [
    {
      "id": "uuid",
      "agent_code": "AGENT-001",
      "name": "示例智能体",
      "platform": "coze",
      "agent_type": "chat",
      "published_from_draft_id": null
    }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 235
  }
}
```

兼容方案：

- `/api/admin/agents/picker` 在兼容期继续返回旧的 `data/totalCount/capped`。
- 新前端只请求 `/api/admin/agents/picker/page` 并校验 `contractVersion=2`。
- `ADMIN_AGENT_PICKER_V2` 只控制 `/picker/page` 背后的 SQL 实现或兼容回退实现，不改变该 URL 的分页响应结构，也不要求客户端读取服务端环境变量。
- 新接口不返回 `capped`；超过一页的数据通过搜索或翻页获取。
- 当前已绑定智能体不依赖候选页是否包含，由 `step.agent` 直接展示。
- 至少跨一个稳定发布周期，并确认访问日志中已无受支持旧前端调用后，才单独删除旧接口。
- 通过代码版本回滚新前端时切回旧组件和旧路径，不影响旧标签页。

### 7.2 数据库实现

新增：

```text
supabase/migration_v60_admin_agent_picker_rpc.sql
```

新增 RPC：

```text
admin_agent_picker_page(...)
```

RPC 要求：

- 复用 `agent_effective_admin_scopes`，保持与智能体中心一致的权限语义。
- 先完成可见性和搜索过滤，再执行分页。
- 只查询选择器需要的轻量字段。
- 一次返回当前页与准确 `total`。
- 固定使用 `ORDER BY name ASC, id ASC`，确保翻页稳定。
- `.all` 是唯一的全范围绕过路径。
- 非法或无法反查的组织、部门、小组范围必须 fail-closed。
- `SECURITY INVOKER`。
- 撤销 `PUBLIC/anon/authenticated` 执行权限，只授权 `service_role`。

禁止继续采用：

- `.limit(2000)` 后前端搜索；
- Node.js 中逐条调用 `requireAccess()`；
- 为了显示当前绑定项而全量加载候选。

### 7.3 选择器交互

修改 `AgentBindPopover`：

- 打开时请求第 1 页。
- 输入搜索词 300ms 防抖。
- 新搜索取消上一条请求。
- 支持“加载更多”或页码翻页，推荐“加载更多”。
- 每次最多追加 20～50 条。
- 相同 ID 去重。
- 关闭弹窗时取消未完成请求。
- 默认只在本次弹窗实例内缓存已加载页；关闭后不保留长期候选缓存。
- 再次打开时重新请求第 1 页；如需减少闪烁，可先显示本组件实例旧值并立即后台校验，但新响应返回前不得据此授权写入。
- 如果未来引入跨弹窗缓存，缓存键必须至少包含 actor、session/权限版本和查询条件；没有可靠权限版本时不得启用长期缓存。
- 请求失败时保留已加载结果，并显示局部重试，不关闭整个工作流页面。
- 最终提交绑定时，写接口仍按 6.4 重新校验目标智能体读取权限。

## 8. 阶段 D：工作流列表查询 SQL 化

### 8.1 第一批低风险收窄

在不改变接口响应的前提下，先完成以下修改：

1. 先查询当前页工作流。
2. 取得当前页 `workflowIds`。
3. `resource_permissions` 只查询：

   ```ts
   .eq("resource_type", "workflow")
   .in("resource_id", workflowIds)
   ```

4. 创建者名称只查询当前页 `created_by`。
5. 工作流步骤和绑定智能体摘要只查询当前页。

这一步只优化“分页后当前页权限摘要和操作能力”的查询，不能替代分页前的可见性计算：

- 分页前：确定 actor 能看到哪些工作流，旧路径仍可能向 Node.js 返回大量可见工作流 ID。
- 分页后：只为当前页聚合权限摘要和操作能力，本节的 `.in("resource_id", workflowIds)` 可以立即收窄这一部分。

只有 v61 将工作流可见性过滤迁移到 SQL 后，才能真正消除分页前的大量权限 ID 回传。

### 8.2 统计和分类计数

当前实现最多扫描 5000 个工作流 ID，再将 `workflow_categories` 拉回 Node.js 统计。建议新增：

```text
supabase/migration_v61_admin_workflow_page_rpc.sql
```

新增 RPC：

```text
admin_workflow_page(...)
```

输入参数覆盖：

- 管理员可读范围；
- `q`
- `categoryId`
- `status`
- `visible`
- `focusId`
- `page`
- `pageSize`

返回：

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 10,
    "total": 0,
    "focusFound": false,
    "focusPage": null
  },
  "stats": {
    "total": 0,
    "ungrouped": 0,
    "categoryCounts": {}
  }
}
```

实现要求：

- 可见范围、搜索、状态和可见性筛选在数据库完成。
- 分类计数使用 SQL 聚合，不向 Node.js 返回最多 5000 个 ID。
- 当前页使用 `OFFSET/LIMIT` 或等价的窗口分页。
- `focusId` 使用 `row_number()` 计算所在页，不查询 4999 条 ID 后在 Node.js `findIndex()`。
- 只聚合当前页步骤、绑定智能体和权限信息。
- 保持现有排序规则 `sort_order ASC`，相同排序值增加 `id ASC` 作为稳定排序。
- 返回准确 `total`，不能受 PostgREST 默认行数上限影响。
- 权限语义必须与现有 builtin/custom admin 路径逐角色等价。
- 函数必须使用 `SECURITY INVOKER`，不得使用 `SECURITY DEFINER` 扩大调用者权限。
- SQL 内所有业务对象使用 `public.workflows`、`public.resource_permissions` 等完整 schema 限定；不得依赖调用者可控的 `search_path`。
- 函数定义显式设置安全的 `search_path`，例如 `SET search_path = pg_catalog, public`。
- 迁移必须在函数创建后按其完整参数签名执行：

  ```sql
  REVOKE ALL ON FUNCTION public.admin_workflow_page(<exact_arg_types>)
    FROM PUBLIC, anon, authenticated;

  GRANT EXECUTE ON FUNCTION public.admin_workflow_page(<exact_arg_types>)
    TO service_role;
  ```

- `<exact_arg_types>` 在正式迁移中必须替换为函数的完整 PostgreSQL 参数类型，禁止保留占位符。
- Node.js API 只接受 `q/categoryId/status/visible/focusId/page/pageSize` 等业务筛选参数；`canReadAll`、组织/部门/小组范围和其它权限参数只能在完成登录校验后根据 `PermissionActor` 构建。
- 禁止把浏览器提交的权限布尔值、scope ID 数组或角色名称直接透传给 RPC。
- `scripts/verify-7.28up-db.ts` 必须验证函数存在、`anon/authenticated` 无 EXECUTE、`service_role` 有 EXECUTE，并验证函数不是 `SECURITY DEFINER`。

### 8.3 冻结统计和筛选口径

v61 至少使用两个明确的数据集：

```text
stats_base
  = 权限可见性
  + q 关键词
  + status
  + visible
  - categoryId

page_base
  = stats_base
  + categoryId
```

响应口径：

- `stats.total`：`stats_base` 中去重后的工作流数量。
- `stats.categoryCounts`：基于 `stats_base` 统计，每个工作流在同一分类中只计一次。
- `stats.ungrouped`：`stats_base` 中没有任何 `workflow_categories` 行的工作流数量。
- `pagination.total`：`page_base` 中去重后的工作流数量。
- 当前页数据和 `focusPage`：均基于 `page_base`。

关键词语义继续兼容旧接口：

- `q` 匹配工作流名称；
- `q` 匹配工作流描述；
- `q` 匹配标签名称；
- 一个工作流命中多个标签时只返回一次。

`visible` 语义：

- `all/org_only/personal_only/custom`：精确匹配 `workflows.visible_to`。
- `custom:org`：先要求 `visible_to='custom'`，再要求至少存在一条 `resource_type='workflow' AND scope_type='org'` 的权限行。
- `custom:dept`：先要求 `visible_to='custom'`，再要求至少存在一条 `scope_type='dept'` 的权限行。
- `custom:team`：先要求 `visible_to='custom'`，再要求至少存在一条 `scope_type='team'` 的权限行。
- 同一工作流同时具有 org/dept/team 多类 scope 时，会分别出现在对应的 `custom:*` 筛选结果中，但单次结果内按工作流去重。
- `custom:*` 只在 actor 已通过工作流可见性过滤的集合内进一步筛选，不能借此扩大可见范围。
- 除 `org/dept/team` 外的 `custom:<suffix>` 一律返回 `400 VALIDATION_ERROR`，不得拼接进 SQL。

分类语义：

- 未分类指工作流不存在任何标签关系。
- 多标签工作流在每个所属分类的 `categoryCounts` 中分别计 1。
- `stats.total` 仍按工作流去重计数，不因多标签重复。
- 选择某一分类后，`pagination.total` 是该分类下的工作流去重数量。

`focusId` 语义保持现有行为：只在当前权限和当前全部筛选条件（包括 `q/status/visible/categoryId`）形成的 `page_base` 内定位。目标存在但不满足当前筛选时返回 `focusFound=false`，不自动清除筛选扩大结果集。

旧接口与 v61 对比时，必须分别断言 `stats.total`、`stats.ungrouped`、每个分类计数、`pagination.total`、ID 集合、顺序和 `focusPage`。

### 8.4 Node.js 层保留职责

数据库负责：

- 可见工作流过滤；
- 搜索、筛选；
- 总数和分类统计；
- 当前页定位；
- 当前页关联聚合。

Node.js 负责：

- 登录和 token 校验；
- 构建权限输入；
- 输入参数校验；
- 写操作能力和创建者层级规则的最终校验；
- 响应日志、错误映射和 Feature Flag 路由。

若工作流写操作能力无法在第一版 RPC 中安全等价，可先对当前页 10～50 条记录在 Node.js 中计算，但禁止再次读取全表。

## 9. 索引方案

索引必须以 `EXPLAIN (ANALYZE, BUFFERS)` 为依据，不能只因“可能有用”就直接生产创建。

候选索引：

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS workflow_categories_category_workflow_idx
  ON public.workflow_categories(category_id, workflow_id);

CREATE INDEX CONCURRENTLY IF NOT EXISTS resource_permissions_type_scope_resource_idx
  ON public.resource_permissions(resource_type, scope_type, scope_id, resource_id);

CREATE INDEX CONCURRENTLY IF NOT EXISTS workflows_sort_order_id_idx
  ON public.workflows(sort_order, id);

CREATE INDEX CONCURRENTLY IF NOT EXISTS agents_created_at_id_idx
  ON public.agents(created_at DESC, id);

CREATE INDEX CONCURRENTLY IF NOT EXISTS agents_name_id_idx
  ON public.agents(name, id);
```

`agents_name_id_idx` 用于 Picker 的无关键词稳定排序。若 `q` 继续使用 `%关键词%` 子串匹配，普通 B-tree 不能直接解决搜索扫描问题；只有在执行计划和数据量证明必要时，再评估 `pg_trgm` 与 GIN/GiST 索引。启用扩展和新增大索引必须独立评审，不包含在默认迁移中。

执行规则：

1. 每个索引保存创建前计划。
2. 明确记录 `create` 或 `not_required` 决策及理由。
3. 决定创建时必须使用独立非事务会话执行 `CREATE INDEX CONCURRENTLY`。
4. 创建后保存执行计划、索引大小、构建耗时和 CPU/锁等待。
5. 对无收益或写放大明显的索引不予创建。

## 12. 权限等价验证

性能优化不能改变“谁能看到什么”。至少覆盖：

### 12.1 智能体

- 超级管理员：全部智能体。
- 系统管理员：按现有 `.all/.org` 权限包。
- 组织管理员：只看本组织允许的智能体。
- 自定义管理员：
  - `agent.read.all`
  - `agent.read.org`
  - 无 read 权限
- 智能体同时存在多个 scope：
  - 全部 scope 都在组织内；
  - 同时包含组织内和组织外 scope；
  - `all + 其它 scope`
  - 完全无权限行但存在发布草稿创建者回退；
  - 非法 dept/team；
  - 仅含非管理 scope。

### 12.2 工作流

- `workflow.read.all/org/dept/team` 分别验证。
- builtin org_admin 与 custom admin 结果集合等价。
- `visible_to=all/org_only/custom/personal_only`。
- `visible=custom:org/custom:dept/custom:team` 分别验证：
  - 只命中对应 scope 类型；
  - 同一工作流具有多类 scope 时分别命中且单次结果不重复；
  - 不扩大 actor 原本可见范围；
  - 非法 `custom:<suffix>` 返回 400。
- 工作流同时绑定多个组织、部门、小组。
- 标签、状态、关键字筛选组合。
- 未分类工作流。
- `focusId`：
  - 目标存在且有权；
  - 目标不存在；
  - 目标存在但无权；
  - 目标位于第一页之外。
- 绑定目标安全：
  - 有工作流更新权限且可读目标智能体，允许绑定；
  - 有工作流更新权限但不可读目标智能体，必须返回与不存在相同的 404 和相同文案；
  - 目标智能体不存在，返回统一 404；
  - 前端伪造未出现在 Picker 中的 `agentId`，服务端仍必须拦截；
  - 绑定后失去智能体读取权限，列表摘要必须变为 `null`；
  - 不可读摘要不得泄露名称、平台、外链或其它智能体字段。

### 12.3 两档 oracle 策略

旧路径只能作为兼容基线，不能在超过自身已知上限后继续充当唯一真值。

#### 第一档：旧上限以内严格等价

适用数据集：

- Agent Center/Picker 可见智能体数量不超过 2000；
- 工作流统计参与数量不超过 5000；
- `focusId` 所在位置不超过第 5000 条。

同一账号、同一参数分别请求旧路径和新路径，严格对比：

- ID 集合；
- 总数；
- 分类统计；
- 当前页排序；
- 操作能力；
- 绑定智能体摘要；
- `focusFound/focusPage`。

除已经单独登记并获批的安全收紧差异外，任何差异都阻断灰度。

#### 第二档：超过旧上限使用独立 oracle

至少准备以下确定性夹具：

- 2001 条以上 actor 可见智能体，并将目标记录放在第 2001 条以后；
- 5001 条以上满足工作流统计条件的工作流；
- `focusId` 分别放在第 5001 条和末页；
- 多标签、未分类、`custom:org/dept/team` 混合 scope；
- 同时包含可见和不可见目标的权限夹具。

oracle 不能调用 v60/v61 本身，也不能复用待测 RPC 的核心 CTE。可选来源：

1. 测试夹具生成时保存的预置期望 ID 集、总数、分类计数和顺序；
2. 独立、只读、显式 SQL 查询；
3. 小数据分块查询后由验证脚本合并，并与预置夹具交叉校验。

超上限用例应明确断言预期差异：

- 旧 Picker/Agent Center 截断或遗漏第 2001 条以后数据；
- 旧工作流统计在第 5001 条以后不完整；
- 旧 `focusId` 对第 5001 条以后目标可能返回未找到；
- 新实现必须返回完整、准确且稳定排序的结果。

在第二档中，“新实现与旧实现不同”本身不是失败；只有新实现不符合独立 oracle 才失败。验证报告必须把“兼容差异”和“缺陷修复差异”分栏展示。

## 13. 性能与前端验收清单

### 13.1 浏览器 Network

进入 `/admin/agent-center`：

打开绑定智能体选择器：

- 快速连续输入时，旧请求被取消或响应被忽略。
- 翻页或加载更多时不重复已有 ID。
- 请求路径为版本化 `/api/admin/agents/picker/page`，旧 Picker 契约保持可用。
- 结果固定按 `name ASC, id ASC` 排序。

### 13.2 数据库

- Agent Center V2 不出现逐智能体鉴权查询。
- Agent Picker V2 不读取 2000 条后再过滤。
- Workflow List V2 不返回最多 5000 个 ID给 Node.js 统计。
- 工作流可见性在 SQL 内完成，不向 Node.js 回传全量可见 ID。
- 权限摘要及操作能力只聚合当前页。
- 高并发下无异常锁等待、连接耗尽和显著 CPU 尖峰。
- 报告分别记录 SQL 调用次数、扫描行数、返回行数和响应字节；不能只用“查询次数固定”代替扫描成本分析。

### 13.3 正确性

- 搜索总数与分页结果一致。
- 分类数量与点击分类后的结果总数一致。
- 删除、启停、编辑后当前页和统计同步刷新。
- 新增数据后无需清除浏览器缓存即可搜索到。
- 选择器关闭后不依赖长期候选缓存；重新打开会重新校验第 1 页。
- 绑定写入始终重新鉴权，即使页面仍显示旧候选。
- URL `focus` 跨页定位保持可用。

### 13.4 可复现压测模型

每个并发档位分别执行，不能把不同并发级别的样本混在一起计算百分位：

1. 冷缓存基线：
   - 新实例或清理允许清理的应用缓存；
   - 每类接口至少执行 100 次，用于记录首次查询和计划预热影响。
2. 升压：
   - 10 并发运行 1 分钟；
   - 50 并发运行 2 分钟；
   - 100 并发运行 2 分钟。
3. 稳态：
   - 10、50、100 并发分别持续 10 分钟；
   - 每个档位至少 1000 个有效请求，否则百分位只作参考。
4. 场景占比：
   - 30% 首屏列表；
   - 25% 翻页；
   - 20% 关键词搜索；
   - 10% 状态/分类筛选；
   - 10% 打开 Picker 并搜索/加载更多；
   - 5% `focusId` 跨页定位。
5. 数据分布：
   - 搜索词同时覆盖高命中、低命中和零命中；
   - 页码覆盖第 1 页、中间页和末页；
   - 角色请求按实际生产占比分配，并单独输出各角色指标。

报告必须逐接口、逐并发档位输出：

- 请求数、成功数、错误率；
- P50/P95/P99 和最大耗时；
- 响应字节 P50/P95；
- 数据库 CPU、连接、锁等待和慢 SQL；
- SQL 调用次数、扫描行数、返回行数；
- Node.js RSS、heap 和事件循环延迟；
- 冷缓存与热缓存结果。

## 15. 回滚方案

### 15.1 应用回滚

- `ADMIN_AGENT_CENTER_V2=false`
- `ADMIN_AGENT_PICKER_V2=false`
- `ADMIN_WORKFLOW_LIST_V2=false`
- 重启或重新部署应用实例。

关闭开关后恢复旧接口逻辑，数据库新增 View/RPC 可保留，不影响旧路径。

### 15.2 数据库回滚

- 新 RPC 和索引均为增量对象，不修改现有业务表数据。
- 出现严重问题时优先关闭 Feature Flag，不立即删除数据库对象。
- 确认无旧实例调用后，再按独立回滚脚本撤销函数授权或删除函数。
- 删除并发索引前保存使用情况和执行计划；不得在业务高峰直接删除大索引。

### 15.3 回滚触发条件

满足任一条件立即停止放量：

- 新旧权限结果不一致；
- 5xx 或超时率明显高于基线；
- P95 连续 10 分钟超过基线 30%；
- 数据库 CPU、连接或锁等待达到告警阈值；
- 出现跨组织数据可见；
- 分页丢数据、重复数据或总数明显错误。

## 17. Definition of Done

只有同时满足以下条件，7.28up 才能视为完成：

- 智能体管理生产运行路径使用 SQL 分页。
- 工作流首屏不再加载全量智能体候选。
- 智能体选择器通过版本化接口使用服务端搜索和分页，滚动发布期间旧契约保持兼容。
- 新增、修改步骤绑定均在服务端校验目标智能体存在且 actor 具备 `agent.read`。
- 不存在与不可读的绑定目标对客户端统一返回 404，不能通过响应差异探测资源存在性。
- `step.agent` 只返回经过同一权限口径过滤的最小摘要，不泄露外链或其它非必要字段。
- v61 使用 `SECURITY INVOKER`、完整 `public.` 限定，撤销 `PUBLIC/anon/authenticated` 执行权且只授权 `service_role`；权限参数只由登录后的 Node.js actor 构建。
- 工作流可见性在 SQL 内完成，不向 Node.js 回传全量可见 ID；权限摘要及操作能力只聚合当前页。
- 工作流统计严格遵循冻结的 `stats_base/page_base` 口径，不再扫描并回传最多 5000 个 ID。
- `visible=custom:org/custom:dept/custom:team` 语义和非法后缀校验通过。
- 旧上限以内所有角色新旧结果严格等价；超出旧上限时新实现符合独立 oracle，并记录预期缺陷修复差异。
- Feature Flag、readiness、回滚和数据库验收脚本齐全。
- 测试/预生产按可复现模型完成压测并达到本方案目标。
- 生产灰度期间无跨组织数据、分页错乱和显著性能回退。
