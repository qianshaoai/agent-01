## 条目 1 · 只授「新建草稿」权限：建得了草稿却打不开搭建器、误弹「权限不足」

**现象（用户验收）**
给小组长（custom 角色）只授了「智能体（草稿）`agent_draft`」各动作的「本组织」权限。点「新建智能体」时弹「权限不够」，**但草稿却真的建出来了一个** —— 既报错又建成，逻辑矛盾。

**根因（前后两步权限要求不一致，非判错）**
新建智能体是两步独立操作，权限口径不一致：

1. 列表页 `create()` 发 `POST /api/admin/agent-drafts`（[`app/admin/agent-builder/page.tsx:91`](../../app/admin/agent-builder/page.tsx)）。该接口**只要求 `agent_draft` 的 create / 查看 / 编辑**（[`app/api/admin/agent-drafts/route.ts:105-114`](../../app/api/admin/agent-drafts/route.ts)）—— 小组长全有 → **草稿成功落库、返回 200**。
2. 成功后立刻 `router.push('/admin/agent-builder/{新id}')` 跳搭建器编辑页（同文件 `:100`）。
3. 编辑页 `load()` 并行抓 4 个接口（[`app/admin/agent-builder/[id]/page.tsx:367-375`](../../app/admin/agent-builder/[id]/page.tsx)），其中 `GET /api/admin/model-providers?category=model` **要求 `provider.read.org` 或 `.all`**（[`app/api/admin/model-providers/route.ts:75-83`](../../app/api/admin/model-providers/route.ts)）。小组长**只授了 `agent_draft`、没授 `provider` 读取** → 返回 403「权限不足」。
4. 编辑页 `if (!provRes.ok) throw new Error(provData.error)` → `toast("权限不足")`（`:380` / `:437`）。

所以用户看到的「权限不够」是跳转后的编辑页拉「模型供应商」被拒弹出的，而草稿在上一步就已经建好了。
（草稿本身的读取 `GET /api/admin/agent-drafts/{id}` 对小组长是放行的——他有 `agent_draft.查看.本组织`、草稿归属又是他自己；卡住的精确是供应商接口。）

**修复方向（用户拍板：搭建器容错降级）**
不再让「供应商列表拉取失败」把整个编辑页 hard-fail；改成像同页知识库那样降级为空列表照常打开，并在模型设置区给出精确提示。**不改任何接口 / 权限模型**，避免把 `provider.read` 强行绑进 `agent_draft` 授权（那是另一个更大的口径调整，本次不做）。

| 文件 | 改动 |
|---|---|
| `app/admin/agent-builder/[id]/page.tsx` | ① 新增 state `providersUnavailable`；② `load()` 里供应商 fetch 加 `.catch(() => null)`，删除 `if (!provRes.ok) throw` 这行硬失败，改为 `if (provRes && provRes.ok)` 才解析、否则空列表 + 置 `providersUnavailable=true`；③ 「2. 模型设置」供应商空态提示区分两种情况：`providersUnavailable` 时提示「无法加载模型供应商列表（可能缺少「API 读取」权限）…需联系管理员补授后再来」，否则保留原「当前没有可用供应商，去模型接入添加」。|

效果：小组长只授 `agent_draft` 也能新建并打开草稿，编辑名称/描述等；模型下拉因缺 `provider.read` 为空，但有明确文案，不再误弹「权限不足」、不再「建得了打不开」。草稿 GET / 自动保存(PATCH) / 试跑 / 发布等仍各按自身 `agent_draft` 子权限走，未动。

**CI** `npx tsc --noEmit` ✅ 0 error。dev server（webpack）重编译无报错。

**未验证** 需以小组长身份登录后台实测：新建 → 进编辑页不弹错、模型区显示缺权限提示（验收时一并看）。本机 dev 无小组长测试账号，未跑端到端。

## 条目 2 · dev server 裸 `npm run dev`（Turbopack）启动即崩 → 根因清除，Turbopack 恢复

**性质** dev 环境 / 构建缓存修复，**零代码 / 零接口 / 零 schema 改动**（`next.config.ts` 净未变）。

**现象**
裸 `npm run dev`（Turbopack）启动后首屏编译报 `Can't resolve 'tailwindcss' in 'g:\zhinengticang'` → 白屏/502；`postcss.js` worker 反复 spawn 不回收（一次泄漏 ~136 进程 ≈ 10GB）→ `JavaScript heap out of memory` → dev server 反复猝死。此前一直靠 `npm run dev -- --webpack` 兜底（稳但慢），见 memory `project_dev_webpack_fallback_pending`。

**排查（systematic-debugging · 受控复现 + 进程熔断，全程不让泄漏累积）**
- 顶层 `g:\zhinengticang` 无任何 lockfile / package.json，按 [Next 官方 root 检测机制](https://nextjs.org/docs/app/api-reference/config/next-config-js/turbopack)（只认 5 种 lockfile）不该把 root 判到上级。
- 受控复现 STDERR 实证：`@import "tailwindcss"` 由 PostCSS worker（enhanced-resolve）解析，解析根**独立锚在 `g:\zhinengticang`**，只找 `g:\zhinengticang\node_modules` / `g:\node_modules`，从不看 `agent-01\node_modules`（tailwindcss 实际所在）。
- 试 ① `next.config.ts` 加 `turbopack:{ root: __dirname }` → **无效**（管不到 PostCSS worker 的解析根），已撤回。
- 试 ② 删 stray `g:\zhinengticang\node_modules`（Jun 6 误装的 esbuild/tsx）→ 仍报同样错（root 仍锚上级）。
- **真凶**：`agent-01\.next` 持久缓存 **1.1G**，把 Jun 6 当时（顶层曾有 node_modules + lockfile）推断的旧 root=`g:\zhinengticang` 烤进缓存，每次启动复用中毒 root。`--webpack` 用另一套缓存，故始终正常。

**修复（用户逐项授权）**
1. 删除 stray `g:\zhinengticang\node_modules`（与 agent-01 无关的 cruft，root 触发源）。
2. 删除 `agent-01\.next`（1.1G 中毒持久缓存，可再生）。

**验证（受控复现）** 裸 Turbopack：`HTTP 200`、首屏 31323 bytes、iter0(~5s) 即出、**进程峰值 6（不再泄漏）**、无 tailwindcss 解析错误。✅

**预防 / 复发处理** 别在 `g:\zhinengticang` 顶层跑 `npm i` / `npx`（会生成 node_modules + lockfile，毒化 Turbopack root 并写进 `.next`）。万一再犯：删顶层 stray node_modules + 删 `agent-01\.next` 即可，无需改代码。`scripts/dev.mjs` 的 `--webpack` 兜底保留备用。

## 条目 3 · 「本组织可见」漏掉「全平台公共」资源 —— v2/custom 权限层未对齐 5.30up 规则

**性质** 后端权限逻辑修复，**零 schema 改动**；放宽 org 角色对平台公共资源的【读】可见性，写权限不变。

**现象（用户验收）**
给小组长（custom 角色）授了「本组织可见」的 API（model_provider）读权限后，搭建器「模型设置」里供应商下拉仍为空 —— 平台公共（全平台可见）的 API 没显示。用户指出："给了本组织可见，那全平台可见的它肯定也该可见"。

**根因**
`5.30up` 把「公共(tenant_code=NULL)对 org 可见」写进了 **builtin 通道**（[`lib/scoped-access.ts`](../../lib/scoped-access.ts) 的 `canReadRow` / `listScopeFilter`：`tenant_code IS NULL 或 = 本组织`）。但 `6.4up v2 / Phase D` 给 **custom 角色 + enforce adapter** 那层**没把这条规则带过去**：
- 行级 [`lib/adapters/access/_generic.ts`](../../lib/adapters/access/_generic.ts) `checkRead` 把公共行（NULL）当成「要 `.read.all`」；
- `kb / provider / notice` 的 custom/org 列表分支退化成只 `.eq("tenant_code", 本组织)`，漏掉 NULL。

影响不止列表：org 角色连「引用一个公共 provider/KB 去建/发布智能体」都被行级 `checkRead` 拒（create/publish/duplicate/test-chat 的 `canReadTenantOwned` 全过这条）。审计结论见上一轮对话（逐资源核对表）。

**修复（用户授权"给我修好"）**
| 文件 | 改动 |
|---|---|
| `lib/adapters/access/_generic.ts` | `buildTenantOwnedAdapter` 加 `publicReadableByOrg?` 配置；`checkRead` 对公共行（NULL）若该 flag=true → `checkAnyScopedPermission(actor, prefix, 'read', [], ['all','org','dept','team'])` 放行（持任一 read scope 即可读，因公共=全员可见）。`checkWrite` **不动**（org 仍不能改公共）。 |
| `lib/adapters/access/knowledge-base.ts` / `model-provider.ts` / `notice.ts` | 各置 `publicReadableByOrg: true`（kb / provider / notice 是共享资源）。 |
| `lib/scoped-access.ts` | 抽出 `tenantPublicOrOwnFilter(tenantCode)` = `"tenant_code.is.null,tenant_code.eq.X"` 作单一口径来源；`listScopeFilter` 复用之。 |
| `app/api/admin/model-providers/route.ts` / `knowledge-bases/route.ts` / `notices/route.ts` | 列表 org/custom 分支 `query.eq("tenant_code", X)` → `query.or(tenantPublicOrOwnFilter(X))`（公共 + 本组织）。 |

**未纳入（有意）** `audit`（平台级日志不外泄给 org，公共行仍需 `.read.all`）；`category / tenant` 本就平台级。
**待复核** `user_group / dept / team` 是否存在 NULL 行、是否需同款修复 —— 正用对抗式复核 workflow 查漏，确认的缺口会在本条目下追加。

**CI** `npx tsc --noEmit` ✅ 0 error。dev server（裸 Turbopack）重编译无报错。

**未验证** 需以小组长身份实测：搭建器供应商/知识库下拉能看到并选用「全平台公共」项；引用公共 provider 能正常建/发布。本机 dev 无小组长测试账号，未跑端到端。

## 条目 4 · 自定义角色（org 范围）发布「可见范围」错显平台管理员选项

**性质** 纯前端 UX 修复，**零接口 / 零 schema 改动**；后端 publish 路由本就已强制 org 范围只能发本组织，本次只是让前端选项与之对齐。

**现象（用户验收）**
小组长（custom 角色，仅本组织级权限）在搭建器「6. 发布设置 → 可见范围」里看到「全平台可见」「指定组织可见」选项，且「指定组织可见」下的组织选择器显示「暂无组织」。用户指出：给了（本组织级）权限后，发布应只能「仅自己所在组织可见」。

**根因**
发布可见范围整段 UI 用 `isOrgAdmin = adminRole === "org_admin"` 分支，而 [`/api/admin/me`](../../app/api/admin/me/route.ts) 对 **custom 角色返回 `role: null`** → 小组长 `isOrgAdmin=false` → 被前端当成**平台管理员**，显示「全平台/指定组织可见」+ 任意组织选择器；组织列表又因无 `tenant.read.all` 拉不到 → 「暂无组织」。
后端 [`agent-drafts/[id]/publish`](../../app/api/admin/agent-drafts/[id]/publish/route.ts) 第 131-153 行其实已强制 `isCustomAdmin && !publish.all` 时最大可见范围=本组织（选全平台/他组织会被拒），所以**不是越权，是前端给了会被后端拒的选项 + 空选择器**。

**修复（用户授权"动手改吧"）**
| 文件 | 改动 |
|---|---|
| `app/admin/agent-builder/[id]/page.tsx` | ① 新增 `isPublishOrgScoped` state；`load()` 里从 `meData.source` + `meData.permissions` 算：`role==="org_admin" \|\| (source==="custom_admin" && !perms.includes("agent_draft.publish.all"))`——与后端 publish 口径一致。② 可见范围下拉、组织多选器、"未勾组织"校验、组织列表拉取（org 范围跳过 fetchAllTenants 免 403）全改用 `isPublishOrgScoped` 替代 `isOrgAdmin`。③ 知识库提示那行（line 988 的 `isOrgAdmin`）属另一关注点，本次不动。 |

效果：org 范围（org_admin 或无 publish.all 的 custom 角色）发布时只见「本组织可见 / 暂不公开」，无「全平台可见」「指定组织可见」、无空组织选择器。平台级（super/system、或持 publish.all 的 custom 角色）不变。

**CI** `npx tsc --noEmit` ✅ 0 error。dev server（裸 Turbopack）热更新无报错。

**未验证** 需小组长实测：可见范围下拉只剩「本组织可见 / 暂不公开」；选本组织可见能正常发布。本机 dev 无小组长账号，未端到端。

## 条目 8 · custom 角色 `workflow.read.org` 列表漏掉本组织 dept/team 工作流（"改完工作流不见了"）

**性质** 后端权限列表过滤修复；零 schema。与条目 3 同一类根因（v2/custom 路径未复制 builtin 的 scope 展开）。

**现象（用户验收）**
小组长（custom 角色，持 `workflow.read.org`）在工作流管理里**看不到本组织的小组级/部门级工作流**；把工作流改成小组级后它就从列表"消失"，因此也无法再修改。

**根因**
[`app/api/admin/workflows/route.ts`](../../app/api/admin/workflows/route.ts) 的 `computeCustomAdminVisibleWorkflowIds`：custom 角色持 `read.org` 时，`listReadableScopes` 返回 `{org}`，但该函数**只 push `scope_type=org` 的过滤**，没有展开到本组织下的 dept/team。而 builtin org_admin 列表路径（同文件 142-169 行）是 org + 本组织所有 dept + 本组织所有 team 全展开。→ custom `read.org` 看到的工作流**少于** builtin org_admin，小组级/部门级工作流被漏掉。
（写入路径 update 的 `isScopeWithinOrg` 反查 team/dept 的 tenant_code 是对的，故只有**列表过滤**这处漏。）

**修复（用户授权"你得修"）**
