# 6.6up · 前端权限不足即隐藏 + 资源归属层级写规则 · 方案

**日期** 2026-06-07
**前置** 6.6up 后端全资源 enforce 已落地（`方案-权限后端全量补齐-20260606.md`，后端闸已为准）
**性质** A=纯前端体验对齐；B=后端归属层级 + 前后端配套（含 DB migration）
**口径** 后端永远是最终闸；本方案的前端隐藏只为"别误导"，不替代后端校验。

---

## 背景 & 目标

用户在验收时提两条要求：

1. **权限不足就别显示对应功能**——显示了点进去才 403，会误导人。
2. **能编辑"本组织"资源的人，只能改本组织管理员自己建的**智能体 / 工作流 / 知识库；**系统管理员、超级管理员建的不能随便改**。

对应两块改动：

- **A · 前端 least-privilege 可见性**：按 actor 有效权限隐藏各后台页的操作控件。
- **B · 归属层级写规则**：写操作（编辑/删除/启停）按"创建者角色 vs actor 层级"再收一道；低层级不能动高层级建的资源。

# Part A · 前端权限不足即隐藏

## A1. 数据源（已就绪，无需后端改）

`GET /api/admin/me` 已返回：

| 字段 | builtin | custom |
|---|---|---|
| `source` | admin_table / user_admin | custom_admin |
| `role` / `builtinRole` | 实际角色 | null |
| `permissions` | **effectivePermissions**（默认包 + override） | **custom role permissions** |
| `tenantCode` / `deptId` / `teamId` / `userType` | ✓ | ✓ |

→ 前端只需消费 `permissions` 这个 key 集合 + scope 上下文即可判定"能不能看到某按钮"。

## A2. 共享 hook（新增）

新增 `lib/hooks/use-admin-permissions.ts`（client hook + 轻 context，避免每页各拉一次 /me）：

```ts
type AdminPerms = {
  loaded: boolean;
  source: "admin_table" | "user_admin" | "custom_admin" | null;
  role: AdminRole | null;          // custom = null
  isSuper: boolean;                // role === 'super_admin'
  isCustom: boolean;
  tenantCode: string | null;
  deptId: string | null;
  teamId: string | null;
  perms: Set<string>;              // /me.permissions
  has(key: string): boolean;       // super 恒 true；否则 perms.has(key)
  canAny(keys: string[]): boolean;
  // 便捷：某资源某动作是否持有"任一 scope"
  canAction(resource: string, action: string): boolean; // 检查 <res>.<action>.{team,dept,org,all} 任一
};
```

- `isSuper` → `has()` 恒 true（与后端公式第 1 行一致）。
- builtin 非 super：按 `perms`（effective）判定 —— 与后端 enforce 默认开后的真实能力一致。
- custom：按 `perms`（角色权限）判定。
- **统一口径**：前端只信 `/me.permissions`，不再各页自己按 `role` 硬编码（现状各页 `isOrgAdmin` 散落判断，逐步收敛到 hook；本期至少新控件全走 hook，旧 role 判断保留不破坏，作为二次兜底）。

> admin-layout 已在做菜单级过滤（`requiredAnyPermissions`）；本 hook 与之同源（都读 /me.permissions），可顺带把 admin-layout 的拉取逻辑抽进 context，避免重复请求。

## A3. 每页控件 → 权限 key 映射（隐藏规则）

`canAction(resource, action)` = 持有 `<resource>.<action>.{team|dept|org|all}` 任一即显示。资源 key 前缀见 `KEYS_BY_RESOURCE`。

表内 `create/update/delete` 这类斜杠写法表示“对应控件分别检查对应 action”，不是把 `create/update/delete` 当成一个 action 字符串传给 hook。

| 页面 | 控件 | 显示条件（满足才显示） |
|---|---|---|
| 用户管理 | 新建用户 | `canAction("user","create")` |
| | 改状态/启停 | `canAction("user","enable")` |
| | 改角色 | `canAction("user","role.update")` |
| | 调组织 | `canAction("user","tenant.transfer")` |
| | 调部门/小组 | `canAction("user","department.assign")` / `team.assign` |
| | 重置密码 | `canAction("user","password.reset")` |
| | 删除 | `canAction("user","delete")` |
| | 批量调组织 | `has("user.tenant.transfer.all")`（跨组织本就 .all） |
| 用户组 | 增/改/删/成员增删 | `canAction("user_group", create/update/delete)`（成员增删=update） |
| 组织管理 | 建/改/启停/删组织 | 分别检查 `tenant.create.all` / `tenant.update.all` / `tenant.delete.all` |
| | 部门 增/改/删 | 分别检查 `canAction("dept", "create/update/delete 对应动作")` |
| | 小组 增/改/删 | 分别检查 `canAction("team", "create/update/delete 对应动作")` |
| 智能体管理 | 新建 | **不显示新建入口**；新建统一去“智能体搭建”，由 `agent_draft.create.*` 控制 |
| | 编辑 | `canAction("agent","basic.update")` + **Part B 归属校验** |
| | 启停 | `canAction("agent","enable")` + Part B |
| | 删除 | `canAction("agent","delete")` + Part B |
| | 重建索引 | `has("agent.reindex.all")` |
| | 设可见范围(resource-permissions) | 目标资源 `basic.update`（见 resource-permissions 口径） |
| 智能体搭建(草稿) | 新建/复制/编辑/删除/发布/试跑 | `canAction("agent_draft", create/duplicate/update/delete/publish/test)` |
| 知识库 | 新建 | `canAction("kb","create")` |
| | 编辑/删除 | `canAction("kb","update"/"delete")` + **Part B 归属校验** |
| | 文档 上传/重建/删除 | 视为 `kb.update`（与后端口径一致） |
| API 管理 | 新建/编辑/启停/删除/测试 | `canAction("provider", create/update/delete/test)` |
| 公告 | 新建/编辑/启停/删除 | `canAction("notice", create/update/delete)` |
| 标签管理 | 整页 + 增删改 | `canAction("category", read/create/update/delete)`（页级 guard 也用它替代 isTagAdmin 硬判，或二者并存） |
| 工作流 | 新建 | `canAction("workflow","create")`（已部分实现 canCreateWf） |
| | 编辑/步骤写 | `canAction("workflow","update")` + **Part B 归属校验**（已部分实现 canTouchWf） |
| | 启停/复制/删除 | `canAction("workflow", enable/duplicate/delete)` + Part B |
| 工作流配置/分层级 | 进入页面/读取树/compact 列表 | `canAction("workflow","read")` 或 `canAction("workflow","update")`；后端按目标 scope 再收口 |
| | 拉取/排序/移除 | `canAction("workflow","update")` + 目标 org/dept/team scope；`PERMISSION_V2_ENFORCE_RESOURCES=none` 时 builtin 回退旧 `isWorkflowConfigAdmin` |
| 控制台/用量/日志/审计 | 只读，无写控件 | 菜单已按 `audit.read.*` 过滤；页内无需额外隐藏 |

## A4. 页面级兜底（直接改 URL 进页）

菜单隐藏挡不住手输 URL。每个管理页在 `/me` 加载后，若**连该资源的 read 权都没有** → 渲染"无权访问"占位（或 `router.replace` 回 dashboard / 工作流），与 admin-layout 的 custom 兜底页一致。后端 list 接口本就会 403，前端兜底只为不闪空壳。

## A5. 已拍板（A 部分实施口径）

1. **智能体管理页去掉“新建”入口**：不引入 `agent.create`，也不在已发布智能体页用 `agent_draft.create` 代判。新建统一进入“智能体搭建”，由 `agent_draft.create.org/all` 控制；“智能体管理”页只管理已发布资源。
2. **旧页 `isOrgAdmin` 本期不做大收敛**：只加新的 least-privilege 隐藏和页面 guard，旧 role 判断并存作为冗余兜底。后续单独开清理任务再把散落 role 判断收敛进 hook。

# Part B · 资源归属层级写规则（用户新增要求）

## B1. 规则定义

对**写操作**（编辑 / 删除 / 启停 / 复制 / 步骤写）在"持有权限"之上再加一道**创建者层级闸**：

> actor 只能写"创建者角色层级 ≤ 自己"的资源。
> 即：org 层级的人（org_admin / 仅持 org 及以下 scope 的 custom admin）**只能改本组织管理员（org_admin）自己建的**资源；**system_admin / super_admin 建的资源对其只读**。

层级序：`super_admin(3) > system_admin(2) > org_admin(1)`。判定沿用 `lib/admin-permissions.ts` 的 `canActOnRole(actorRole, creatorRole)`（actor ≥ creator 才放行）。

custom admin 的"层级"映射（**已拍板**）：custom admin 不是 builtin 角色，按其**最高写权限 scope** 折算：

- 最高 scope ≤ `org`（team/dept/org）→ 视为 `org_admin` 级（1）。
- 持任一相关资源的 `.all` 写权限 → 视为 `system_admin` 级（2）。
- 永远不折算为 `super_admin`；`super_admin` 仍只属于 builtin 超级管理员硬全权。

这样"org 级 custom admin 只能动 org_admin 建的"自然成立，同时避免 custom `.all` 变相越过 super 边界。

## B2. 现状盘点（关键约束）

| 资源 | 有 `created_by_role`？ | 现有层级闸 |
|---|---|---|
| **workflow** | ✅ 有（v31 `created_by_role` + v50 kind/role_code） | ✅ 已有 `ensureAdminHierarchyAllows`（PATCH/DELETE 调 `canActOnRole`） |
| **agent（已发布）** | ❌ **无**（agents 表无 created_by_role；甚至无 created_by） | ❌ 无 |
| **knowledge_base** | ❌ 无（kb 仅 `created_by` uuid，无 role） | ❌ 无 |
| model_provider | ❌ 无（仅 created_by uuid） | ❌ 无（用户本期未点名，可暂不纳入） |

→ **agent / kb 要支持本规则，必须先补"创建者角色"信息**。

## B3. 需要的改动

### B3.1 DB（新 migration v54，幂等）

- `agents` 加 `created_by_role TEXT`（CHECK in super/system/org）+ 索引；存量 agents 没有可靠 `created_by` 快照，统一回填 `system_admin`。
  - ⚠ 这是保守安全侧：当成平台层级创建，org/custom-org 只能读不能改。
  - 首次从草稿发布到 agents 时写入发布 actor 的快照层级；重复发布不覆盖已有 `created_by_role`，仅在历史 NULL 时补写。
- `knowledge_bases` 同样加 `created_by_role` + 索引；存量回填优先用 `created_by` 反查 `admins/users.role`，反查不到或角色非法时回填 `system_admin`。
  - KB 5.30up 起才有 org 归属，存量平台公共数据默认 `system_admin` 更安全。
- 不动 workflows（已有）。

> 也可不加列、改为"写时反查 created_by 的当时角色"——但 created_by 是 uuid 且角色可变、custom admin 的 created_by 是 users.id，反查不可靠。**结论：加 created_by_role 列更稳**（与 workflow v31 同款）。

agent / KB 本期只新增 `created_by_role` 快照列，不额外引入 `created_by_kind` / `created_by_role_code`。custom 创建时直接写入 B1 折算后的 `created_by_role`（org 级 custom 写 `org_admin`，`.all` custom 写 `system_admin`）。

### B3.2 后端 enforce（写路径加层级闸）

- `agents/[id]` PATCH/DELETE、`knowledge-bases/[id]` PATCH/DELETE：在现有 `requireAccess` 之后，加 `ensureCreatorHierarchyAllows(actor, resource)`：
  - 取目标的 `created_by_role`；
  - builtin：`canActOnRole(actor.role, created_by_role)` 不过 → 403；
  - custom：按 B1 折算层级再比；
  - super_admin 直接放行。
- workflow 已有此闸（确认 custom admin 路径也走到——当前 workflow custom 分支只校 scope，**需补一道 created_by_role 层级校验**，与 builtin 对齐）。
- 写入侧：
  - agent 首发发布：写 `created_by_role = actor 快照层级`；重复发布不覆盖已有快照，避免后续发布者改变资源创建层级。
  - KB create：写 `created_by_role = actor 快照层级`。
  - workflow create：builtin 继续写 `created_by_role`；custom 现有 `created_by_kind/custom role_code` 继续保留，但 B 闸比较时必须用 B1 折算层级参与判断。

### B3.3 前端隐藏（Part A 的归属增强）

A3 表中标了 **Part B 归属校验** 的控件（agent/kb/workflow 的 编辑/删除/启停）：除 `canAction` 外，还要 `canActOnRole(myLevel, row.created_by_role)` 为真才显示编辑/删除；否则置灰或隐藏并提示"该资源由上级管理员创建，仅可查看"。
- 列表接口需回带每行 `created_by_role`（workflow 已回带 created_by_role；agent/kb 需在 list select 补该列）。

## B4. 边界 / 不纳入

- **创建（create）不受归属闸**：建新资源无"创建者"可比，仅受 Part A 的 create 权限控制。
- model_provider / notice / 组织架构（tenant/dept/team）本期**不纳入**归属层级（用户只点名 agent/workflow/kb）；provider 已有 org ownership（tenant_code）够用。
- `super_admin` 硬放行；`system_admin` 仍按层级比较，只能写 `system_admin/org_admin` 创建的资源，不能写 `super_admin` 创建的资源。
- provider / notice 本期仍做权限与组织归属控制，但不叠加"创建者层级"规则。

## 验收用例（A+B 合并）

1. custom 角色只有 `kb.read.org`：知识库页**看不到**新建/编辑/删除按钮（A）；工作流等菜单不出现（已实现）。
2. custom 角色有 `workflow.update.team`：只在**本小组 + 本组织管理员建**的工作流上显示编辑（A + B）；org/system/super 建的工作流不显示编辑按钮，强行调 PATCH 也 403（后端 B 闸）。
3. org_admin 编辑一个 system_admin 建的智能体：**编辑按钮不显示**（A+B），直调 API 返 403（B 后端）。
4. org_admin 编辑本组织管理员建的智能体：可编辑 ✓。
5. system_admin 编辑 super_admin 建的知识库：写按钮不显示，直调 API 返 403；编辑 system_admin/org_admin 建的知识库可通过。
6. 手输 URL 进无 read 权的页：渲染"无权访问"占位，不闪空壳（A4）。
7. super_admin：所有控件照常全显示（isSuper 短路）。

## 已拍板决策

1. **智能体"新建"入口**：智能体管理页移除"新建"按钮；新建统一走智能体搭建，由 `agent_draft.create.org/all` 控制。
2. **旧 `isOrgAdmin` 判断**：本期不做大规模收敛，只加新隐藏与页面 guard；旧逻辑并存兜底，后续单独清理。
3. **custom admin 层级折算**：最高写 scope ≤ org 折算为 `org_admin`；持 `.all` 写权限折算为 `system_admin`；永远不折算为 `super_admin`。
4. **agent / KB 历史回填**：默认回填 `system_admin`；KB 能可靠反查创建者角色时用真实角色，否则仍回填 `system_admin`。
5. **B 范围**：只做 agent / workflow / knowledge_base 三类；provider / notice 本期不叠加创建者层级规则。
