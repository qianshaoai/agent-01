## 目标

1. 把两个 page 里的「分类管理 Tab」整体抽到独立页面 `/admin/tags`
2. 独立页 = 2 子 Tab（智能体标签 / 工作流标签）
3. 智能体管理 / 工作流管理页面：去掉「分类管理 Tab」，**主列表 Tab 直接默认占满**
4. UI 文案统一改为「标签」（chip 显示、入口按钮、placeholder）
5. 在智能体/工作流的新增/编辑入口里，「设置标签」入口**保持**（这本来就有，UI 文案改成「标签」即可）

## 路线对比

| 路线 | 内容 | 改动量 | 风险 | 推荐 |
|---|---|---|---|---|
| **A** · 抽 UI + 改文案（不动数据） | 数据/API 沿用 `categories` / `wf_categories`，前端新建 `/admin/tags` 页面 2 Tab 把两块搬过来，UI 文案统一改"标签"。**所有内部 schema/API/字段名仍叫 categories** | **小**（仅前端搬迁 + 文案）| 低 | ✅ **推荐** |
| **B** · 彻底统一 tags 表（DB 改） | 新建 `tags(id, kind ∈ {agent,workflow}, name, ...)`，migrate 两表 → tags + 改两套关联表 → 改 API → 改前端 | 大 | 高（migration + 多处引用 + 关联表迁移）| ❌ |
| **C** · 不抽 UI，只改文案 | 留两个分类 Tab 不动，改文案叫"标签"。`/admin/tags` 不建 | 极小 | 低 | ❌（用户明确要独立页）|

### 推 A 的理由

1. **DB schema 是个长期资产，UI 是短期皮肤** —— v11 当年把 wf_categories 拆开，说明业务上**有**「两类需要独立管控」的诉求。强行统一在 tags 表加 kind 列，未必比现在好
2. **本期所有改动可在 1 个 commit 内回滚** —— 不涉及 migration，dev DB 不需要重跑
3. **API 完全不动** —— 现有 `/admin/categories` 和 `/admin/wf-categories` 继续 work，新页面只是换个调用方
4. **代码语义不混乱的代价** —— 前端可以加一层 alias（`TAG_LABELS = { agent: "智能体标签", workflow: "工作流标签" }`），让 UI 层"标签"概念清楚，但底层路由/字段仍叫 categories

唯一缺点：DB schema 里仍叫 `categories` —— 但只有读 SQL 的人会看到，对终端用户透明。如果以后真要统一，再做独立的 6.x.x 版本 schema migration 即可。

export function isTagAdmin(admin: { role: AdminRole }): boolean {

### R1.2 · 决策点 3 反转 · 不加智能体侧 DELETE

#### R0 推 a 的理由失效

R0 推（a）"对齐工作流侧 UX，加智能体分类删除"。但小B 指出：智能体侧 `categories/[id]/route.ts` **没有 DELETE** export。
加 DELETE = 必须做 4 表清理 + 拒绝逻辑：

| 引用表 | 处理 |
|---|---|

### R1.2-2 · isTagAdmin helper 签名 + guard 写法修正

#### 错误

R1.1-1 写：

```ts
export function isTagAdmin(admin: { role: AdminRole }): boolean {
  return admin.role === "super_admin" || admin.role === "system_admin";
}
```

但 R1.1 同段的页面级 guard 示例：

```ts
// app/admin/tags/page.tsx 顶部 effect
if (!isTagAdmin(adminRole)) router.replace("/admin/dashboard");
//                ↑ 传 string，但 helper 签名要 object → typecheck fail
```

且 `adminRole` 在 `/api/admin/me` 返回前是 `null`/`undefined`，**直接 `!isTagAdmin(null)` 会误判为"无权"立即跳转**，导致页面闪一下就跳走。

#### R1.2 修订

**Helper 签名改为 与现有 [admin-permissions.ts](lib/admin-permissions.ts) 三个 helper 同风格**（`canActOnRole` / `roleLabel` / `noWritePermissionMessage` 都收 `AdminRole | null | undefined`）：

```ts
// lib/admin-permissions.ts 追加
/**
 * 6.5up · 标签管理写操作权限（super_admin + system_admin）
 * role 为 null/undefined（/api/admin/me 未返回时）→ false（拒绝）
 * 调用方页面级 guard 需在 role 加载完成后再判断，避免初始 null 误跳转
 */
export function isTagAdmin(role: AdminRole | null | undefined): boolean {
  return role === "super_admin" || role === "system_admin";
}
```

**调用方写法**：

```ts
// 服务端（10 个 API endpoint）
const admin = await requireAdmin();
if (admin instanceof Response) return admin;
if (!isTagAdmin(admin.role)) return apiError("无权管理标签", "FORBIDDEN");

// 页面级（app/admin/tags/page.tsx）
useEffect(() => {
  if (loadingMe) return;          // ← 等 /api/admin/me 返回
  if (!adminRole) return;         // ← null/undefined 时不跳，避免初始误跳
  if (!isTagAdmin(adminRole)) {
    router.replace("/admin/dashboard");
    toast("无权访问标签管理");
  }
}, [loadingMe, adminRole]);

// 渲染门禁：只写 useEffect 跳转不够，useEffect 在首屏渲染后才执行，org_admin 可能看到一帧内容。
// loading / 无角色 / 非 tag admin 时，不渲染标签管理主体，也不发起标签数据请求。
if (loadingMe || !adminRole || !isTagAdmin(adminRole)) {
  return (
    <AdminLayout>
      <div className="space-y-6">
        <PageHeader icon={<Tag size={20} />} title="标签管理" subtitle="管理智能体与工作流的标签" />
        <Card padding="lg" className="py-16 text-center text-gray-400">加载中…</Card>
      </div>
    </AdminLayout>
  );
}
```

⚠️ **关键不变**：必须**等 `loadingMe === false`** 才判断角色，否则刚进页面 adminRole 还是 null，会误跳到 dashboard。页面主体渲染与 `loadTags()` / `loadTenants()` 等数据请求也必须在 `isTagAdmin(adminRole)` 为 true 后才执行，确保 org_admin 不会看到标签管理内容闪现。
