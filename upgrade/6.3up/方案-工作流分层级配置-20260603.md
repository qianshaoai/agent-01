## 背景

用户 2026-06-03 提出：

> 在工作流管理这个部分我面临着一个问题，就是，如果我想给每个组织按照不同部门展示不同工作流，我该怎么做，我打算新增一个工作流配置的功能，用户进入这个功能以后首先选择要配置的组织，随后是部门，最后是小组，管理员可以在这个里面拉取已有的工作流给该公司/部门/小组，之后，管理员可以在公司/部门/小组页面给展示的工作流进行排序，这个功能作为工作流管理的子功能，可以在工作流管理界面点击按钮进入修改。

需求拆解：
1. 新页面「工作流配置」选定组织 → 部门 → 小组层级
2. 给该层级"拉取"已有工作流
3. 给该层级"排序"工作流
4. 入口：工作流管理头部加按钮

## 现状

### 数据层（已有 · 不需要重建）

| 表 | 用途 | 关键字段 |
|---|---|---|
| [`workflows`](supabase/migration_v2.sql) | 工作流主表 | id / sort_order INT（**全局排序**）/ visible_to / enabled |
| [`departments`](supabase/migration_v7.sql) | 部门表 | id / tenant_code TEXT / name / sort_order |
| [`teams`](supabase/migration_v7.sql) | 小组表 | id / dept_id FK / name / sort_order |
| [`users`](supabase/migration_v7.sql) | 用户 | tenant_code / dept_id / team_id |
| [`resource_permissions`](supabase/migration_v8.sql) | **通用资源权限**（agent + workflow 共用）| resource_type / resource_id / scope_type ∈ {all, org, dept, team, user, user_type} / scope_id |

**关键事实**：
- ✅ `resource_permissions` 已经能控制"工作流 X 对组织 A / 部门 B / 小组 C 可见"
- ✅ 工作流的「自定义可见范围」(visible_to=custom) 入口就是写这张表
- ❌ **缺失**：按 scope 的工作流**排序**字段

### 缺失能力的关键点

| 问题 | 现状 | 期望 |
|---|---|---|
| 工作流 X 对组织 A 可见？ | resource_permissions 有 | ✓ |
| 工作流 X 在组织 A 的展示顺序 = ? | **无字段** | 新增 |
| 工作流 X 在部门 B 的展示顺序 = ? | **无字段** | 新增 |
| 用户 U（属于组织 A、部门 B、小组 C）看到的工作流顺序 = ? | 现按全局 `workflows.sort_order` 排 | 应按 team→dept→org→全局 回退 |

## 三路对比

| 路 | 内容 | 改动量 | 风险 | 推荐 |
|---|---|---|---|---|
| **A** · 新增专用排序表 + 复用 permissions 拉取 | 新建 `workflow_scope_order` 表只管排序，"拉取"沿用 `resource_permissions` | 中 | 低 | ✅ **推荐** |
| B · 重做：新表同时管可见 + 排序，替代 permissions for workflow | 既要改 permissions 现有逻辑、又要 migrate 现存数据 | 大 | 高（破坏 v8 设计 + agent 侧仍用 permissions，工作流单飞）| ❌ |
| C · 在 permissions 表加 sort_order 列 | 改表结构，所有调用方都受影响 | 小 | 中（permissions 是 agent+workflow 通用表，加排序列污染语义 + agent 不需要）| ❌ |

### 推 A 的理由

1. **职责单一** —— permissions 管"谁能看"、order 管"什么顺序"，互不干扰
2. **现有 visible_to 编辑器不动** —— 用户进工作流编辑器照常勾"可见组织"，写 permissions
3. **agent 侧不受影响** —— permissions 表语义不动
4. **可独立回滚** —— 删 order 表 + RPC 即可，不会让工作流"消失"

## 推荐路线 A · 实施面

### Phase -1 · DB（migration_v46 or 后续）

新表：

```sql
CREATE TABLE IF NOT EXISTS workflow_scope_order (
  scope_type  TEXT NOT NULL CHECK (scope_type IN ('org', 'dept', 'team')),
  scope_id    TEXT NOT NULL,  -- org: tenant_code TEXT；dept/team: UUID 转 TEXT 统一存
  workflow_id UUID NOT NULL REFERENCES workflows(id) ON DELETE CASCADE,
  sort_order  INT NOT NULL DEFAULT 0,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (scope_type, scope_id, workflow_id)
);
CREATE INDEX wf_scope_order_workflow_idx ON workflow_scope_order(workflow_id);
NOTIFY pgrst, 'reload schema';
```

**RPC**（核心 · 用户端展示用）：

```sql
CREATE OR REPLACE FUNCTION get_user_workflow_order(p_user_id UUID)
RETURNS TABLE(workflow_id UUID, sort_order INT, scope TEXT)
AS $$
  -- 思路：取用户的 tenant_code/dept_id/team_id；按 team → dept → org → 全局回退
  -- 用 DISTINCT ON (workflow_id) 实现"最具体层级胜出"
  WITH u AS (
    SELECT tenant_code, dept_id, team_id FROM users WHERE id = p_user_id
  ),
  ranked AS (
    -- team level
    SELECT o.workflow_id, o.sort_order, 'team'::TEXT AS scope, 1 AS priority
    FROM workflow_scope_order o, u
    WHERE o.scope_type = 'team' AND o.scope_id = u.team_id::TEXT
    UNION ALL
    -- dept level
    SELECT o.workflow_id, o.sort_order, 'dept'::TEXT AS scope, 2 AS priority
    FROM workflow_scope_order o, u
    WHERE o.scope_type = 'dept' AND o.scope_id = u.dept_id::TEXT
    UNION ALL
    -- org level
    SELECT o.workflow_id, o.sort_order, 'org'::TEXT AS scope, 3 AS priority
    FROM workflow_scope_order o, u
    WHERE o.scope_type = 'org' AND o.scope_id = u.tenant_code
  )
  SELECT DISTINCT ON (workflow_id) workflow_id, sort_order, scope
  FROM ranked
  ORDER BY workflow_id, priority ASC, sort_order ASC;
$$ LANGUAGE sql STABLE;
```

## 风险

| 风险 | 缓解 |
|---|---|
| **拉取 ≠ 可见性**：admin 在 workflow-config 添加了工作流，但用户实际看不到（被 permissions 拦了）| Phase 1 UI 加 hint: "该工作流可见组织：XX、YY（可见配置在工作流编辑器修改）" |
| 大量层级配置 PG 查询慢 | RPC 加 index + Phase 3 加 LIMIT |
| scope_id 类型混用（org 是 TEXT code，dept/team 是 UUID）| 表设计 scope_id TEXT 统一；API 层做类型校验 |
| 多 admin 同时拖拽冲突 | 乐观更新 + 后端 PUT 接收完整 orderedIds，覆盖最后一次写 |
| 部门 / 小组删除后 order 表残留 | 加 FK ON DELETE CASCADE（scope_id 是 TEXT 不能直接 FK，要 trigger）—— 或本期接受残留，未来清理 |
