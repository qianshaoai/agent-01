# 后台管理性能优化方案（2026-07-23）

> 修订状态：已完成三轮方案审核修订。  
> 实施结论：**全量 Go**。阶段 A、B 可立即开始；`agent_effective_admin_scopes` 的创建、授权和等价测试前移为阶段 C 的 Dashboard Summary 上线前置条件，阶段 D 直接复用。

## 1. 结论

当前后台卡顿不是单纯由“接口数量多”造成，而是以下问题叠加：

1. 后台控制台没有使用持久化的 Next.js 路由组 Layout，每次切换菜单都会重新挂载侧栏和公共状态。
2. `/api/settings`、`/api/admin/me` 被布局和各业务页面重复调用。
3. 控制台为了展示数量，调用了统计、智能体、公告、用户等完整列表接口。
4. 统计接口把大量日志明细拉到 Node.js 内存中重复聚合，数据量越大越慢。
5. 智能体中心先扫描大量数据，再逐条做权限查询，非超级管理员存在严重 N+1 风险。
6. 组织、部门、团队、分类等低频字典数据在多个页面重复加载，没有跨页面缓存。
7. 单个 API 在进入业务查询前还会重复查询登录新鲜度、管理员资料和权限包，前端请求数会被进一步放大为数据库请求数。

本次建议按三个阶段实施：

- **P0：路由组公共布局、管理员上下文、控制台摘要接口。** 先解决登录页隔离、权限契约和每次切页重复请求的问题。
- **P1：统计与智能体中心后端重构。** 解决最重的全表扫描、内存聚合和 N+1。
- **P2：公共字典缓存、鉴权查询合并、索引与可观测性。** 收口整体性能和长期可维护性。

目标不是机械地把所有接口合成一个，而是做到：

- 页面只请求当前首屏真正需要的数据；
- 公共数据只加载一次；
- 列表、筛选、聚合尽量在数据库完成；
- 数据库查询数量不随列表行数线性增长；
- 权限实时性和安全边界不因缓存优化而降低。

### 1.1 开工阻断项及修订结论

| 阻断项 | 修订后的明确结论 |
|---|---|
| `/admin` 登录页会被后台 Layout 包裹 | 使用 `app/admin/(console)/layout.tsx` 路由组；`app/admin/page.tsx` 保持在路由组外 |
| Dashboard Summary 权限模型不完整 | 7.23up 先明确拒绝 custom admin；builtin admin 仍按指标逐项鉴权，无权字段返回 `null` |
| 管理 RPC 可能被非 service role 调用 | 管理 RPC 默认 `SECURITY INVOKER`，撤销 `PUBLIC/anon/authenticated`，只授权 `service_role` |
| Persistent Layout 无法靠 Flag 恢复旧页面包装 | Layout 采用代码版本回滚，不设置运行时 Flag；只有业务 V2 接口保留独立 Feature Flag |
| Agent 草稿回退无法在 Node 与 SQL 分页之间闭环 | 使用数据库视图 `agent_effective_admin_scopes` 统一计算显式 scope 和草稿归属回退，RPC 直接关联视图 |

## 2. 当前问题基线

以下数量按生产环境正常挂载计算，不包含浏览器开发模式可能产生的额外 effect 检查，也不包含 Next.js 页面/RSC 请求。

| 页面 | 当前首屏 API 数量（约） | 主要问题 |
|---|---:|---|
| 控制台 `/admin/dashboard` | 6 | 布局 2 个公共请求 + 4 个完整业务接口 |
| 用量看板 `/admin/analytics` | 6 | 统计接口很重，另拉组织/部门/团队 |
| 用户管理 `/admin/users` | 7 | 重复 `/admin/me`，一次性加载三类组织字典 |
| 工作流管理 `/admin/workflows` | 9 | 身份重复请求 + 5 个参考数据接口 + 列表 |
| 标签管理 `/admin/tags` | 6 | 身份重复请求 + 两类标签 + 组织列表 |
| API 管理 `/admin/model-providers` | 4～5 | 身份重复请求，随后再加载组织列表 |
| 知识库管理 `/admin/knowledge-bases` | 4～5 | 公共身份重复请求，列表后自动加载首个详情 |
| 操作日志 `/admin/logs` | 4 | 日志翻页/筛选时会重复加载组织列表 |

### 2.1 公共布局重复加载

`components/layout/admin-layout.tsx` 当前在每个后台页面内单独使用，不是 App Router 的共享布局。

该组件的 effect 依赖 `pathname`，每次路径变化都会调用：

- `GET /api/settings`
- `GET /api/admin/me`

页面自身又会再次加载 `/api/admin/me`。因此普通菜单切换也会重复执行管理员资料和权限查询。

### 2.2 控制台首页过度取数

控制台当前并行调用：

- `GET /api/admin/analytics`
- `GET /api/admin/agents`
- `GET /api/admin/notices`
- `GET /api/admin/users?pageSize=1`

其中前三个接口返回的数据远超首页实际需要。

另外，智能体和公告接口默认分页大小均有限制，首页通过 `array.length` 取数量，在数据超过默认页大小后可能显示错误，不只是性能问题。

### 2.3 统计接口在应用层全量聚合

`app/api/admin/analytics/route.ts` 当前会对同一时间范围的聊天日志执行多条查询：

- 总调用数；
- 成功调用数；
- 成功日志明细，用于 Top 智能体；
- 全部日志明细，用于用户用量；
- 用户信息关联查询。

Top 智能体、用户调用次数、最近使用时间、最常用智能体、部门/团队筛选等都在 Node.js 内存中完成。

该实现还存在高优先级的数据正确性风险。日志明细查询没有应用层可靠分页，可能受到 Supabase/PostgREST 单次最大返回行数限制。日志超过限制后：

- `count` 得到的总调用数仍可能正确；
- Top 智能体可能只基于返回的部分成功日志；
- 用户维度统计可能只基于返回的部分全部日志；
- 页面会出现“总数正确、分项合计和排名错误”的不一致。

因此 Analytics 改造不能只作为性能优化，必须先按“数据正确性缺陷”处理。在新聚合上线前，应补一条大于 PostgREST 返回上限的数据用例，证明旧接口能复现截断、新接口聚合结果完整。

主要影响：

- 日志越多，Supabase 到 Node.js 的数据传输越大；
- 同一批日志被重复读取；
- 搜索、部门和团队筛选不能在数据库提前缩小数据集；
- 控制台首页不使用用户明细，却仍承担完整计算成本；
- 用量看板的用户搜索没有防抖，输入过程可能连续触发重查询。

### 2.4 智能体中心扫描与 N+1

`app/api/admin/agent-center/route.ts` 当前最多先读取 2000 个智能体，再在内存中筛选和分页。

对于非超级管理员：

1. 每个智能体调用一次 `canReadAgent()`；
2. 每次权限判断会加载智能体详情和 `resource_permissions`；
3. 当前页每条记录还要分别判断编辑、启停、删除三种权限。

这会让数据库查询数量随智能体数量增长。

此外，会话数当前通过读取相关 `conversations.agent_id` 明细后在 Node.js 中计数，缺少 `conversations(agent_id)` 专用索引，数据量增加后会进一步变慢。

权限重构还必须保持现有“无权限行时按发布草稿创建者反推归属”的兼容语义。当前 `agent` adapter 会在 `resource_permissions` 为空且存在 `published_from_draft_id` 时回退到草稿归属。等价测试以该 adapter 实际调用的单条 `resolveAgentDraftOwnerScopesById()` 为权威 oracle；批量版 `resolveAgentDraftOwnerScopesMap()` 当前在“同一 UUID 同时存在于 admins/users，且 admin tenant 为空、user tenant 非空”时与单条 resolver 存在差异，修正前不得作为 oracle。TypeScript resolver 不能作为 RPC 分页前的运行时步骤；数据库分页路径统一改用 `agent_effective_admin_scopes`。新 RPC 如果只看 `resource_permissions`，会造成智能体消失或权限变化。

### 2.5 鉴权查询被每个 API 重复执行

当前一次后台 API 通常包含：

1. token 验签；
2. 查询 `force_relogin_at` 验证 token 新鲜度；
3. 再查一次管理员/用户资料构建 `PermissionActor`；
4. 非超级管理员继续查询角色权限包和个人覆盖权限；
5. 最后才执行真正的业务查询。

因此“前端 6 个 API”在系统管理员场景下，鉴权部分本身就可能带来约 20 次数据库往返，然后再叠加业务查询。

### 2.6 组织结构请求瀑布

组织管理页展开组织后先加载部门，再在循环中逐个加载每个部门的小组，且当前是串行 `await`。

一个组织如果有 20 个部门，就可能额外产生 20 次小组接口请求，页面展开时间取决于所有请求的串行总耗时。

## 3. 优化目标与验收指标

### 3.1 用户体验目标

- 后台菜单切换时侧栏不闪烁、不重新进入骨架状态。
- 页面切换不再重复请求品牌设置和管理员身份。
- 控制台首屏不等待完整用户维度统计。
- 智能体、用户、工作流等列表翻页时，只刷新列表区域。
- 输入搜索条件时不出现连续请求堆积和旧请求覆盖新结果。

### 3.2 技术指标

| 指标 | 目标 |
|---|---|
| 后台内部路由切换公共 API | `/api/settings`、`/api/admin/me` 均为 0 次重复请求 |
| 控制台业务 API | 由 4 个降为 1 个摘要接口 |
| 普通列表页首屏业务 API | 原则上 1～2 个；非首屏字典按需加载 |
| 智能体中心数据库查询复杂度 | 与返回页大小基本无关，禁止逐行查询 |
| 统计接口 | 禁止向 Node.js 拉取全部日志明细再聚合 |
| 用户维度统计 | 服务端分页，单次最多返回当前页数据 |
| 搜索请求 | 300～500ms 防抖，并取消过期请求 |
| 组织树加载 | 1 个聚合接口，不按部门逐个请求 |
| 接口响应可观测性 | 能看到总耗时、鉴权耗时、业务查询耗时和请求 ID |

性能绝对值需在测试/生产相同数据量下采集基线后确定。建议将常用列表和控制台摘要的服务端 P95 目标设为 800ms 以内，普通交互接口 P95 目标设为 500ms 以内。

## 4. P0：公共布局与控制台摘要

### 4.1 建立持久化后台 Layout

新增：

- `app/admin/(console)/layout.tsx`
- `components/admin/admin-shell.tsx`
- `components/admin/admin-session-provider.tsx`
- `components/admin/admin-page-frame.tsx`

目标路由结构：

```text
app/
└─ admin/
   ├─ page.tsx                         # 登录、首次修改密码；不挂后台 Shell
   └─ (console)/                       # 路由组，不改变 URL
      ├─ layout.tsx                    # 持久化后台 Shell
      ├─ dashboard/page.tsx            # URL 仍为 /admin/dashboard
      ├─ users/page.tsx                # URL 仍为 /admin/users
      ├─ workflows/page.tsx
      ├─ analytics/page.tsx
      └─ ...
```

明确禁止在 `app/admin/layout.tsx` 挂载后台 Shell，因为该 Layout 会同时包裹 `/admin` 登录和首次修改密码页面。

职责划分：

#### `app/admin/(console)/layout.tsx`

- 作为所有后台控制台页面共享的 App Router Layout；
- 不包裹 `app/admin/page.tsx`；
- 只挂载一次 `AdminSessionProvider` 和 `AdminShell`；
- 路由切换时保留侧栏、管理员上下文和公共缓存。

#### `AdminSessionProvider`

- 首次进入后台调用一次 `GET /api/admin/me`；
- 对外提供 `source`、`role`、`permissions`、`tenantCode`、`deptId`、`teamId`、`username`；
- 提供 `refreshAdminSession()`，只在以下情况刷新：
  - 窗口重新获得焦点且距离上次刷新超过 30 秒；
  - 权限管理修改了当前管理员权限；
  - 管理员主动触发刷新；
- `useAdminPermissions()` 改为消费该 Context，不再自行 fetch。

Provider 状态不能只用 `loaded: boolean` 表达，至少区分：

```ts
type AdminSessionState =
  | { status: "loading"; data: null }
  | { status: "ready"; data: AdminMePayload }
  | { status: "forbidden"; data: AdminMePayload | null }
  | { status: "error"; data: AdminMePayload | null; message: string }
  | { status: "unauthenticated"; data: null };
```

失败处理：

- `/api/admin/me` 返回 401：清空上下文和本地敏感缓存，使用 `window.location.replace("/admin")` 回登录页；
- 返回 403：进入 `forbidden` 状态，显示无权访问兜底页，不把 403 当成未登录，不形成登录跳转循环；
- 临时 5xx/网络错误且已有成功上下文：保留最后一次成功数据，进入带 stale 标记的 `error` 状态并提示“管理员信息刷新失败”；
- 首次加载即遇到 5xx：显示可重试错误页，不渲染猜测角色，也不伪装成 401；
- 成功刷新后清除 stale/error 状态。

并发控制：

- focus、manual refresh 和权限变更刷新共享 single-flight Promise；
- 同参数并发只发一条 `/api/admin/me`；
- 如允许强制刷新启动新请求，必须使用 request sequence 或 `AbortController`；
- 只有最新请求可以写入 Context，旧响应不能覆盖新权限状态；
- 组件卸载后不得继续写状态。

#### `AdminShell`

- 只负责固定侧栏、移动端顶栏和主内容插槽；
- 从 `AdminSessionProvider` 获取权限并过滤菜单；
- 品牌配置只在首次挂载时加载一次；
- 路径变化只用于判断菜单高亮，不触发数据请求。

#### `AdminPageFrame`

- 普通页面负责 padding、最大宽度和 footer；
- 知识库等沉浸式页面使用 `fullBleed` 变体；
- 解决当前 `AdminLayout fullBleed/hideFooter` 无法直接移动到统一 Layout 的问题。

### 4.2 页面迁移

先将后台业务页面移动到 `(console)` 路由组。路由组目录名不会进入 URL，因此现有链接、书签和 middleware 路径无需改名：

```text
app/admin/dashboard/page.tsx
→ app/admin/(console)/dashboard/page.tsx

app/admin/users/page.tsx
→ app/admin/(console)/users/page.tsx
```

所有后台业务页面按同一方式迁移，但以下文件保持原位：

- `app/admin/page.tsx`；
- `app/api/admin/**`；
- 与 URL 无关的 `components/**`、`lib/**`。

移除所有后台页面中的：

```tsx
<AdminLayout>...</AdminLayout>
```

改为：

```tsx
<AdminPageFrame>...</AdminPageFrame>
```

沉浸式页面改为：

```tsx
<AdminPageFrame fullBleed hideFooter>...</AdminPageFrame>
```

同时删除页面内重复的 `/api/admin/me` 请求，统一改为：

```tsx
const admin = useAdminSession();
const permissions = useAdminPermissions();
```

重点迁移页面：

- `app/admin/(console)/users/page.tsx`
- `app/admin/(console)/workflows/page.tsx`
- `app/admin/(console)/notices/page.tsx`
- `app/admin/(console)/tenants/page.tsx`
- `app/admin/(console)/tags/page.tsx`
- `app/admin/(console)/model-providers/page.tsx`
- `app/admin/(console)/permissions/page.tsx`
- `components/admin/knowledge-base-workbench.tsx`
- `app/admin/(console)/agent-builder/page.tsx`
- `app/admin/(console)/agent-builder/[id]/page.tsx`

路由组迁移验收必须覆盖：

- 未登录访问 `/admin` 不请求 `/api/admin/me`，页面无后台侧栏；
- 首次修改密码流程仍在 `/admin` 内正常完成；
- 未登录访问 `/admin/dashboard` 仍被 middleware 重定向到 `/admin`；
- 登录后所有原 URL 均保持不变；
- custom admin 登录后仍按现有规则进入 `/admin/workflows`。

### 4.3 新建控制台摘要接口

新增：

- `app/api/admin/dashboard-summary/route.ts`

建议返回结构：

```ts
type DashboardSummary = {
  totalTenants: number | null;
  totalUsers: number | null;
  totalAgents: number | null;
  totalNotices: number | null;
  totalCalls: number | null;
  successCalls: number | null;
  successRate: number | null;
  topAgents: Array<{
    id: string;
    name: string;
    calls: number;
  }> | null;
  tenantUsage: Array<{
    code: string;
    name: string;
    used: number;
    quota: number;
  }> | null;
  generatedAt: string;
};
```

控制台只调用该接口，不再调用完整的 analytics、agents、notices、users 列表。

接口要求：

- 所有数量使用数据库 `count` 或 RPC 聚合；
- Top 智能体只按稳定的 `agent_code` 聚合，再关联 `agents` 获取当前名称；不得按 `agent_code, agent_name` 双字段分组，以免智能体改名后被拆成两组；
- 不返回用户维度明细；
- 7.23up 明确只允许 builtin admin；`custom_admin` 调用返回 403，前端继续按现有登录逻辑进入工作流页面；
- builtin admin 的每个指标仍按所属权限域逐项检查，不能因为能进入控制台就默认拥有全部数据权限；
- 无权指标返回 `null`，前端隐藏对应卡片或模块；不能返回 `0`，避免把“无权查看”误导为“真实数量为零”；
- `totalAgents` 拥有 `agent.read.all` 时可直接统计全部可见智能体；只有 `agent.read.org` 时必须通过 `agent_effective_admin_scopes` 按“全部 effective scope 均在 actor 组织内”的规则统计，禁止使用普通总数或任一 scope 命中；
- `agent_effective_admin_scopes` 未创建、未完成权限收紧或未通过等价测试前，组织范围的 `totalAgents` 必须返回 `null`，不得让 Dashboard Summary V2 全量上线；
- 组织配额只返回展示所需字段；
- 支持 30～60 秒短缓存，但缓存 key 至少包含 `source + actorId + role + effectivePermissions 指纹 + tenantCode + deptId + teamId`；
- 权限修改、组织修改不依赖该缓存做安全判断，缓存只服务展示。

逐指标权限契约：

| 指标 | 至少需要的读取权限 | 无权处理 |
|---|---|---|
| 组织数、组织配额 | `tenant.read.all`；org_admin 即使持有该键也按现有 route 语义只返回本组织 | 返回 `null`，隐藏组织卡片和配额模块 |
| 用户数 | `user.read.org/all` 中覆盖当前范围的权限 | 返回 `null`，隐藏用户卡片 |
| 智能体数 | `agent.read.org/all` 中覆盖当前范围的权限 | 返回 `null`，隐藏智能体卡片 |
| 公告数 | `notice.read.org/all` 中覆盖当前范围的权限 | 返回 `null`，隐藏公告卡片 |
| 调用数、成功率、Top 智能体 | `audit.read.org/all` 中覆盖当前范围的权限 | 相关字段全部返回 `null`，隐藏统计卡片 |

权限判定必须复用现有 `PermissionActor`/权限 helper，不在 dashboard route 中再写一套角色猜测逻辑。

控制台页面自身也要做 builtin guard：

- custom admin 直接访问 `/admin/dashboard` 时重定向 `/admin/workflows`；
- API 即使被绕过前端直接调用也必须返回 403；
- `null` 字段在 UI 上不渲染，不显示 `0`、`—` 或“暂无数据”冒充已授权结果。

### 4.4 P0 预期收益

- 后台内部切换不再重复加载品牌和身份；
- `/api/admin/me` 从“每页 1～2 次”降为“后台会话首次 1 次”；
- 控制台业务接口从 4 个降为 1 个；
- 控制台不再触发完整用户用量聚合；
- 侧栏不再每次切换都出现权限骨架屏。

## 5. P1：统计接口重构

本章节同时修复性能和数据正确性。当前明细查询可能被 PostgREST 行数上限截断，因此不得等到“性能优化有空再做”；持久化 Shell 完成后，应优先切换到数据库聚合，再让 Dashboard 复用同一套聚合能力。

### 5.1 拆分概览和用户明细

保留原路由兼容性，增加 `view` 参数：

```http
GET /api/admin/analytics?view=summary&days=30
GET /api/admin/analytics?view=users&days=30&page=1&pageSize=20
```

#### `view=summary`

只返回：

- 总调用数；
- 成功数和成功率；
- Top 智能体；
- 组织用量。

#### `view=users`

只在用户切换到“用户维度”Tab 时调用，返回：

- 当前页用户用量；
- 总条数；
- page/pageSize；
- 用户资料、部门、小组和最常用智能体。

### 5.2 数据库聚合

建议新增 Supabase RPC：

- `admin_usage_summary`
- `admin_user_usage_page`

输入由服务端根据 actor 计算后传入，不能直接信任浏览器传入的组织范围。

聚合规则：

- 时间、组织、部门、团队、搜索条件在 SQL 中过滤；
- `COUNT(*) FILTER (WHERE status = 'success')` 计算成功数；
- Top 智能体只按 `agent_code` 分组并限制 5 条，再关联 `agents` 获取当前名称；已删除智能体可回退使用最近一次日志名称；
- 用户用量首期使用 `tenant_code + user_phone` 作为复合聚合主键后再分页；
- 部门和团队通过 `users` 关联后过滤；
- 不向 Node.js 返回用于聚合的原始日志明细。

Analytics 用户聚合主键约束：

1. SQL 必须按两个独立列 `GROUP BY logs.tenant_code, logs.user_phone`，不要用字符串拼接生成 key；
2. 聚合完成后使用 `LEFT JOIN users` 补充当前用户资料，不能使用 `INNER JOIN`；
3. 关联条件使用 `phone` 加 tenant 的空值安全比较，避免同手机号跨组织合并；
4. 找不到用户、用户已删除或历史账号无法唯一对应时，仍保留日志聚合行，只把 `userId/realName/dept/team` 返回为 `null`；
5. 如果同一 `(tenant_code, phone)` 存在多个可关联用户，使用确定性规则选择当前有效用户，禁止 JOIN 放大调用次数；
6. `unknown/null phone` 作为明确的未知用户分组处理，不与真实手机号合并。

首期采用该键是因为现有日志没有稳定 `user_id`。它无法完美区分“同一组织内手机号删除后被重新注册”的历史身份，因此后续应给 `logs` 增加可空 `user_id`，新日志同时写入 `user_id`；历史数据不做不可靠的强行回填。

Dashboard 和 Analytics Summary 必须复用 `admin_usage_summary` 或同一数据库聚合函数，禁止分别维护两套统计 SQL。Dashboard 只裁剪返回字段，不能重新实现一遍 Top 智能体和成功率算法。

完整性验收：

- 准备超过 PostgREST 单次返回上限的日志数据；
- SQL/RPC 总数、Top 智能体、用户分项合计与直接 SQL 校验一致；
- 智能体改名前后的日志仍聚合为同一个 `agent_code`；
- 时间边界、组织边界和状态过滤使用同一时区口径；
- 用户分页翻完后的调用次数合计与对应筛选条件下总数一致。

### 5.3 管理 RPC 数据库安全约束

项目服务端使用 service role，会绕过 RLS。所有新增管理 RPC，包括但不限于：

- `admin_usage_summary`
- `admin_user_usage_page`
- `admin_agent_center_page`
- Dashboard 后续新增的其他管理聚合函数

都必须在迁移中显式收紧执行权限。

默认要求：

1. 优先使用 `SECURITY INVOKER`；
2. 撤销 `PUBLIC`、`anon`、`authenticated` 的执行权；
3. 只向 `service_role` 授予执行权；
4. 业务表使用 schema 限定名；
5. 可见组织、部门、团队范围只由 Node.js route 根据 `PermissionActor` 计算；
6. 浏览器参数只能表达用户选择的筛选条件，不能声明“我可以查看哪些组织”；
7. route 先求“权限允许范围 ∩ 用户筛选范围”，再调用 RPC。

迁移模板：

```sql
CREATE OR REPLACE FUNCTION public.admin_usage_summary(...)
RETURNS jsonb
LANGUAGE sql
SECURITY INVOKER
AS $function$
  -- 所有表使用 public.logs、public.agents 等完整名称
$function$;

REVOKE ALL ON FUNCTION public.admin_usage_summary(...) FROM PUBLIC;
REVOKE ALL ON FUNCTION public.admin_usage_summary(...) FROM anon;
REVOKE ALL ON FUNCTION public.admin_usage_summary(...) FROM authenticated;
GRANT EXECUTE ON FUNCTION public.admin_usage_summary(...) TO service_role;
```

如果某个函数确实必须使用 `SECURITY DEFINER`，则额外要求：

- `SET search_path = pg_catalog`；
- 所有业务表、视图、函数使用完整 schema 名；
- 函数 owner 使用专用、不可登录角色；
- 不拼接未校验的动态 SQL；
- 单独完成越权审计后才能合并。

迁移验收必须包含：

```sql
SELECT has_function_privilege(
  'anon',
  'public.admin_usage_summary(实际参数签名)',
  'EXECUTE'
); -- 必须为 false
```

并分别验证 `anon`、`authenticated` 调用失败，`service_role` 调用成功。权限检查必须使用完整函数签名，避免遗漏重载函数。

`app/admin/analytics/page.tsx` 改造：

## 6. P1：智能体中心重构

### 6.1 禁止逐条加载权限

当前 `canReadAgent()` 和 `canWrite()` 不能继续在列表循环中调用 `requireAccess(..., { id })`。

改造原则：

1. 请求开始时只构建一次 `PermissionActor`；
2. 一次性解析 actor 可读和可写的 scope；
3. 数据库视图统一解析显式 scope 和草稿归属回退；
4. Agent Center RPC 直接关联该视图完成权限过滤和分页；
5. 只查询当前页展示和动作判断所需的数据；
6. 当前页 `canEdit/canEnable/canDelete` 基于已经取得的 effective scope 批量计算，不再逐行访问数据库。

`resolveAgentDraftOwnerScopesMap()` 不进入新 RPC 的运行时请求链。等价测试以 `agent` adapter 实际调用的 `resolveAgentDraftOwnerScopesById()` 为权威 oracle；批量 resolver 必须先修正为与单条 resolver 一致的 `COALESCE(admin.tenant_code, user.tenant_code)` 语义，才能作为批量测试辅助。不得先把全部候选智能体拉到 Node.js 调用任一 TypeScript resolver，再交回数据库分页，否则会重新退化为大范围扫描。

### 6.2 数据库侧 Agent Effective Scope

阶段 C 的 Dashboard Summary 上线前新增普通视图，阶段 D 的 Agent Center 直接复用：

- `public.agent_effective_admin_scopes`

建议输出：

```text
agent_id
scope_type       # all / org / dept / team
scope_id
scope_source     # explicit / draft_owner_fallback
```

统一语义：

1. 智能体存在显式 `all/org/dept/team` 权限行时，输出这些 admin scope；
2. 只有在该智能体**完全不存在任何 `resource_permissions` 行**时，才允许按发布草稿创建者回退；
3. 如果只存在 `user`、`user_type` 或未知 scope 行，不输出 admin scope，同时也不能触发草稿回退；
4. 草稿创建者组织使用 `COALESCE(admin.tenant_code, user.tenant_code)`：admin 的非空组织优先；admin 行存在但组织为空时仍回退到 user 组织，与 `agent` adapter 实际调用的 `resolveAgentDraftOwnerScopesById()` 一致；
5. 创建者 `tenant_code` 非空时回退为 `org`，为空时回退为 `all`；
6. 找不到发布草稿时不产生回退 scope。

关键判断必须针对所有权限行：

```sql
NOT EXISTS (
  SELECT 1
  FROM public.resource_permissions rp_any
  WHERE rp_any.resource_type = 'agent'
    AND rp_any.resource_id = agents.id
)
```

不能把条件写成“过滤 `all/org/dept/team` 后为空”，否则只有 `user/user_type` 权限行的智能体会被错误回退成组织或全局可见。

视图实现骨架：

```sql
CREATE OR REPLACE VIEW public.agent_effective_admin_scopes
WITH (security_invoker = true)
AS
-- 1. 显式 admin scope
SELECT
  a.id AS agent_id,
  rp.scope_type,
  CASE WHEN rp.scope_type = 'all' THEN NULL ELSE rp.scope_id END AS scope_id,
  'explicit'::text AS scope_source
FROM public.agents a
JOIN public.resource_permissions rp
  ON rp.resource_type = 'agent'
 AND rp.resource_id = a.id
WHERE rp.scope_type IN ('all', 'org', 'dept', 'team')

UNION ALL

-- 2. 完全无任何权限行时，按发布草稿创建者回退
SELECT
  a.id AS agent_id,
  CASE WHEN owner_scope.tenant_code IS NULL THEN 'all' ELSE 'org' END AS scope_type,
  owner_scope.tenant_code AS scope_id,
  'draft_owner_fallback'::text AS scope_source
FROM public.agents a
JOIN public.agent_drafts d
  ON d.id = a.published_from_draft_id
LEFT JOIN public.admins ad
  ON ad.id = d.created_by
LEFT JOIN public.users u
  ON u.id = d.created_by
CROSS JOIN LATERAL (
  SELECT COALESCE(ad.tenant_code, u.tenant_code) AS tenant_code
) owner_scope
WHERE NOT EXISTS (
  SELECT 1
  FROM public.resource_permissions rp_any
  WHERE rp_any.resource_type = 'agent'
    AND rp_any.resource_id = a.id
);
```

正式迁移需根据实际列类型补显式 cast，并通过 lint/数据库测试确认。该视图只做实时 JOIN，不使用物化视图，避免权限变更后出现刷新延迟。

视图权限：

```sql
REVOKE ALL ON public.agent_effective_admin_scopes FROM PUBLIC;
REVOKE ALL ON public.agent_effective_admin_scopes FROM anon;
REVOKE ALL ON public.agent_effective_admin_scopes FROM authenticated;
GRANT SELECT ON public.agent_effective_admin_scopes TO service_role;
```

RPC 使用 `SECURITY INVOKER` 并由 `service_role` 查询该视图。不得把视图直接开放给浏览器角色。

性能前置验证：

- `resource_permissions(resource_type, resource_id)` 现有索引应支持 `NOT EXISTS`；
- `agent_drafts(id)`、`admins(id)`、`users(id)` 使用主键索引；
- `agents(published_from_draft_id)` 已有索引时先复用；
- 用生产等量数据检查 view + RPC 的 `EXPLAIN (ANALYZE, BUFFERS)`；
- 确认计划没有对每一页请求执行不可接受的全表嵌套扫描。

长期可选治理：后续可为历史智能体补齐显式 `resource_permissions`，并保证发布事务强制写入归属；只有完成数据审计、回填和兼容期后，才能另行取消草稿回退。本次 7.23up 不直接删除回退语义。

### 6.3 数据库先筛选和分页

建议新增 RPC：

- `admin_agent_center_page`

输入：

- page/pageSize；
- q/source/status/category/platform；
- actor 允许的组织/部门/团队范围；
- 是否拥有 all 范围读取权限。

输出：

- 当前页智能体；
- total；
- 当前筛选下的状态统计；
- 分类计数；
- 当前页知识库引用数、工作流引用数、会话数。

要求：

- 不再先扫描 2000 条再内存分页；
- 搜索和分类过滤在数据库执行；
- 直接关联 `agent_effective_admin_scopes`，完整保留显式权限和发布草稿归属回退语义；
- scope 过滤必须保持现有 `hasPermission()` 的 **AND 语义**：资源存在多个 effective scope 时，必须全部位于 actor 允许范围内；严禁用“存在任意一条 scope 命中”的 `EXISTS` 作为可见条件；
- actor 持有 `agent.read.all` 时才允许绕过 scope 范围过滤；只有 `agent.read.org` 时，`all` scope、其他组织的 `org` scope，以及反查后属于其他组织的 `dept/team` scope 均视为越界；
- Dashboard 的 `totalAgents`、Agent Center 的 total、分类/状态统计和分页数据必须复用同一个“无任何越界 scope”过滤 CTE，禁止只保护列表而泄漏统计数量；
- 会话数使用 `GROUP BY agent_id`；
- 工作流引用数使用 `COUNT(DISTINCT workflow_id)`；
- 知识库引用数使用 `COUNT(DISTINCT kb_id)`；
- 引用名称只查询当前页、且只在页面确实展示时返回。

组织范围过滤应表达为“找不到任何越界 scope”，而不是“找到一条范围内 scope”。以下为约束骨架，正式 SQL 需按实际部门/团队表结构补齐关联：

```sql
WHERE
  p_has_agent_read_all
  OR (
    p_has_agent_read_org
    AND NOT EXISTS (
      SELECT 1
      FROM public.agent_effective_admin_scopes eas
      LEFT JOIN public.departments d
        ON eas.scope_type = 'dept'
       AND d.id = eas.scope_id
      LEFT JOIN public.teams t
        ON eas.scope_type = 'team'
       AND t.id = eas.scope_id
      WHERE eas.agent_id = a.id
        AND (
          eas.scope_type = 'all'
          OR (
            eas.scope_type = 'org'
            AND eas.scope_id IS DISTINCT FROM p_actor_tenant_code
          )
          OR (
            eas.scope_type = 'dept'
            AND d.tenant_code IS DISTINCT FROM p_actor_tenant_code
          )
          OR (
            eas.scope_type = 'team'
            AND t.tenant_code IS DISTINCT FROM p_actor_tenant_code
          )
          OR eas.scope_type NOT IN ('org', 'dept', 'team')
        )
    )
  )
```

`IS DISTINCT FROM` 用于把空值和反查失败安全地判为越界。有效 scope 为空时，上述反向条件自然通过，与当前 adapter 对空 `targetScopes` 的行为一致；若后续要收紧无归属智能体的可见性，必须单独立项，不能在本次性能重构中静默改变权限语义。浏览器不能传入 `p_has_agent_read_all` 或 actor 组织范围，这些参数只能由服务端根据已鉴权的 `PermissionActor` 计算。

切流前必须建立权限等价测试。对同一批智能体同时运行旧判定和新判定，并逐项比较：

- 是否可见；
- `canEdit`；
- `canEnable`；
- `canDelete`；
- 无权限行且有发布草稿；
- 无权限行且无发布草稿；
- 只有 `user` 或 `user_type` 权限行时不得触发回退；
- 同时存在用户 scope 和 admin scope 时只输出 admin scope、且不得回退；
- 草稿创建者在 admins/users 同时存在且 admin tenant 非空时保持 admin tenant 优先；
- 草稿创建者在 admins/users 同时存在、admin tenant 为空且 user tenant 非空时使用 user tenant，不得扩大为 `all`；
- 同时存在多个 all/org/dept/team 范围时，逐项验证“全部 scope 命中”而非任一行命中；
- 组织 A 管理员面对 A+B、A+all、A+外组织 dept/team 等组合时均不可见，`.all` actor 可见；
- super/system/org/custom admin 各角色。

任何差异都必须先归类为“旧逻辑缺陷修复”或“新实现缺陷”，不能在性能改造中静默改变权限语义。

### 6.4 补充索引

索引属于“执行计划验证后的候选项”，不是方案一批准就直接执行的固定清单。

现有 Schema 已包含：

- `logs(created_at DESC)`；
- `logs(tenant_code, created_at DESC)`；
- `logs(agent_code)`；
- `logs(user_phone)`；
- `logs(action)`。

因此日志部分索引必须先对真实 RPC SQL 执行：

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
SELECT ...;
```

只有确认现有索引不能满足谓词、排序或分组，并评估写放大后，才增加部分复合索引。

优先验证的缺失索引候选：

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS conversations_agent_id_idx
  ON conversations(agent_id);

CREATE INDEX CONCURRENTLY IF NOT EXISTS workflow_steps_agent_id_idx
  ON workflow_steps(agent_id);

CREATE INDEX CONCURRENTLY IF NOT EXISTS agent_knowledge_bases_agent_id_idx
  ON agent_knowledge_bases(agent_id);
```

日志候选索引如 `WHERE action = 'chat'` 的部分索引，必须根据最终 SQL 执行计划单独决定，不再列为默认必建项。

生产上线约束：

- 大表只使用 `CREATE INDEX CONCURRENTLY`；
- `CREATE INDEX CONCURRENTLY` 不能运行在事务中，必须使用独立的非事务上线脚本；
- RPC/表结构迁移与并发索引脚本分开；
- 执行前记录表大小、写入 QPS、数据库 CPU 和连接数；
- 执行期间监控 `pg_stat_progress_create_index`、锁等待、写入延迟和复制延迟；
- 失败索引检查 `indisvalid`，按独立运维步骤清理，不在应用脚本里自动删除；
- 上线后再次执行相同 `EXPLAIN (ANALYZE, BUFFERS)`，证明扫描行数和总耗时确有收益。

- 组织、部门、团队、标签新增/修改/删除成功后主动失效对应缓存；
- 不将权限结果和业务列表混入该缓存。

### 7.2 按需加载

以下数据不应在页面首屏无条件加载：

- 新建/编辑弹窗才使用的组织归属选项；
- 权限弹窗才使用的组织、部门、团队、用户组；
- 智能体绑定弹窗才使用的 picker 数据；
- 可见范围编辑器才使用的完整组织树。

页面首屏只保留列表和直接展示所需的分类数据。

### 7.3 组织树聚合接口

新增通用接口：

- `GET /api/admin/org-tree?purpose=picker`

可复用现有 `/api/admin/scope-tree` 的三表并行查询和树形组装方式，但不能直接复用其“仅工作流配置管理员可访问”的权限规则。

通用接口要求：

- 根据 actor 权限裁剪可见组织范围；
- 一次返回组织、部门和团队树；
- 仅返回 `id/code/name/parent/sortOrder` 等 picker 必需字段；
- 替代组织管理页逐部门请求小组的串行瀑布；
- 大规模组织场景再增加按组织懒加载，而不是回退到逐部门接口。

### 7.4 修复重复字典刷新

操作日志页面将“日志列表请求”和“组织选项请求”拆成两个 effect：

- 翻页、状态筛选只刷新日志；
- 组织选项只在首次进入或缓存失效时刷新。

用户、工作流、公告、标签等页面同样遵守该规则。

## 8. P2：鉴权查询合并

### 8.1 统一解析管理员上下文

当前 `validateAdminTokenFreshness()` 和 `buildPermissionActor()` 会重复查询管理员/用户表。

新增统一入口，例如：

```ts
resolveAdminRequestContext(accessToken): Promise<AdminActorContext>
```

一次解析中完成：

- token 验签；
- 管理员或 custom admin 当前状态；
- `force_relogin_at` 校验；
- role、tenant/dept/team；
- effective permissions。

可以通过一个数据库 RPC 或一次主资料查询加一次权限查询完成，禁止先查 freshness、随后再查同一管理员资料。

### 8.2 缓存边界

不建议直接长期缓存完整 `PermissionActor`，否则会破坏权限修改和强制下线的即时性。

可选方案：

1. **短缓存方案：** 10～30 秒进程内缓存，key 包含 actor/source；权限修改后主动失效。
2. **权限版本方案：** token 携带 `permissionVersion`，管理员/角色变更时递增版本；版本一致时复用权限快照。
3. **数据库 RPC 方案：** 不做跨请求缓存，但将多次查询合并为一次 RPC。

首期推荐第 3 种，风险最低；确认性能仍不足后再引入短缓存或权限版本。

### 8.3 Middleware 边界

后台页面 Middleware 当前每次路由请求都会查询 token freshness，业务 API 内又会再次校验。

调整时必须满足：

- 页面壳可只做 token 验签和基本登录判断；
- 所有业务 API 继续做完整实时鉴权；
- 页面即使短暂显示旧菜单，也不能拿到越权业务数据；
- 如必须保持页面层即时踢出，可给 Middleware freshness 增加极短 TTL，而不是完全取消。

安全性优先，不能为了减少一次查询而删除业务 API 的权限校验。

## 9. 请求竞态、轮询和错误重试

### 9.1 搜索与筛选

所有搜索型列表统一：

- 300～500ms 防抖；
- 使用 `AbortController` 取消旧请求；
- 响应中记录 request sequence，旧响应不能覆盖新状态；
- 页码和筛选条件进入 URL，避免刷新丢失；
- 空搜索不重复触发同参数请求。

### 9.2 知识库轮询

知识库在文档 `pending/indexing` 时每 3 秒轮询详情属于合理业务行为，但应增加：

- 页面不可见时暂停；
- 连续失败指数退避；
- 文档全部完成后立即停止；
- 最长轮询时间和手动刷新入口；
- 后续可升级为 SSE，但本次不强制引入。

### 9.3 重试

API 管理页面当前失败会最多重试 3 次。统一约束：

- 仅网络错误、502/503/504 自动重试；
- 400/401/403/404 不重试；
- 使用指数退避并加随机抖动；
- 用户主动刷新时取消旧的重试链。

## 10. 可观测性方案

在优化前后采集同一数据量、同一账号角色的对比数据。

### 10.1 服务端指标

当前 middleware 只在 `NextResponse.next()` 的响应头上设置 `X-Request-Id`，业务 Route 无法从请求中读取该 ID，因此现状不能算 requestId 已贯通。

新增统一 API wrapper，例如：

- `lib/api-handler.ts`
- `withApiObservability(handler)`

wrapper 职责：

1. 从请求头读取 `x-request-id`，不存在则生成；
2. 建立统一计时上下文；
3. 包装 auth、business、serialize 阶段；
4. 在同一条结构化日志中输出 requestId 和阶段耗时；
5. 给最终响应设置 `X-Request-Id` 和 `Server-Timing`；
6. 捕获未处理异常并保留 requestId；
7. 不记录 token、Cookie、API Key 和完整个人敏感字段。

middleware 如继续生成 ID，必须把它同时转发到下游请求头：

```ts
const requestHeaders = new Headers(req.headers);
requestHeaders.set("x-request-id", requestId);

const res = NextResponse.next({
  request: { headers: requestHeaders },
});
res.headers.set("X-Request-Id", requestId);
return res;
```

Route wrapper 仍需在请求头缺失时生成兜底 ID，保证测试、内部调用或绕过 middleware 的请求也可追踪。

API 响应增加：

```http
X-Request-Id: mabc123-0042
Server-Timing: auth;dur=18, db;dur=92, serialize;dur=4, total;dur=119
```

日志至少记录：

- requestId；
- method/path；
- actor source/role，不记录敏感信息；
- authMs；
- businessMs；
- responseBytes；
- statusCode；
- totalMs。

### 10.2 数据库指标

- 开启并检查 `pg_stat_statements`；
- 对 analytics、agent-center、users、workflows 执行 `EXPLAIN ANALYZE`；
- 记录查询行数与返回行数；
- 检查慢查询是否命中新增索引；
- 对 RPC 设置合理的 statement timeout。

### 10.3 前端指标

- 页面首屏请求数；
- 请求传输总字节；
- 首次内容展示时间；
- 列表 loading 持续时间；
- 搜索期间被取消的旧请求数；
- 路由切换时侧栏是否重新挂载。

## 13. 灰度与回滚

### 13.1 Feature Flag

建议增加：

```env
ADMIN_DASHBOARD_SUMMARY_V2=true
ADMIN_ANALYTICS_SQL_AGG=true
ADMIN_AGENT_CENTER_V2=true
```

新旧接口短期并存，先让测试环境和少量管理员使用新实现。

Persistent Layout 不设置运行时 Feature Flag。页面迁入 `(console)` 并删除旧 `AdminLayout` 包装后，单个环境变量无法恢复旧目录结构和页面包装；该部分明确采用 Git/构建版本回滚。

若实施团队坚持让 Layout 可运行时切换，则迁移期必须真实保留完整的旧壳和新壳两套页面组合，并证明 Flag 两侧都可构建、登录和导航。考虑维护成本和重复代码，7.23up 不采用双壳方案。

### 13.2 数据库迁移

- 新增 RPC 使用独立事务迁移，并在同一迁移中完成 `REVOKE/GRANT`；
- `agent_effective_admin_scopes` 与对应 `REVOKE/GRANT` 使用受审计的结构迁移，RPC 不得在 view 权限收紧前上线；
- RPC 迁移后自动运行 `anon/authenticated/service_role` 执行权限测试；
- 大表索引使用独立、非事务的 `CREATE INDEX CONCURRENTLY` 运维脚本，不与 RPC 迁移混跑；
- 已有索引和候选索引先做重复性、执行计划与写放大评估；
- 新 RPC 上线不删除旧查询路径；
- 确认新接口稳定后，再清理旧实现。

### 13.3 回滚策略

- Persistent Layout 异常：回滚到上一应用构建版本；不承诺环境变量恢复旧壳；
- Dashboard、Analytics、Agent Center 异常：分别关闭对应 Feature Flag，切回仍保留的旧接口；
- RPC 异常：路由切回旧实现，保留新增 RPC 不影响旧功能；
- 索引异常：先确认是否影响写入，再按独立迁移处理，不在应用发布脚本中临时删除；
- 权限异常：立即关闭相关 V2 页面/接口，不能用“放宽权限”作为性能故障兜底。
