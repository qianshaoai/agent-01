# 权限管理 v2 重构方案

**日期** 2026-06-04 · **基线** 6.4up 已上线 R1.2 · **作者** 小A
**位置（建议）** `upgrade/6.4up2/`

---

## Context · 为什么重做

用户原本要的两件事：
1. **超管可以设定除超级管理员以外其他管理员（system_admin / org_admin）的所有后台权限**——不局限工作流。
2. **同时支持自定义角色**（如"小组长只能建本组工作流"）。

6.4up 实际产出（"扭曲了原本的意思"）：
- ✅ 加了 `custom_roles` / `custom_role_permissions` / `user_custom_roles` 三表 + `requirePermission()` 通道
- ❌ permission_keys 只 12 项，**全部 workflow**——agents / kb / model_providers / tenant / user 等资源完全没接入
- ❌ **builtin admin（system_admin / org_admin）权限完全不可改**——还是硬编码 role list
- ❌ 自定义角色只能挂到 `role=user` 的普通用户

诉求 ① 完全缺失；诉求 ② 只做了"workflow 试点"的简化版。本方案补齐两条诉求。

## 推荐路线 · D · 三层混合

最终权限公式：

```
hasPermission(actor, key, targetScopes):
  if actor.builtinRole == 'super_admin': return true            # 硬规则，super 永远全权
  if hasStructuralDeny(actor, key, targetScopes): return false  # tenant_code 等不可改的归属约束
  finalKeys = roleDefaultPack(actor.builtinRole)                # 来自 builtin_role_permissions
            ∪ customRolePack(actor.customRoles)                 # 来自 v50 三表（6.4up）
            ∪ adminGrantOverride(actor.actorId)                 # 来自 admin_permission_overrides
            − adminRevokeOverride(actor.actorId)
  return finalKeys.has(key) && scopeOk(actor, key, targetScopes)
```

三层职责：

| 层 | 内容 | 谁能改 |
|---|---|---|
| **结构性约束**（hardcode） | org_admin 只能动自己 `tenant_code` 的资源；user_admin 不能超出提升来源 role；org_admin 缺 tenantCode fail-closed | 无人能改（代码层） |
| **角色默认包**（DB） | 每个 builtin role 的"标准权限集"，新管理员默认拿到 | 仅 super 改 `builtin_role_permissions` 表 |
| **个人 override**（DB） | 某个具体 admin 在标准包基础上 grant / revoke | 仅 super 改 `admin_permission_overrides` 表 |

**为什么选 D（其它方案为什么不要）**：
- A（全废 hardcode）→ 60+ 路由全改、scoped-access 拆散、回滚噩梦 → 否决
- B（只动角色默认包）→ 没法做"个体粒度调整"，用户原话"设定其他所有管理员"需要个体粒度 → 不足
- C（B + override，但 tenant_code 也变可 override）→ 5.30up 模型崩 → 否决
- **D** 三层分工清晰，5.30up 与 6.4up 都不动、可叠加、可回滚

## DB · migration_v52_permission_v2.sql（新建）

```sql
-- 1. 角色默认权限包
CREATE TABLE IF NOT EXISTS builtin_role_permissions (
  role           TEXT NOT NULL CHECK (role IN ('system_admin','org_admin')),
                                              -- super_admin 不入表（硬全权）
  permission_key TEXT NOT NULL,
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_by     UUID,
  PRIMARY KEY (role, permission_key)
);
CREATE INDEX idx_brp_role ON builtin_role_permissions(role);

-- 2. 个人 override
CREATE TABLE IF NOT EXISTS admin_permission_overrides (
  admin_id       UUID NOT NULL,
  admin_source   TEXT NOT NULL CHECK (admin_source IN ('admin_table','user_admin')),
  permission_key TEXT NOT NULL,
  effect         TEXT NOT NULL CHECK (effect IN ('grant','revoke')),
  reason         TEXT,
  created_by     UUID NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (admin_id, permission_key)
);
CREATE INDEX idx_apo_admin ON admin_permission_overrides(admin_id);

-- 3. seed 默认包：等价于 6.4up 现状（system_admin 全开除 setting/permission；org_admin 本组织 read+create+update）
-- 完整 seed 列表见方案附录（约 40 行 INSERT）

-- v52 跑完后行为 = 6.4up 现状（seed 等价）；ENFORCE flag 关闭时也完全等价
```

**幂等**：全 `IF NOT EXISTS` / `ON CONFLICT DO NOTHING`。
**回滚**：`DROP TABLE` 两张表 + 代码 revert。**v50 三表不动**。
**MIGRATIONS.md**：跑迁移后同步追一行（5.30up Fix 3 已立此规约）。

## 应用层改动 · P0 / P1 / P2

### P0 · 基建（必须最先）

| 文件 | 改动 |
|---|---|
| `lib/permission-keys.ts` | 扩到 ~80~100 keys，按 resource 分子文件 union；新增 `KEYS_BY_RESOURCE` + `KEYS_FOR_ROLE_DEFAULT_SEED` 常量；6.4up 12 个 workflow keys 保留 |
| `lib/permission-actor.ts` | `buildPermissionActor()` 同时查 `builtin_role_permissions`（按 role）+ `admin_permission_overrides`（按 admin_id），合成 `effectivePermissions: Set<PermissionKey>`；`hasPermission()` 改用新公式 |
| 新建 `lib/access-facade.ts` | 暴露 `checkAccess(actor, kind, action, row?)` / `requireAccess(...)`；**内部按顺序调** `canWriteRow / canReadRow`（结构性）→ `hasPermission()`（显式）→ `scopeContainment` |
| 新建 `app/api/admin/admin-overrides/route.ts` + `[adminId]/route.ts` | super-only 的个人 override CRUD |
| 改 `app/api/admin/permission-keys/route.ts` | 返回扩展后全集，按 resource group 分组 |
| `lib/scoped-access.ts` | **完全不动**（被 facade 在内部调）|

**命名 / scope 规则**：`<resource>.<action>.<scope>`，scope 按资源分级：
- workflow / agent：team/dept/org/all（4 档）
- kb / provider / notice / user：org/all（2 档）
- tenant / category / setting / permission：all（1 档）
- 资源清单按 `app/api/admin/**` 实际目录全量铺开（约 12 资源）
- 动作集：read / create / update / delete / enable / test

### P1 · UI 重做

`app/admin/permissions/page.tsx` 改成 4 Tab：

1. **管理员个人权限**：列所有 builtin admin（admins 表 + users.role∈3 档），点进去看 effective permissions = 默认包 + override，勾选 grant/revoke 立刻写 `admin_permission_overrides`
2. **角色权限模板**：编辑 `builtin_role_permissions`（system_admin / org_admin 两栏）；二次确认对话框显示"此次改动将影响 N 个同角色管理员"
3. **自定义角色**：6.4up 现有页面整体搬过来，行为不变
4. **权限审计**：从 `audit_logs WHERE resource_type IN ('builtin_role_permission','admin_override','custom_role')` 拉

`components/layout/admin-layout.tsx`：
- `allowedRoles` 闸门保留为最外层 fail-fast（避免 super-only 菜单白屏闪）
- 真实权门改 `requiredPermission` 字段对应 `effectivePermissions.has(key)`
- `settings` / `permissions` 菜单仍硬锁 `SUPER_ONLY`（不允许通过 override 给非超管放权）

### P2 · 路由分阶段接入（关键）

**不一锅端**：

1. 60~80 个 admin 路由维持 `requireAdmin()` + scoped-access 五件套不动
2. 在 `requireAdmin()` 之后**新增一行**：`const gate = await requireAccess(admin, 'agent', 'update', row); if (gate) return gate;`
3. 默认 `PERMISSION_V2_ENFORCE=false`（hasPermission fallback 到旧 role 判定）
4. 按 resource 逐组开 enforce：`notice → category → user → agent → workflow → kb → provider → tenant`（低→高风险）
5. **6.4up custom_admin 通道单独保留**：custom admin 完全不受 v2 影响

### Feature flags

- `PERMISSION_V2_ENFORCE_RESOURCES`：CSV 列表，按 resource 维度开 enforce（如 `"notice,category"`）
- `PERMISSION_V2_UI`：是否展示新 Tab 1/2/4
- 两个 flag 可独立开关：先开 UI 让超管演练编辑（不 enforce）2~3 天，验证 effective permissions 计算正确后再 enforce

## 验收口径（13 条渗透/UI 用例）

**全权与默认**
1. super_admin 在 v52 启用后任何操作仍放行（公式第 1 步）
2. system_admin 不做 override 时所有 6.4up 之前能操作的接口仍能操作（seed = 等价）
3. org_admin 不做 override 时本组织内 agent/workflow/kb/provider CRUD 行为与 5.30up 完全一致

**编辑生效**
4. super 在 Tab 1 给某 org_admin grant `kb.delete.org` → 该 admin 下次请求**立即**能删本组织 KB（无需重登）
5. super 在 Tab 2 把 `org_admin` 默认包里 `workflow.create.org` 删掉 → 所有 org_admin 立即不能创建工作流；但持有个人 grant 的 admin 仍可（override 优先于默认包）

**结构性约束不被绕过**
6. super 不能 override 给某 org_admin 操作**别的组织**资源的能力（tenant_code 归属在 hardcode 层）
7. super 不能给 system/org_admin grant `permission.*` 或 `setting.*`（API + UI 双层禁止）

**custom role 不破坏**
8. custom admin（v50 路径）所有 12 个 workflow keys 行为与 6.4up 一致；`requirePermission()` 不读 v52 两表
9. `.all` 后缀仍只能由 super 授予（6.4up R1.2 决策 10 不变）

**前端不是边界**
10. 浏览器 devtools 删菜单 `display:none` 强进禁用页 → 后端 `requireAccess()` 仍 403
11. 直接 curl `PATCH /api/admin/kb/123`（admin 没默认包也无 override）→ 403

**审计可追溯**
12. Tab 1/2 每次改动写 audit_logs，detail 含 before/after

**回滚验证**
13. 关 `PERMISSION_V2_ENFORCE` flag → 所有路由回到 6.4up 行为（无需 DROP 表）

## 主要风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 80+ keys seed 写漏 → 某 system_admin 接口突然 403 | seed 用 `KEYS_FOR_ROLE_DEFAULT_SEED` 常量生成；新增 `scripts/audit-permission-coverage.ts` 扫所有 `requireAccess()` 调用与 seed 取差集报警；ENFORCE 默认关 |
| R2 | super 把自己 `permission.update.all` revoke → 自锁死 | UI + API + DB trigger 三层拒：override 写入校验 `target is super OR key starts permission.*` → reject |
| R3 | scoped-access 五件套被 v2 公式绕过，org_admin 改别组织 KB | access-facade 强制顺序"先 `canWriteRow` 后 hasPermission"；ESLint custom rule 禁止 admin route 直接 import `hasPermission`，必须走 facade |
| R4 | `?? "super_admin"` 历史兜底再次触发 | Phase F 全仓二扫；unit test：fake actor builtinRole=null → hasPermission 必拒 |
| R5 | Tab 1 加载慢（100+ admin × 80 key = 8000 cell） | 列表只显示"override 条数"+"effective key 数"，详情 lazy load；effective 后端聚合接口，不在前端 N+1 |
| R6 | 半开半关 flag 调试困难 | flag 改 resource 维度 CSV；`/api/admin/me` 返回 `enforceMap` 供前端调试 |
| R7 | Tab 2 改默认包影响所有同角色 admin，超管误操作放大 | 二次确认对话框显示影响人数 + audit 记录 + "一键回滚到上次版本"按钮（读 audit_logs） |
