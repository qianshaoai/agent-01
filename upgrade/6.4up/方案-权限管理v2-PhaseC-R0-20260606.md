## 4 个低风险 resource

| Resource | 风险等级 | 路由 | enforce 后影响 |
|---|---|---|---|
| `notice` | 低 | `/api/admin/notices` GET/POST/PATCH/DELETE | system_admin / org_admin 默认包都含 → 不变；override 才能改 |
| `category` | 低 | `/api/admin/categories` GET/POST/PATCH/DELETE | platform-level，all only；system/org admin 都管 |
| `analytics` | 低 | `/api/admin/analytics` GET only | 读类，audit.read.org/all 复用（or 新 key） |
| `audit` | 低 | `/api/admin/audit-logs` GET only | 读类，audit.read.org/all（已在 ADMIN_KEYS） |

**为什么这四个先行**：
- notice / category：写操作不影响业务运行（错改可秒回）
- analytics / audit：只读路径
- 都不涉及钱、quota、外部 API key
- 4 个 resource 在矩阵里都已 seed 完整（v52）

## 关键设计决策

### D1 · analytics 是不是要新 key

| 选项 | 描述 |
|---|---|
| **(a) 复用 audit.read.{org,all}** | analytics 是审计/统计入口；用 audit 同一 key 简化（推荐） |
| (b) 新增 analytics.read.{org,all} 2 keys | 语义更精细，但 ADMIN_PERMISSION_KEYS / v52 seed / KEYS_BY_RESOURCE 都要加；矩阵也要补 |

**我倾向 (a)** —— Phase C 不动 keys 全集，保持基建 frozen；若以后 analytics 真要独立权限再拆。

### D2 · category 是不是要 4 keys 都接

`category.{read,create,update,delete}.all` 都 seed 了。route 是单文件多 method。

| 选项 | 描述 |
|---|---|
| **(a) GET → check read；POST/PATCH/DELETE → 各自 check create/update/delete**（推荐） | 与 _generic.buildPlatformAdapter 行为对齐；细粒度 |
| (b) 只接 GET，写动作仍用旧 hardcode | 简化但 Phase C 价值打折 |

**我倾向 (a)**。

### D3 · enforce 命中失败时的 fallback 策略

| 选项 | 描述 |
|---|---|
| **(a) requireAccess 返 403 → 直接 return（fail-closed）**（推荐） | 与方案 R3 一致；adapter 报错或拒，路由立即停 |
| (b) 报错后仍继续走旧逻辑 | 隐性 fail-open，违 §3.4 |

**我倾向 (a)** —— 与 Phase A R1 F1 fail-closed 策略对齐；任何 enforce 路径都不退回旧逻辑。

## 风险 / 边界

**R12（dev override 已存数据库）**：Phase B 期间小B 二审可能在 dev 写过一些 override，env 一开它们立即生效。
- 应对：Phase C 启动前先去 dev `/admin/permissions` Tab 1/2 看实际 override；若有意外加的，先清理
- 或：env 设 `notice,category` 两个先（少 surface），验通后再加 analytics/audit

**R13（adapter 已注册但 read action 名称不对齐）**：
- `_generic.buildTenantOwnedAdapter` 默认 readAction = "read"，notice/category 都是。OK。
- audit 在 `_generic.buildTenantOwnedAdapter`（Phase A 注册时）也 readAction=read；权限 key 为 `audit.read.{org,all}`。OK。
- analytics 不在 13 adapter 中——`/api/admin/analytics/route.ts` 没有"row" 概念（聚合数据），不走 adapter 模板。
  - 应对：analytics 用 `hasPermission(actor, "audit.read.all")` 内联判定（不走 requireAccess），或 facade 加 audit-only adapter（adapter 提前 enrich audit 的 list scope，但 analytics 不存在"detail row"）
  - **我倾向**：analytics 路由内联 `hasPermission(actor, "audit.read.all" / "audit.read.org")`，不走 facade —— 简化、与"非 row 资源"路径一致

**R14（双闸顺序）**：方案 §1.5 顺序是
1. requireAdmin（解 actor）
2. 5.30up 第一闸 `requireWriteAccess`（角色白名单 fail-fast，DB 实时 role）
3. Phase C 新增：v2 第二闸 `requireAccess`
- 第一闸已挡掉绝大多数非授权请求；第二闸是 v2 公式的细化判定
- 顺序错位（先第二再第一）会让 v2 直接返 403 错误文案，第一闸"角色不在白名单"的语义丢失 → 用户体验差但不放权
- 实施时严格按 1→2→3 顺序
