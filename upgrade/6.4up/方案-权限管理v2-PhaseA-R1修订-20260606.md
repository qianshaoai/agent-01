## F1 · effectivePermissions.size 不能当模式开关

### 现状

[`lib/permission-actor.ts:349`](../../lib/permission-actor.ts#L349)：

```ts
if (actor.effectivePermissions.size > 0) {
  // 走 v2 公式
} else {
  // 退回旧 role-based fallback（保 6.4up 行为）
}
```

[`lib/permission-actor.ts:184`](../../lib/permission-actor.ts#L184) 的 `loadEffectivePermissions` 把以下三种"应当 fail-closed"语义全部碾平成 `new Set<string>()`：

| 情景 | 期望 | 现状（size==0 → 走旧 fallback） |
|---|---|---|
| v2 未启用（env 空） | 走旧 fallback ✓ | ✓ 期望命中 |
| v2 启用，DB 查询失败 | fail-closed（403） | ✗ fail-open（旧权限回流） |
| v2 启用，全部 grant 都被 revoke | 无权 | ✗ 旧权限回流 |
| v2 启用，role 在 builtin_role_permissions 真的没 seed | 无权 | ✗ 旧权限回流 |

### 修法

在 `PermissionActor` 上增加显式开关字段，把"是否启用 v2"与"effective set 是否为空"解耦：

```ts
export type PermissionActor = {
  // ... 已有字段
  /** v2 enforce 通道是否对本 actor 加载成功（决定 hasPermission 走哪条路径） */
  v2Loaded: boolean;
  effectivePermissions: Set<string>;
};
```

`loadEffectivePermissions` 改返 tagged union（更难误用）：

```ts
type V2Load =
  | { kind: "skipped" }                   // env 空 / super_admin
  | { kind: "loaded"; set: Set<string> }  // 查 DB 成功
  | { kind: "failed" };                   // 查 DB 失败

async function loadEffectivePermissions(...): Promise<V2Load> { ... }
```

`buildBuiltinAdminActor` 把 V2Load 映射到 `v2Loaded` 字段：

| V2Load.kind | actor.v2Loaded | actor.effectivePermissions |
|---|---|---|
| `skipped` | `false` | 空 set（不参与判定） |
| `loaded` | `true` | 真实 set（可能为空 = 显式无权） |
| `failed` | **抛错 / actor 构建失败** | 让上游 requireAdmin 链返 500 |

`hasPermission` builtin 路径改写：

```ts
if (actor.source !== "custom_admin") {
  const role = actor.builtinRole;
  if (!role) return false;

  if (actor.v2Loaded) {
    // v2 启用：finalKeys 严格判定（空 set = 无权）
    if (!actor.effectivePermissions.has(key)) return false;
    // ... scope 闸 ...
    return true;
  }

  // v2 未启用：走旧 role-based fallback
  // （原 system_admin workflow 全放行 / org_admin workflow 按 tenantCode 闸门 分支）
}
```

### 取舍

- 选 fail-fast（v2 启用但 DB 查询失败 → actor 构建失败 → 上游 500）而非"v2 启用但加载失败 → 走旧 fallback"——前者更符合"启用 = 唯一判定通道"的语义，避免任何隐性 fail-open。
- env 空时**显式不查 DB**（v2Loaded 直接 false），保留 §3.4 no-op 性能预算。

## F2 · set-role 的 42883 fallback 必须删除

### 现状

[`app/api/admin/users/[id]/route.ts:100-117`](../../app/api/admin/users/[id]/route.ts#L100-L117)：

```ts
if (isPromotingToBuiltinAdmin) {
  const { error: rpcErr } = await db.rpc("change_user_role_clear_custom", { ... });
  if (rpcErr) {
    if (rpcErr.code === "42883") {                                  // RPC 不存在
      const { error: updErr } = await db.from("users").update({ role }).eq("id", id);
      if (updErr) return dbError(updErr);
    } else { ... }
  }
}

await writeAuditLog({
  ...
  detail: { ..., clearedCustomRoles: isPromotingToBuiltinAdmin },   // 标签恒等于 true，与实际不符
});
```

### 问题

| 现象 | 后果 |
|---|---|
| v52 RPC 未跑（生产部署漏）→ 42883 命中 fallback | `user_custom_roles` 未清理 → builtin admin 仍持 custom 权限 → 方案 §1.3 双通道隔离破裂 |
| 审计写 `clearedCustomRoles: true` | 实际未清；事后排查时审计撒谎 |

### 修法

去掉 42883 分支，让 RPC 缺失硬失败：

```ts
if (isPromotingToBuiltinAdmin) {
  const { error: rpcErr } = await db.rpc("change_user_role_clear_custom", { ... });
  if (rpcErr) return dbError(rpcErr);  // 包含 42883 ——配置错误，返 500
}
```

`MIGRATIONS.md` v52 行旁追加注释："**强依赖**：未跑 v52 → set-role 升 builtin admin 路径将 500"。

### 取舍

- 牺牲"未跑 v52 时降级可用"，换回方案硬合约。
- v52 是 Phase A 上线必跑（已在 MIGRATIONS.md 标 🔑），运行时缺 RPC 等价于"上线步骤漏跑"——本就该让人看见错。

## F3 · adapter registry 自动 bootstrap

### 现状

[`lib/adapters/access/index.ts`](../../lib/adapters/access/index.ts) 通过 side-effect imports 注册 13 个 adapter。但**没有任何文件 import 它**——`grep -r "adapters/access"` 在 app/ 与 lib/ 里 0 命中。

[`lib/access-facade.ts:134`](../../lib/access-facade.ts#L134)：

```ts
const adapter = getAccessAdapter(resourceKind);
if (!adapter) {
  console.error(`[requireAccess] adapter not registered for resource: ${resourceKind}`);
  return apiError("权限校验未就绪", "INTERNAL_ERROR");
}
```

一旦 `PERMISSION_V2_ENFORCE_RESOURCES = "notice"` 配上 → REGISTRY 空 → 路径恒 500。

### 修法 · 拆 registry 文件 + facade 顶部 import

直接在 `access-facade.ts` 顶部 `import "./adapters/access"` 会触发循环（facade → adapters/access/notice.ts → @/lib/access-facade → facade 还在评估 → adapter 文件拿到 partial module，`registerAccessAdapter` 可能未 hoist 完成）。

**改造**：把 REGISTRY 与 register/get 函数拆到独立模块 `lib/access-registry.ts`，facade 与 adapters 都依赖它，没有循环。

1. 新建 [`lib/access-registry.ts`](../../lib/access-registry.ts)（约 25 行）：

```ts
import type { ResourceAccessAdapter } from "@/lib/access-facade-types";
const REGISTRY = new Map<string, ResourceAccessAdapter<unknown>>();

export function registerAccessAdapter<TRow>(a: ResourceAccessAdapter<TRow>): void {
  REGISTRY.set(a.resourceKind, a as ResourceAccessAdapter<unknown>);
}
export function getAccessAdapter<TRow = unknown>(k: string): ResourceAccessAdapter<TRow> | null {
  return (REGISTRY.get(k) ?? null) as ResourceAccessAdapter<TRow> | null;
}
```

2. 把 `ResourceAccessAdapter` 接口 + `QueryModifier` type 抽到 [`lib/access-facade-types.ts`](../../lib/access-facade-types.ts)（纯 type-only，无 runtime 依赖；不引入循环）。

3. [`lib/access-facade.ts`](../../lib/access-facade.ts) 改：
   - 顶部 `import "./adapters/access";` —— 触发 13 个 side-effect register
   - `register / get` 改 re-export 自 `access-registry`
   - `ResourceAccessAdapter` re-export 自 `access-facade-types`（保持 `@/lib/access-facade` 对外 API 不变）

4. 13 个 adapter 文件 `import { registerAccessAdapter, type ResourceAccessAdapter } from "@/lib/access-registry"` + `from "@/lib/access-facade-types"`。

### 取舍

- 一次性把 facade / registry / types 三层分清，未来再加 adapter 无需 consumer 路由记得 import 任何东西。
- 若担心 13 个 adapter 都被 eager-evaluate 的体积开销：当前每个 adapter ≈ 10 行 stub，可忽略；enforce 前的副作用仅是 Map.set，无 DB / 网络。

## F4 · create 分支不传 row=null 给通用 adapter

### 现状

[`lib/access-facade.ts:172-175`](../../lib/access-facade.ts#L172-L175)：

```ts
if (action === "create") {
  const ok = await adapter.checkWrite(actor, row as never, action);  // row === null
}
```

[`lib/adapters/access/_generic.ts:55-58`](../../lib/adapters/access/_generic.ts#L55-L58)：

```ts
async checkWrite(actor, row, action) {
  const scope: "org" | "all" = row.tenant_code ? "org" : "all";       // row.tenant_code on null → TypeError
  ...
}
```

facade 注释说"adapter 内部处理 null row 的 create 语义"，但通用 adapter 没实现这条分支，所有 13 个 stub 都会 NPE。

### 修法 · 把 create 升为接口一等公民

在 `ResourceAccessAdapter` 增加 `checkCreate(actor, payload?)` 方法：

```ts
export interface ResourceAccessAdapter<TRow = unknown> {
  resourceKind: string;
  listFilter(actor): QueryModifier | null;
  loadDetail(id): Promise<TRow | null>;
  checkRead(actor: PermissionActor, row: TRow): Promise<boolean>;
  checkWrite(actor: PermissionActor, row: TRow, action: string): Promise<boolean>;
  /** Phase A 新增：create 不传 row；adapter 内部按 prefix.create.{scope} key 判定 */
  checkCreate(actor: PermissionActor, payload?: Partial<TRow>): Promise<boolean>;
  resolveCreateOwnership(actor, payload): Partial<TRow>;
}
```

`requireAccess` create 分支改：

```ts
if (action === "create") {
  const ok = await adapter.checkCreate(actor);
  if (!ok) return apiError("权限不足", "FORBIDDEN");
  return null;
}
```

`_generic.ts` 通用实现：

```ts
async checkCreate(actor) {
  // tenant-owned：actor 必须有 tenantCode 才能创建（org scope）
  const key = `${config.permissionPrefix}.create.org` as PermissionKey;
  return actor.tenantCode ? await hasPermission(actor, key, [{ scope_type: "org", scope_id: actor.tenantCode }]) : false;
}
```

`buildPlatformAdapter`（tenant / category）：

```ts
async checkCreate(actor) {
  const key = `${config.permissionPrefix}.create.all` as PermissionKey;
  return await hasPermission(actor, key);
}
```

`setting.ts` super-only：`checkCreate: async () => false`（super 在 facade 顶部已放行）。

### 取舍

- interface 加一个方法比"checkWrite 内部 if (action === 'create')"分支更显式，后续 lint rule / 自动注册的检查都更好做。
- Phase A 没 enforce 任何 resource，接口变化零运行时影响。

## F5 · `scripts/generate-permission-seed.ts`

### 现状

方案 §3.5 要求"矩阵驱动、可复算"的 seed 生成脚本。当前 v52 内 173 行 INSERT 是**手写**的，KEYS_BY_RESOURCE 一变就要手工同步。Phase A 缺这个脚本。

### 修法 · 新建脚本

[`scripts/generate-permission-seed.ts`](../../scripts/generate-permission-seed.ts)：

```ts
// 输入：lib/permission-keys/admin.ts 的 KEYS_BY_RESOURCE
// 业务规则：定义 SYSTEM_ADMIN_DEFAULT_PACK / ORG_ADMIN_DEFAULT_PACK 两个 set
//   - SYSTEM 包含资源 list 中 resource 是 system 层默认管的全集，但不含 provider.create.* / setting.* / permission.*
//   - ORG 包含 org 范围内所有资源的 read/update/.org 后缀，按矩阵规则裁剪
// 输出：v52 内 INSERT … 片段，写到 stdout

import { KEYS_BY_RESOURCE } from "@/lib/permission-keys/admin";

const SYSTEM_ADMIN_DEFAULT = (resource: string, key: string): boolean => {
  // 规则在脚本注释里写清楚——与方案 §2.2 矩阵对应
  if (resource === "provider" && key.startsWith("provider.create.")) return false;
  if (resource === "setting" || resource === "permission") return false;
  return true;
};

const ORG_ADMIN_DEFAULT = (resource: string, key: string): boolean => {
  if (!key.endsWith(".org")) return false;
  // ... 按矩阵规则
};

console.log("-- system_admin 默认包");
for (const [resource, keys] of Object.entries(KEYS_BY_RESOURCE)) {
  for (const k of keys) {
    if (SYSTEM_ADMIN_DEFAULT(resource, k))
      console.log(`INSERT INTO builtin_role_permissions(role, permission_key) VALUES ('system_admin', '${k}') ON CONFLICT DO NOTHING;`);
  }
}
// ...
```

### 验收闭环

跑 `npx tsx scripts/generate-permission-seed.ts > /tmp/seed.sql`，与 v52 内 seed 段 diff 必须为 0。若 keys 增/删后再跑脚本，diff 即为下一版 migration 的 seed 段。

### 不动 v52

- v52 已写好（手工）；R1 仅补脚本，让脚本输出与 v52 完全一致（脚本是"事后可复算证明"），不重发 migration。
- 未来 keys 调整 → 重跑脚本生成 v53 migration 的 INSERT 段，**保留 v52 作为基线**。

## N1（建议）· admin-overrides POST 校验

### 现状

[`app/api/admin/admin-overrides/route.ts:72-110`](../../app/api/admin/admin-overrides/route.ts#L72-L110) 只校验：
1. caller 是 super_admin ✓
2. 入参形状 ✓
3. permission_key 在合法清单 ✓
4. 拒 setting.* / permission.* 前缀 ✓

未校验：
- target adminId 在 `admins` 或 `users` 表是否真的存在
- target admin 的 role 是否为 super_admin（super 不应被 override，super 硬全权）

### 修法

POST handler 在 upsert 前增加 target 解析：

```ts
const tableMap = { admin_table: "admins", user_admin: "users" } as const;
const { data: targetRow } = await db
  .from(tableMap[adminSource])
  .select("id, role")
  .eq("id", adminId)
  .maybeSingle();

if (!targetRow) {
  return apiError("目标管理员不存在", "NOT_FOUND");
}
if ((targetRow as { role?: string }).role === "super_admin") {
  return apiError("不允许给 super_admin override（super 硬全权）", "FORBIDDEN");
}
```

### 取舍

- 短期不阻断 enforce（super 硬全权吞所有判定），但数据完整性 + 审计 + Phase B UI 复算时都受益。
- 提示文案明确告诉 super 不被 override，避免使用方误以为 v2 出 bug。
