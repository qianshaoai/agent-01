## B · 三大子主题 · 全方案候选

### 子主题 1 · RAG 单轮召回率

> 痛点：「我第一次轮值」语义距离 > 0.5 被丢掉

#### ☐ 1-A · 降 threshold 0.5 → 0.35

- 改 [lib/kb/config.ts:26](../../lib/kb/config.ts#L26) 一行
- 实施 10 秒；用户复测 1 分钟
- ✅ 立即见效
- ❌ 召回噪声片段，弱模型 / 紧凑模型可能被噪声误导 hallucinate
- ❌ 没解决「代词 / 模糊指代」类 query
- 工程量：**~10 min**

#### ☐ 1-B · query 改写（LLM rewrite）

- 在 `retrieveKbChunks` 前加一步：用便宜模型（如 gpt-4o-mini / haiku-4-5）把 user query 改写成 3 个语义不同的检索 query；每个 embed + 检索，合并去重 top-K
- 例：「我第一次轮值是啥时候」→ ["轮值排班表", "第一轮值班时间", "我的轮值日期"]
- ✅ 召回精度高
- ❌ 每轮 +1 LLM 调用，+ ~500ms 延迟、+ ~200 token 成本
- ❌ 改写模型对 Claude / 智谱 / OpenAI 平台都要适配（或硬编一个 rewriter provider）
- 工程量：**~3-4h**（含 prompt 设计 + 改写模型选型 + dev 测）

#### ☐ 1-C · history-aware query（历史拼接检索）

- query 改成 「最近 N 轮 user message + 当前问题」拼接后再 embed
- 例：第 3 轮 user 问「刚才那个职责具体是啥」→ query = 「轮值职责\n第一轮排班\n刚才那个职责具体是啥」
- ✅ 解决「代词 / 模糊指代」型问法
- ✅ 0 状态管理、不调额外 LLM
- ❌ 跨话题对话时 query 焦点模糊
- ❌ embedding 输入变长（多 ~300 token，影响不大）
- 工程量：**~1h**

#### ☐ 1-D · 不改（教 admin 用「明确措辞」）

- 写一段 admin 知识库使用须知，告诉 admin / 客户「问问题时用 KB 里的关键词原文」
- ✅ 0 改动
- ❌ 用户原话否决：「客户会用自己的方式去问」

#### ☐ 1-E · 组合 · A + C（降 threshold + 历史拼接）

- 1-A 提整体召回率，1-C 解决代词问题，两个都便宜
- 工程量：**~1.5h**

#### ☐ 1-F · 组合 · A + B + C（全套）

- 召回率天花板，但成本最高
- 工程量：**~5h**

### 子主题 2 · KB 多轮累积记忆

> 痛点：第 N 轮丢失第 1 轮 KB 注入的内容

#### ☐ 2-A · 简单累积 chunks 池

- 加 `sessionRetrievedChunks` 数组到 conversation 状态，每轮 KB chunks 加入并去重，全量注入到当前 user message
- ✅ 实现最简单（~30 行）
- ❌ 第 10 轮可能 50 chunks ≈ 25000 token，Opus OK 但 Haiku 紧
- ❌ 旧话题无关 chunks 残留干扰
- ❌ 跨话题时 prompt 混杂
- 工程量：**~1-2h**

#### ☐ 2-B · 滚动窗口累积（LRU N=8）

- 加 `KB_CONTEXT_MAX_CHUNKS = 8`，按 LRU 淘汰；多轮内固定 ~8×500=4000 token 上限
- ✅ token 可控
- ✅ 老话题 chunks 自然淘汰
- ❌ 跳话题瞬间会"短暂混杂"
- ❌ 需要 conversation 级状态管理（DB 或前端 ref 传回）
- 工程量：**~3h**（含状态持久化方案）

#### ☐ 2-C · history-aware 检索（同 1-C，复用）

- 不真累积 chunks，而是让检索能召回"上次提过的相关内容"
- ✅ 0 新状态
- ❌ 仍依赖 embedding 距离，「具体的"5 月 12 日"日期」这种事实型记忆仍会丢
- 工程量：与 1-C 合并，**0 额外**

#### ☐ 2-D · system role 持续注入 KB 摘要

- 每轮把"近 N 轮命中过的 chunks 摘要"放进 system role
- ✅ system 多轮持续可见，符合 LLM 角色设计
- ❌ Claude 中转吞 system → 对当前 anthropic provider 没用（5.30.1 R4 已知）
- ❌ 智谱 / OpenAI 可用，但增加 system 长度
- 工程量：**~2h**

#### ☐ 2-E · LLM 自检索（tool use）

- LLM 每轮自己决定要不要 call `search_kb(query)` tool；调用后 chunks 流回 LLM
- ✅ 最智能，按需检索
- ❌ 需要 tool_use 支持；anthropic 已有 / OpenAI 已有 / 其它平台不一定
- ❌ 实现复杂度最高（需要 tool-loop 处理）
- 工程量：**~1 天**

#### ☐ 2-F · 摘要 + 滚动（hybrid）

- 每 N 轮把之前的 KB 上下文压缩成摘要 + 保留最近 K 个 raw chunks
- ✅ 平衡 token + 长期记忆
- ❌ 复杂度高、需调摘要质量
- 工程量：**~1 天**

#### ☐ 2-G · 不做（保持每轮独立）

- 0 改动
- 用户已表达不满，应该做

### R1-1 · 【严重】intent.ts 短追问规则 · 必须先收窄

**原问题**：[lib/kb/intent.ts:18](../../lib/kb/intent.ts#L18) 当前规则

```ts
if (historyLength > 0 && t.length <= 6) return true;
```

会让「职责呢？」「时间呢？」「谁负责？」这类正是 1-C 历史拼接最想救回来的多轮追问
**在 [chat/route.ts:416](../../app/api/agents/[id]/chat/route.ts#L416) 被 `skipKbForThisTurn=true` 拦在 KB 检索前**。
1-C 改了也没用——根本没进检索逻辑。

**R1 修订**：把这条规则的"裸长度判断"换成**纯确认词白名单**：

```ts
// 6.4up R1-1 · 原规则被 1-C 历史拼接路线推翻：
//   多轮追问（"职责呢？" "时间呢？" "谁负责？"）正是 1-C 要救回来的场景，
//   不能在 KB 检索前直接 skip。改为只匹配真正的"确认 / 寒暄"白名单。
const CONFIRM_OR_ACK_RE = /^(好的|好|嗯+|明白|收到|了解|知道了|谢谢|多谢|可以|行|ok|OK)[。.！!~]?$/;
if (historyLength > 0 && t.length <= 6 && CONFIRM_OR_ACK_RE.test(t)) return true;
```

**白名单覆盖范围**：8 个高频中文确认词 + ok + 末尾标点容错。`谁负责` `时间呢` `职责呢`
这类追问都不匹配 → 进入 KB 检索 → 走 1-C 历史拼接路径。

**配套验收**（落入子主题 1 验收）：
- ☑ user 输入「好的」「明白」「谢谢」「ok」（≤6 字符 + 在白名单）→ skipKbForThisTurn=true
- ☑ user 输入「谁负责？」「时间呢？」「职责呢？」（≤6 字符 + 不在白名单）→ skipKbForThisTurn=false，触发 KB 检索

### R1-2 · 【严重】2-B LRU 不能存 chunk 正文 · 必须存 id + 注入前回查

**原问题**：R0 2-B 描述里隐含「LRU 数组里直接挂 chunk content」。这样有 3 个雷：
- KB 被 admin 停用（`knowledge_bases.status='disabled'`）后，旧 chunks 仍在 LRU 里继续注入
- 文档被重新 ingest（`kb_documents.status='indexing'` / `failed`）后，旧 chunk content 已不代表真实内容
- 文档被删除后，悬空 chunks 仍注入

这与 [migration_v42 RPC](../../supabase/migration_v42_match_kb_chunks_done_filter.sql) 设的「active KB + done 文档」过滤口径**直接相违**。

**R1 修订**：

#### a. LRU 状态结构

**只存最小必要**：`{ chunk_id, last_hit_at, order_in_window }`，**不存 content / kb_id / similarity**。

存储位置：**DB 新表 `kb_context_state`**（不走前端传回，避免恶意客户端伪造扩大 KB 注入）：

```sql
-- migration_v45_kb_context_state.sql
CREATE TABLE IF NOT EXISTS kb_context_state (
  conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  chunk_id        UUID NOT NULL REFERENCES kb_chunks(id) ON DELETE CASCADE,
  last_hit_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (conversation_id, chunk_id)
);
CREATE INDEX kb_context_state_conv_time_idx
  ON kb_context_state (conversation_id, last_hit_at DESC);
NOTIFY pgrst, 'reload schema';
```

ON DELETE CASCADE 保证：
- conversation 删 → 状态清空
- chunk 删（文档重 ingest）→ 状态自动剔除（无需手动清理）

#### b. 每轮注入流程

```ts
// 1. 本轮 KB 检索 → 本轮 chunks（沿用 retrieveKbChunks，含 active+done 过滤）
const currentChunks = await retrieveKbChunks(kbIds, expandedQuery);

// 2. 拉本轮 conversation 的 LRU chunk_id 列表（按 last_hit_at desc，取 N=8）
const { data: lruRows } = await db
  .from("kb_context_state")
  .select("chunk_id, last_hit_at")
  .eq("conversation_id", convId)
  .order("last_hit_at", { ascending: false })
  .limit(KB_CONTEXT_MAX_CHUNKS);  // 默认 8

// 3. 取 LRU chunk_id 中"不在本轮 chunks"的部分 → 注入前回查并过滤有效性
const currentIds = new Set(currentChunks.map((c) => c.id));
const lruExtraIds = (lruRows ?? [])
  .map((r) => r.chunk_id)
  .filter((id) => !currentIds.has(id));

const lruExtraChunks = await fetchActiveChunksByIds(lruExtraIds, kbIds);
// ↑ 新 helper：按 chunk_id 回查 kb_chunks，JOIN knowledge_bases.status='active'
//   + kb_documents.status='done' + kb_id IN (本 agent 当前 kbIds)
//   只返回仍有效的 chunks（已停用 / 失败 / 索引中 / 解绑的 KB 都被剔除）

// 4. 合并 → 注入 user prefix
const mergedChunks = [...currentChunks, ...lruExtraChunks];  // 本轮 chunks 优先排前
const kbInjectText = buildKbStrictAnswerPrompt(mergedChunks);

// 5. 写回 LRU（upsert，last_hit_at = NOW）
const allHitIds = mergedChunks.map((c) => c.id);
if (allHitIds.length > 0) {
  await db.from("kb_context_state").upsert(
    allHitIds.map((id) => ({ conversation_id: convId, chunk_id: id })),
    { onConflict: "conversation_id,chunk_id" }
  );
}

// 6. LRU 容量裁剪（写超 N 个时按 last_hit_at asc 删旧）
// 用 PG window function 或单条 DELETE WHERE rank > N 实现
```

#### c. 新 helper · `fetchActiveChunksByIds`

放 `lib/kb/retrieve.ts`：

```ts
export async function fetchActiveChunksByIds(
  chunkIds: string[],
  agentKbIds: string[],
): Promise<KbSearchResult[]> {
  if (chunkIds.length === 0) return [];
  const { data, error } = await db
    .from("kb_chunks")
    .select(`
      id,
      document_id,
      kb_id,
      content,
      knowledge_bases!inner(status),
      kb_documents!inner(status, filename)
    `)
    .in("id", chunkIds)
    .in("kb_id", agentKbIds)            // agent 已解绑某 KB → 立即不注入
    .eq("knowledge_bases.status", "active")
    .eq("kb_documents.status", "done");
  if (error) {
    console.warn("[kb/lru] fetchActiveChunksByIds 失败", error.message);
    return [];
  }
  return (data ?? []).map((r) => ({
    id: r.id,
    document_id: r.document_id,
    kb_id: r.kb_id,
    content: r.content,
    similarity: 0,                       // LRU 历史 chunks 不参与排序，给 0
    filename: r.kb_documents?.filename,
  })) as KbSearchResult[];
}
```

**口径与 RPC 一致**：`active` KB + `done` 文档 + `kb_id IN agentKbIds`。少一项就漏挡。

### R1-3 · 【中等】历史拼接限量

**原问题**：R0 1-C 没说拼几条 / 多长。直接拼 20 轮会让跨话题对话 query 严重失焦。

**R1 修订**：

```ts
// lib/kb/retrieve.ts 新签名：
export async function retrieveKbChunks(
  kbIds: string[],
  query: string,
  historyMessages?: ChatMessage[],   // 6.4up 1-C 新增
): Promise<KbSearchResult[]> {
  const ids = [...new Set(kbIds.filter((x) => typeof x === "string" && x))];
  if (ids.length === 0 || !query.trim()) return [];

  // 6.4up 1-C · 拼最近 2 条 user message + 当前问题
  //   - 只取 user 不取 assistant（assistant 答内容可能是模型乱编，污染检索）
  //   - 去掉 [参考：xx]\n 标记（前端 chip 标签，不是真实问题）
  //   - 去掉 [附件内容]\n... 段（附件文本太长会冲淡 query 焦点）
  //   - 每条 + 当前问题合并后整体截断 800 字符上限
  const recentUserTurns = (historyMessages ?? [])
    .filter((m) => m.role === "user")
    .slice(-2)
    .map((m) => stripAttachmentsAndRefMarker(m.content));
  const expandedQuery = [...recentUserTurns, query.trim()]
    .filter(Boolean)
    .join("\n")
    .slice(0, KB_RETRIEVE_QUERY_MAX_CHARS);  // 默认 800

  const queryVec = await embedQuery(expandedQuery);
  // ... 后续 match_kb_chunks RPC 不变
}

function stripAttachmentsAndRefMarker(content: string): string {
  return content
    .replace(/^\[参考：[^\]]+\]\n/, "")     // 参考 chip 标签（同 chat/route.ts:351）
    .replace(/\n\n\[附件内容\][\s\S]*$/, ""); // 附件文本段（chat/route.ts:368-369）
}
```

### R1.1-A · 2-B+ 核心设计 · 池 vs 注入分离

```
┌─────────────────────────────────────────────────────────────┐
│  记忆池（DB · kb_context_state）· 默认 64，可调 100         │
│   - 大池子，保存"这个会话见过的所有 KB chunk 元数据"          │
│   - 不存 content，只存 id + 元数据                          │
│   - 每轮 upsert：hit_count++, last_hit_at=NOW                │
│   - 超 N_POOL 时按 last_hit_at asc 删旧                     │
└─────────────────────────────────────────────────────────────┘
                          ↓ 每轮注入前
┌─────────────────────────────────────────────────────────────┐
│  注入窗口（prompt · runtime 选）· 默认 12（Opus 16 / 紧凑 8-10）│
│   - 候选池 = 本轮 RPC 召回 ∪ 记忆池所有有效 chunks            │
│   - 按 4 维综合分排序，取 top K_inject                       │
│   - K_inject 按 agent 模型能力动态选档                        │
│   - K_inject 个 chunks 才回查 kb_chunks 拿正文              │
└─────────────────────────────────────────────────────────────┘
```

**池大 / 窗口小**的好处：
- 记忆池大 → 第 20 轮还能记住第 3 轮命中过的 chunk（hit_count 累积体现"重点资料"）
- 注入窗口小 → token 不爆，模型 attention 不分散
- 排序解耦 → 旧 chunks 不会自动占位，必须"分高才能上桌"

### R1.1-B · 记忆池 schema（替换 R1-2 表定义）

```sql
-- migration_v45_kb_context_state.sql · R1.1 版本
CREATE TABLE IF NOT EXISTS kb_context_state (
  conversation_id  UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  chunk_id         UUID NOT NULL REFERENCES kb_chunks(id) ON DELETE CASCADE,
  first_seen_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_hit_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  hit_count        INT NOT NULL DEFAULT 1,
  last_similarity  REAL NOT NULL DEFAULT 0,    -- 0..1 余弦相似度，0 表示历史命中未参与本轮 RPC
  PRIMARY KEY (conversation_id, chunk_id)
);
CREATE INDEX kb_context_state_conv_time_idx
  ON kb_context_state (conversation_id, last_hit_at DESC);
CREATE INDEX kb_context_state_conv_hits_idx
  ON kb_context_state (conversation_id, hit_count DESC);

NOTIFY pgrst, 'reload schema';
```

字段语义：
| 字段 | 含义 | 写时机 |
|---|---|---|
| `first_seen_at` | 这条 chunk 第一次被命中的时间 | INSERT 时；UPDATE 不动 |
| `last_hit_at` | 最近一次命中（本轮 RPC 命中或本轮注入了它）| 每轮命中 / 注入都 = NOW() |
| `hit_count` | 累计命中次数 | 每轮命中 / 注入 ++1 |
| `last_similarity` | 最近一次 RPC 命中的余弦相似度；0 = 仅作为历史活跃被注入，未参与本轮 RPC | RPC 命中时 = similarity；纯历史注入时不改 |

CASCADE：
- conversation 删 → 池清空
- chunk 删（文档重 ingest / 文档删 / KB 删）→ 池自动剔除

### R1.1-E · 排序算法 · 综合分

```ts
type Candidate = {
  chunk_id: string;
  is_current: boolean;        // 本轮 RPC 命中？
  similarity: number;         // 0..1（本轮 RPC 命中的 similarity，否则 last_similarity 兜底）
  hit_count: number;          // 累计命中
  last_hit_at: Date;          // 最近活跃时间
};

function scoreCandidate(c: Candidate, now: Date): number {
  const w = KB_INJECT_SCORE_WEIGHTS;
  const ageMin = (now.getTime() - c.last_hit_at.getTime()) / 60_000;
  const recency = Math.exp(-ageMin / 60);  // 衰减 e^(-min/60)：1h 后衰减到 0.37
  const hitNorm = Math.log(c.hit_count + 1) / Math.log(11);  // hit=10 时 ≈ 1
  return (
    (c.is_current ? 1 : 0) * w.is_current +
    c.similarity * w.similarity +
    hitNorm * w.hit_count +
    recency * w.recency
  );
}
```

**为什么这样设：**
- `is_current` 权重 2.0 → 本轮命中肯定能进，避免被旧 chunks 挤掉
- `similarity` 1.5 → 即使是历史 chunk，与本轮 query 相关性高的优先复活（用 `last_similarity` 近似当前相关性）
- `hit_count` log 归一 → 防止"被命中 100 次的 chunk"永远霸榜
- `recency` 1h e-decay → 平衡"重点资料"和"旧话题"

**最终选 K**：候选池排序后取 top `pickInjectK(model)`，再调 `fetchActiveChunksByIds(selectedIds)` 拿正文（含 active KB / done 文档 / agent kbIds 过滤）。

### R1.1-F · 每轮注入完整流程（替换 R1-2 流程图）

```ts
// chat/route.ts · KB 注入段（R1.1 完整版）
async function injectKbForTurn(args: {
  convId: string;
  agentKbIds: string[];
  query: string;
  history: ChatMessage[];
  model: string;
}): Promise<{
  injectedChunks: KbSearchResult[];   // 真正注入给 prompt 的（K_inject 个）
  currentChunks: KbSearchResult[];    // 本轮 RPC 命中的（用于日志）
  poolSize: number;                   // 写回后池大小（用于日志）
}> {
  const { convId, agentKbIds, query, history, model } = args;

  // 1. history-aware query（1-C 已在 retrieveKbChunks 内部处理）
  const currentChunks = await retrieveKbChunks(agentKbIds, query, history);
  const currentIds = new Set(currentChunks.map((c) => c.id));

  // 2. 拉记忆池（按 last_hit_at desc，取全池）
  const { data: poolRows } = await db
    .from("kb_context_state")
    .select("chunk_id, first_seen_at, last_hit_at, hit_count, last_similarity")
    .eq("conversation_id", convId)
    .order("last_hit_at", { ascending: false });

  // 3. 构造候选池 = 本轮 RPC 命中 ∪ 记忆池（去重，本轮 RPC 命中优先用 similarity 覆盖）
  const candidates = new Map<string, Candidate>();
  for (const c of currentChunks) {
    candidates.set(c.id, {
      chunk_id: c.id,
      is_current: true,
      similarity: c.similarity,
      hit_count: 1,  // 临时，下面会从 pool 覆盖
      last_hit_at: new Date(),
    });
  }
  for (const r of (poolRows ?? [])) {
    const exist = candidates.get(r.chunk_id);
    if (exist) {
      exist.hit_count = r.hit_count + 1;  // 本轮命中 → ++
    } else {
      candidates.set(r.chunk_id, {
        chunk_id: r.chunk_id,
        is_current: false,
        similarity: r.last_similarity,
        hit_count: r.hit_count,
        last_hit_at: new Date(r.last_hit_at),
      });
    }
  }

  // 4. 综合分排序，取 top K_inject
  const k = pickInjectK(model);
  const now = new Date();
  const ranked = Array.from(candidates.values())
    .sort((a, b) => scoreCandidate(b, now) - scoreCandidate(a, now))
    .slice(0, k);

  // 5. 注入前回查正文（active KB + done 文档 + agentKbIds 过滤）
  const injectedChunks = await fetchActiveChunksByIds(
    ranked.map((c) => c.chunk_id),
    agentKbIds,
  );
  // 注：fetchActiveChunksByIds 内会按入参顺序返回；被过滤掉的 chunk_id 不返回
  // injectedChunks.length 可能 < k（少数 chunks 被回查过滤掉）

  // 6. 写回池：本轮所有命中的 chunks（current + 注入到的 LRU）upsert
  //    upsert 语义：新 chunk INSERT；旧 chunk UPDATE last_hit_at=NOW, hit_count+=1
  //    last_similarity 仅 current chunks 覆盖（其它保持原值）
  const upsertRows = injectedChunks.map((c) => {
    const isCurrent = currentIds.has(c.id);
    return {
      conversation_id: convId,
      chunk_id: c.id,
      last_hit_at: now.toISOString(),
      last_similarity: isCurrent ? c.similarity : undefined, // undefined 用 RPC，PG 保留旧值
      // hit_count 通过 DB 函数 atomic ++1
    };
  });
  // 用 RPC `bump_kb_context_state(p_rows jsonb)` 做 atomic upsert + hit_count++
  await db.rpc("bump_kb_context_state", { p_rows: upsertRows });

  // 7. 池容量裁剪：超 KB_MEMORY_POOL_SIZE 按 last_hit_at asc 删旧
  await db.rpc("trim_kb_context_state", {
    p_conversation_id: convId,
    p_max_size: KB_MEMORY_POOL_SIZE,
  });

  // 8. 拉裁剪后池大小（供日志用）
  const { count: poolSize } = await db
    .from("kb_context_state")
    .select("chunk_id", { count: "exact", head: true })
    .eq("conversation_id", convId);

  return { injectedChunks, currentChunks, poolSize: poolSize ?? 0 };
}
```

**RPC 必要性**（migration_v45 加 2 个 PL/pgSQL 函数）：
- `bump_kb_context_state(jsonb)`：单语句 atomic upsert + `hit_count = COALESCE(hit_count, 0) + 1` + 条件保留旧 `last_similarity`
- `trim_kb_context_state(uuid, int)`：DELETE WHERE 该 conv 池里按 `last_hit_at asc` 排第 N+ 行

不走业务代码 SELECT-then-DELETE 是因为并发场景下两轮请求会互相覆盖。

补充白名单：`清楚了 / 清楚`（小B R1.1 提示）。其它（"职责呢?" "时间呢?" "谁负责?"）放行进 KB。

### R1.1-H · workflowContext 场景的 KB 决策

> 小B R1.1 风险列表第 6 项：「workflowContext 场景是否应该跳过 KB 或保留现状」

**当前**：[chat/route.ts:416](../../app/api/agents/[id]/chat/route.ts#L416) `skipKbForThisTurn = wfCtx !== null || isMetaOrChitchatMessage(...)`

**R1.1 决策**：**移除 `wfCtx !== null` 这条短路**。只让 `isMetaOrChitchatMessage`（已收窄到纯确认词）单独负责拦截。

```ts
const skipKbForThisTurn = isMetaOrChitchatMessage(message, history.length);
//                       ↑ 不再 || wfCtx !== null
```

**理由**：
- 5.21up 当初加 wfCtx 短路是因为「工作流接力首条通常是 '好的进入下一步' 型」—— 但这种情况会被收窄后的 `isMetaOrChitchatMessage` 拦下
- 真实业务场景：工作流第 7 步问「我第一次轮值是啥时候」就是要查 KB 的，老短路把它误伤了（用户截图实锤）
- 多查一次 embedding 成本可控（~$0.0001/次）

**副作用**：工作流接力首条若是 7+ 字符的非知识问题（如「请帮我总结上一步」），会多走一次 embedding 调用。可接受。

### R1.1-J · 6 项风险与兜底（必写）

| # | 风险 | R1.1 兜底 |
|---|---|---|
| 1 | **token 爆炸**（多轮叠加 prompt 过长）| 注入窗口 K_inject 固定 ≤ 16；按模型档位动态降到 8（紧凑模型）。记忆池只存 id 不存正文。每轮 prompt 最大 ~16×500=8000 token，主流模型都吃得下 |
| 2 | **旧话题 chunks 干扰当前问题** | 综合分排序里 `is_current=2.0` + `similarity=1.5` 占绝对主导；纯历史活跃只能借 `recency` + `hit_count` 加少量分。跨话题 1-2 轮后旧话题 chunks 就出榜单 |
| 3 | **KB 停用 / 文档重建后旧 chunk 继续注入** | (a) `kb_context_state` ON DELETE CASCADE → chunk 删时池自动剔除；(b) 注入前 `fetchActiveChunksByIds` 必查 `active KB + done 文档 + 当前 agentKbIds`，与 [migration_v42 RPC](../../supabase/migration_v42_match_kb_chunks_done_filter.sql#L40-L49) 口径完全一致 |
| 4 | **前端 references 与实际注入 chunks 不一致** | `retrievedChunks = injectedChunks`（不是 currentChunks，也不是池里全部）。done 事件 references payload 就是真正 prompt 看到的 chunks |
| 5 | **草稿 test-chat 和正式 chat 口径不一致** | [test-chat/route.ts:142](../../app/api/admin/agent-drafts/[id]/test-chat/route.ts#L142) 同步调 `injectKbForTurn`；conversation_id 用「草稿 testId」做 stable key，每次开搭建器测试聊天清空池（草稿测试不需要长期记忆）|
| 6 | **workflowContext 场景跳 KB 还是保留** | 移除 `wfCtx !== null` 短路；只让收窄后的 `isMetaOrChitchatMessage` 单独负责（R1.1-H）。修复工作流第 N 步问知识 KB 不命中问题 |
