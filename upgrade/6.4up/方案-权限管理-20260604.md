## R0 → R1.2 评审摘要

**小B R0 Findings**
- **P0-1** · 后台入口链路被低估：middleware / `/api/me` / `elevate-to-admin` / `AdminPayload` / `getActiveAdmin` / `/api/admin/me` 全链路都只认三类 admin role。R1 不能只改 middleware。
- **P0-2** · `hasPermission()` 缺 scope ctx：`AdminPayload` 只有 tenantCode，没 dept_id/team_id。
- **P0-3** · `workflows.created_by_role` CHECK 只允许 3 档 admin role（v31）；custom admin 创建工作流写不进去 / 被错误伪装。
- **P1-1** · admin-layout 当前按 `allowedRoles` 过滤、`adminRole` state 默认 `super_admin`，me 加载前会闪超管菜单。
- **P1-2** · permission_key 一方面 free text、一方面又要 enum，矛盾。
- **P1-3** · 决策冲突："可被三种 admin 编辑" vs 决策 2 "仅 super_admin"。

**小B R1.0 二审 Findings**
- **P0-4** · custom admin 一旦进入普通 `requireAdmin()` 通道，会默认拿到大量旧 `/api/admin/*` 接口（如 users / tenants / analytics）。菜单隐藏挡不住直调 API。
- **P0-5** · workflow 表没有 `tenant_code/dept_id/team_id` 列；workflow scope 只能从 `resource_permissions` 推导，不能写不存在字段。
- **P0-6** · 现有代码里有 `admin.role ?? "super_admin"` / `role ?? "super_admin"` 历史兜底；如果把 custom admin 表达成 `role=null`，可能被误判成超管。
- **P1-4** · workflow 试点说不开放 enable/disable/duplicate/delete，但 `enabled` 与 update 共用 PATCH，workflow step 也在同页调用，边界需写清。

**R1.1/R1.2 收口方向**：
- 保留现有 `requireAdmin()` 语义：只允许 builtin admin（三档 admin role）。
- 新增独立的 custom-admin 访问通道：`getAdminAccessPayload()` / `requirePermission()` / `buildPermissionActor()`。
- workflow v1 试点只对显式接入 `requirePermission()` 的接口开放；其他 `/api/admin/*` 继续 fail-closed。
- workflow scope 全部基于 `resource_permissions`，不新增 `workflows.tenant_code/dept_id/team_id`。
- 全仓扫描并消除 custom-admin 可达路径里的 `role ?? "super_admin"` 越权风险。
- **R1.2 补强**：后端 custom role 写 API 单列 `.all` 后缀保护；任何 `permission_key` 以 `.all` 结尾时，actor 必须是 `super_admin`，否则 403。

## 背景

用户原话：
> 我想做一个权限管理的功能，超级管理员可以设定其他所有管理员的后台权限；同时支持自定义角色，比如设置小组长，该小组长只能创建本组的工作流。

**用户决策（2026-06-04）**：
- 现有 4 档（super/system/org/user）保留不动。
- custom role = "拥有进入后台钥匙 + 部分功能能力的普通用户"，**不在等级体系内**。
- 仅 `super_admin` 能创建 / 编辑 custom roles。
- scope 要覆盖 team / dept / org / all。

## 推荐路线 · B-R1.2 · 双通道权限模型

### 核心概念

引入 **custom admin access**，但不把它混入旧 `requireAdmin()` 通道：

| Actor | 来源 | access source | 入口 | builtin role | 业务 API 入口 |
|---|---|---|---|---|---|
| 系统内置管理员 | admins 表 | `admin_table` | admin/login | super/system/org | `requireAdmin()` |
| 提升为管理员的普通用户 | users 表 + role∈3档 | `user_admin` | admin/login 或 elevate | super/system/org | `requireAdmin()` |
| **自定义管理员（新）** | users 表 + role=user + 有 custom role | `custom_admin` | admin/login 或 elevate | 无 | 仅 `requirePermission()` |

**硬规则**：
- `requireAdmin()` 保持旧语义，只允许 builtin admin；所有未改造的 `/api/admin/*` 默认不接受 custom admin。
- custom admin 只能访问显式接入 `requirePermission(permissionKey)` 的接口。
- custom admin 不拥有 `AdminRole`，也不能用 `role=null` 塞进 `AdminPayload`，避免旧代码 `role ?? "super_admin"` 误判。
- `/api/admin/me` 是菜单上下文接口，可读取 custom admin access cookie 并返回 permissions；它不是业务写权限入口。

### 数据模型 · migration v50

```sql
-- 1. 角色定义表
CREATE TABLE custom_roles (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT NOT NULL UNIQUE,
  code        TEXT NOT NULL UNIQUE,
  description TEXT NOT NULL DEFAULT '',
  enabled     BOOLEAN NOT NULL DEFAULT true,
  created_by  UUID, -- 无 FK，兼容 admins/users 双来源
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 2. 角色 ↔ 权限
CREATE TABLE custom_role_permissions (
  role_id        UUID NOT NULL REFERENCES custom_roles(id) ON DELETE CASCADE,
  permission_key TEXT NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (role_id, permission_key)
);
CREATE INDEX idx_role_permissions_role ON custom_role_permissions(role_id);

-- 3. 用户 ↔ 角色
CREATE TABLE user_custom_roles (
  user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role_id    UUID NOT NULL REFERENCES custom_roles(id) ON DELETE CASCADE,
  granted_by UUID,
  granted_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (user_id, role_id)
);
CREATE INDEX idx_user_custom_roles_user ON user_custom_roles(user_id);

-- 4. workflow creator 语义拆分
ALTER TABLE workflows
  ADD COLUMN IF NOT EXISTS created_by_kind TEXT
    CHECK (created_by_kind IS NULL OR created_by_kind IN ('admin', 'custom_admin')),
  ADD COLUMN IF NOT EXISTS created_by_role_code TEXT;

UPDATE workflows
   SET created_by_kind = 'admin',
       created_by_role_code = created_by_role
 WHERE created_by_kind IS NULL;

-- 旧 created_by_role 字段保留兼容；builtin admin 继续写旧字段。
-- custom admin 新建 workflow 时 created_by_role 留 NULL，只写 created_by_kind/created_by_role_code。
```

### AccessPayload + PermissionActor

**不要修改 `AdminPayload.role` 为 nullable。** 新增等价访问类型：

```ts
export type AdminAccessPayload =
  | (AdminPayload & { source: 'admin_table' | 'user_admin' })
  | {
      type: 'admin';
      source: 'custom_admin';
      userId: string;
      username: string;
      iat?: number;
    };

export type PermissionActor = {
  actorId: string;
  source: 'admin_table' | 'user_admin' | 'custom_admin';
  tenantCode: string | null;
  deptId: string | null;
  teamId: string | null;
  userType: 'personal' | 'organization' | null;
  builtinRole: AdminRole | null;
  customRoleCodes: string[];
  permissions: Set<PermissionKey>;
};
```

新增 helper：
- `getAdminAccessPayload()`：只验 admin cookie / freshness，返回 builtin 或 custom access payload。
- `getActiveAdmin()` / `requireAdmin()`：继续只返回 builtin `AdminPayload`；遇到 `source='custom_admin'` 返回 401/403。
- `buildPermissionActor(accessPayload)`：从 users/admins/custom role 表补齐 actor 上下文。
- `hasAnyCustomRole(userId)`：给 `/api/me`、admin login、elevate 使用。
- `requirePermission(permissionKey)`：验证 access cookie、构造 actor、校验 permission，失败返回 403。

### hasPermission() 与 workflow scope

```ts
type PermissionScope = {
  scope_type: 'all' | 'org' | 'dept' | 'team';
  scope_id: string | null;
};

export async function hasPermission(
  actor: PermissionActor,
  permissionKey: PermissionKey,
  targetScopes?: PermissionScope[]
): Promise<boolean>;
```

判定规则：
- builtin admin：
  - super_admin：放行。
  - system_admin：放行 v1 workflow 权限。
  - org_admin：必须在本组织范围内，沿用现有 org_admin resource_permissions 逻辑。
- custom admin：
  - 必须持有对应 permission key。
  - create 时按 permission suffix 决定要写入的 `resource_permissions` scope。
  - update/read 时从目标 workflow 的 `resource_permissions` 反查 scope；没有 scope、scope 混杂、或任何一条 scope 超出 actor 权限范围 → 拒绝。

scope 包含关系：
- `team`：仅 `scope_type='team' && scope_id=actor.teamId`。
- `dept`：允许 `scope_type='dept' && scope_id=actor.deptId`，以及 `scope_type='team'` 且该 team 属于 actor.deptId。
- `org`：允许 `scope_type='org' && scope_id=actor.tenantCode`，以及本组织下 dept/team scope。
- `all`：仅持有 `.all` 权限时允许 `scope_type='all'`。

**禁止项**：
- 不新增、也不引用 `workflows.tenant_code` / `workflows.dept_id` / `workflows.team_id`。
- 不用 `visible_to` 字面值推断 custom admin 的写权限；custom admin 写权限只看 `resource_permissions`。

### `role ?? "super_admin"` 安全扫描

实施前必须全仓扫描：
- `role ?? "super_admin"`
- `admin.role ??`
- `actorRole = (admin.role`
- `created_by_role`
- 只调用 `requireAdmin()` 且没有额外权限闸门的 `/api/admin/*` 路由

处理原则：
- custom admin 可达接口必须改为 `requirePermission()`，且不得使用 `admin.role` 兜底。
- custom admin 不可达接口保持 `requireAdmin()`，自动 fail-closed。
- builtin admin 原有兜底如需保留，必须位于 `requireAdmin()` 之后，保证 actor 不可能是 custom admin。

## 验收清单（R1.2）

**权限基础**
1. `PERMISSION_KEYS` 含 workflow read/create/update 的 team/dept/org/all；custom role API 传非法 key 返回 400。
2. `.all` 权限只能由 super_admin 授予；POST/PUT custom role 时任一 `permission_key` 后缀为 `.all` 且 actor 非 `super_admin` → 403。
3. `requireAdmin()` 对 custom admin 返回 401/403；旧 `/api/admin/users`、`/api/admin/tenants`、`/api/admin/analytics` 直调不放行 custom admin。
4. `requirePermission()` 能识别 builtin admin 与 custom admin；custom admin 只按 permissions 集判。

**入口链路**
5. 普通 user 无 custom role：admin/login 拒；elevate 403；`/api/me.isAdmin=false`。
6. 普通 user 有 custom role：admin/login / elevate 能签 custom access cookie；`/api/me.isAdmin=true`。
7. `/api/admin/me` 对 custom admin 返回 `source='custom_admin'`、builtinRole 为空、customRoleCodes、permissions；该空值仅用于前端展示，不回灌 `AdminPayload`。
8. builtin admin 三档登录 / elevate / `/api/admin/me` 行为不变。

**admin layout**
9. me 加载前只有 skeleton，不闪超管菜单。
10. custom admin 只看到 `requiredPermission` 命中的菜单；无菜单时显示兜底页。
11. builtin admin 菜单仍按 `allowedRoles`。

**workflow 试点**
12. custom admin 持 `workflow.create.team` 创建 workflow 后：`visible_to='custom'`，`resource_permissions(scope_type='team', scope_id=actor.teamId)`，不写不存在的 workflow team/dept/org 列。
13. custom admin 持 `workflow.update.team`，目标 workflow 任一 scope 不在 actor.teamId 内 → PATCH 403。
14. custom admin 持 `workflow.update.dept/org` 可更新其 scope 覆盖内的 workflow；跨 scope 或 mixed scope 超出范围 → 403。
15. custom admin PATCH workflow 传 `enabled` → 403；不能启停。
16. custom admin 不能 DELETE / duplicate workflow。
17. custom admin 可新增、编辑、重排自己 update scope 内的 workflow steps；不能删除或启停 steps。
18. builtin admin workflow CRUD / step CRUD 现有行为不变。

**审计与安全扫描**
19. custom_roles CRUD / 授予 / 撤销写 `audit_logs(resource_type='custom_role')`。
20. workflow custom-admin 写操作 audit detail 记录 `created_by_kind / created_by_role_code / permission_key / scope`。
21. 全仓 `role ?? "super_admin"` 扫描完成；custom-admin 可达路径无超管兜底。
22. 全仓只调用 `requireAdmin()` 的旧 API 直调 custom admin 均 fail-closed。

| custom admin 误入旧 `/api/admin/*` | `requireAdmin()` builtin-only；custom 只能走 `requirePermission()` |
| workflow scope 误用不存在列 | R1.2 明确只从 `resource_permissions` 读写 scope |
| `role ?? "super_admin"` 越权 | 新增 AdminAccessPayload，不让 custom admin 进入 AdminPayload；实施阶段强制扫描 |
| update 与 enable/disable 共用 PATCH | custom admin PATCH 显式拒绝 `enabled` 字段 |
| workflow step 同页半通半断 | v1 纳入 step POST/PUT/PATCH；DELETE/enable/disable 明确不开放 |
| 菜单隐藏但 API 可直调 | 后端 `requirePermission()` 是真实权限源，菜单只做体验层过滤 |
