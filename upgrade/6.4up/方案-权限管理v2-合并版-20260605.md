## Context · 为什么重做

用户原本要的两件事：
1. **超管可以设定除超级管理员以外其他管理员（system_admin / org_admin）的所有后台权限**——不局限工作流。
2. **同时支持自定义角色**（如"小组长只能建本组工作流"）。

6.4up 实际产出（"扭曲了原本的意思"）：
- ✅ 加了 `custom_roles` / `custom_role_permissions` / `user_custom_roles` 三表 + `requirePermission()` 通道
- ❌ permission_keys 只 12 项，**全部 workflow**——agents / kb / model_providers / tenant / user 等资源完全没接入
- ❌ **builtin admin（system_admin / org_admin）权限完全不可改**——还是硬编码 role list
- ❌ 自定义角色只能挂到 `role=user` 的普通用户

诉求 ① 完全缺失；诉求 ② 只做了"workflow 试点"的简化版。本方案补齐两条诉求。

## 1. 核心模型 · D 路线三层混合

### 1.1 三层职责

| 层 | 内容 | 谁能改 |
|---|---|---|
| **结构性约束**（hardcode） | org_admin 只能动自己 `tenant_code` 的资源；user_admin 不能超出提升来源 role；org_admin 缺 tenantCode fail-closed | 无人能改（代码层） |
| **角色默认包**（DB） | 每个 builtin role 的"标准权限集"，新管理员默认拿到 | 仅 super 改 `builtin_role_permissions` 表 |
| **个人 override**（DB） | 某个具体 admin 在标准包基础上 grant / revoke | 仅 super 改 `admin_permission_overrides` 表 |

### 1.2 最终权限公式

```
hasPermission(actor, key, targetScopes):
  if actor.builtinRole == 'super_admin': return true            # 硬规则，super 永远全权
  if hasStructuralDeny(actor, key, targetScopes): return false  # tenant_code 等不可改的归属约束
  finalKeys = roleDefaultPack(actor.builtinRole)                # 来自 builtin_role_permissions
            ∪ adminGrantOverride(actor.actorId)                 # 来自 admin_permission_overrides
            − adminRevokeOverride(actor.actorId)
  return finalKeys.has(key) && scopeOk(actor, key, targetScopes)
```

**注意**：公式**不含** customRolePack。custom admin 走完全独立通道（见 §1.3）。

### 1.3 Key 空间拆分

```ts
// lib/permission-keys/workflow.ts
//   6.4up 原 12 keys —— custom 通道（requirePermission）写入校验用
//   注意：这些 keys 也存在于 ADMIN_PERMISSION_KEYS（让 builtin admin 也能被 super 配 workflow 权限）
//   两通道独占的是「写入校验」而非 key 本身
export const WORKFLOW_PERMISSION_KEYS = [
  "workflow.read.team", ..., "workflow.update.all"  // 共 12 个
] as const;

// lib/permission-keys/admin.ts
//   ADMIN 通道（v2 builtin admin override）的全集
//   workflow.read/create/update.{team,dept,org,all} 12 个与 WORKFLOW set 重叠
//   workflow.enable/duplicate/delete.* 是 v2 新增，只在 ADMIN set
export const ADMIN_PERMISSION_KEYS = [
  // workflow 12 keys（与 WORKFLOW set 重叠）+ workflow.enable/duplicate/delete.*（v2 新增）
  // agent 系列、agent_draft 系列、kb / provider / notice / tenant / user / category 等
] as const;

// lib/permission-keys/index.ts
export const PERMISSION_KEYS = [...WORKFLOW_PERMISSION_KEYS, ...ADMIN_PERMISSION_KEYS] as const;
// 仅 type union / list 暴露用，不参与任何写入校验
```

**写入校验严格按 set 分流**：
- `custom-roles` POST/PATCH（6.4up 路径）→ 入参严校 `WORKFLOW_PERMISSION_KEYS`
- `admin-overrides` POST/PATCH（v2 新路径）→ 入参严校 `ADMIN_PERMISSION_KEYS`

**双通道隔离硬规则**：
- `requireAdmin()` builtin 通道**不读** `user_custom_roles`
- `requirePermission()` custom 通道**不读** v52 两张新表
- **role=user 晋升 builtin admin 时强制清 user_custom_roles** —— 实现机制：新增 PostgreSQL RPC `change_user_role_clear_custom(p_user_id UUID, p_new_role TEXT, p_actor_id UUID)`，一次事务完成 `UPDATE users.role` + `DELETE FROM user_custom_roles WHERE user_id=p_user_id` + `INSERT audit_logs(action='delete', resource_type='custom_role', detail={ reason:'promoted_to_builtin_admin' })`；users PATCH set-role 分支调 RPC 而非裸 update

### 1.5 hasPermission 与 scoped-access 协同 · Resource Adapter

**不重写** `lib/scoped-access.ts`（已生产）。新建**资源适配器模式**：

```ts
// lib/access-facade.ts
export interface ResourceAccessAdapter<TRow = unknown> {
  resourceKind: string;
  // list filter：返回 query modifier（如 listScopeFilter 字符串、自定义 SQL where）
  listFilter(actor: PermissionActor): QueryModifier | null;
  // load detail：adapter 知道自己的 table 名 + select
  loadDetail(id: string): Promise<TRow | null>;
  // 读权限判定（结构性 + permission） — 异步：scope 判断常要查 DB
  checkRead(actor: PermissionActor, row: TRow): Promise<boolean>;
  // 写权限判定（结构性 + permission + sub-action） — 异步
  checkWrite(actor: PermissionActor, row: TRow, action: string): Promise<boolean>;
  // 创建时的 ownership 注入（写入 patch 前调）
  resolveCreateOwnership(actor: PermissionActor, payload: Partial<TRow>): Partial<TRow>;
}

// requireAccess 接收 row（已 load）或 id（自动 load）
export async function requireAccess(
  actor: PermissionActor,
  resourceKind: string,
  action: string,
  opts?: { row?: unknown; id?: string },
): Promise<Response | null>;
// 实现逻辑：
//   if (opts.row) → 直接调 adapter.checkRead/checkWrite(actor, opts.row, action)
//   else if (opts.id) → adapter.loadDetail(opts.id) → 404 屏蔽 / 调 check
//   else → 视为 'create' / list 场景，不需要 row
```

**各 resource adapter 落到** `lib/adapters/access/<kind>.ts`（**13 个**）：

| Adapter 文件 | 内部走 | 复用 |
|---|---|---|
| `model-provider.ts` | tenant_code ownership | 直调 `lib/scoped-access.ts` 五件套 |
| `knowledge-base.ts` | tenant_code ownership | 同上 |
| `workflow.ts` | resource_permissions 反查 | 已有 6.4up `getResourceTenantCode("workflow", id)` |
| `agent.ts` | tenant_agents + visibility_config | 已有 5.19up `app/api/admin/agents/route.ts` 逻辑抽出 |
| **`agent-draft.ts`** | `agent_drafts.created_by` 反查 user 的 tenant/dept/team | 5.30up 草稿链路收口已有 canReadRow 雏形 |
| `user.ts` | users.tenant_code + dept/team 上下级 | `lib/admin-permissions.ts canActOnRole` |
| `tenant.ts` | 平台级（all scope only） | — |
| `category.ts` / `notice.ts` / `dept.ts` / `team.ts` / `audit.ts` / `setting.ts` | 各自规则 | — |

**调用模板**（路由层）：

```ts
// 1. requireAdmin（已有）
const admin = await requireAdmin();
if (admin instanceof Response) return admin;

// 2. 构造 actor（已有 buildPermissionActor）

//     const accessErr = await requireAccess(actor, "category", "delete", { id });
```

## 2. DB · migration_v52_permission_v2.sql（新建）

### 2.1 表 schema

```sql
-- 1. 角色默认权限包
CREATE TABLE IF NOT EXISTS builtin_role_permissions (
  role           TEXT NOT NULL CHECK (role IN ('system_admin','org_admin')),
                                              -- super_admin 不入表（硬全权）
  permission_key TEXT NOT NULL,
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_by     UUID,
  PRIMARY KEY (role, permission_key)
);
CREATE INDEX idx_brp_role ON builtin_role_permissions(role);

-- 2. 个人 override
CREATE TABLE IF NOT EXISTS admin_permission_overrides (
  admin_id       UUID NOT NULL,
  admin_source   TEXT NOT NULL CHECK (admin_source IN ('admin_table','user_admin')),
  permission_key TEXT NOT NULL,
  effect         TEXT NOT NULL CHECK (effect IN ('grant','revoke')),
  reason         TEXT,
  created_by     UUID NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  -- PK 含 admin_source：与 actor 身份模型一致（admin_table vs user_admin 是 actor 身份的一部分）
  -- 同时防御理论上的 UUID 撞（admins 与 users 各自 gen_random_uuid 独立空间）
  PRIMARY KEY (admin_source, admin_id, permission_key)
);
CREATE INDEX idx_apo_admin ON admin_permission_overrides(admin_source, admin_id);
```

### 3.3 P2 · 路由分阶段接入

**不一锅端**：

1. 60~80 个 admin 路由维持 `requireAdmin()` + scoped-access 五件套不动
2. 在 `requireAdmin()` 之后**新增一行** `requireAccess(actor, kind, action, { row | id })`
3. 默认空 enforce flag（hasPermission fallback 到旧 role 判定）
4. 按 resource 逐组开 enforce：`notice → category → user → agent → workflow → kb → provider → tenant`（低→高风险）
5. **6.4up custom_admin 通道单独保留**：custom admin 完全不受 v2 影响

### 3.4 Feature flag

**单一 flag**：`PERMISSION_V2_ENFORCE_RESOURCES`（CSV，单一来源）
- 空 = 完全等价 6.4up 行为
- `"notice,category"` = 仅这两类资源走 v2 enforce
- 回滚口径：清空 CSV → 行为回 6.4up；DROP TABLE 是终极物理回滚

**实现边界**（关键，避免歧义）：
- flag 不含该 resource 时 → `requireAccess(actor, kind, action, opts)` **完全 no-op**，直接 `return null`：
    - 不调 adapter 任何方法（不 load row、不 checkRead/checkWrite）
    - 不读 v52 两张新表（`builtin_role_permissions` / `admin_permission_overrides`）
- adapter **不复刻**旧逻辑——它就是新模型本体；旧行为完全由 `requireAdmin()` + `scoped-access` 五件套 + `canManageTarget` + 各路由 hardcode 白名单继承
- "零行为变化"承诺成立的前提：路由内 `requireAccess` 那一行加入后，旧 hardcode 闸门**全部保留**，不动 5.30up 双闸模板；新闸只是叠加一道（且空 flag 时这道是 no-op）

## 5. 验收口径（22 条）

**全权与默认**
1. ✅ super_admin 在 v52 启用后任何操作仍放行（公式第 1 步）
2. ✅ system_admin 不做 override 时所有 6.4up 之前能操作的接口仍能操作（seed 矩阵驱动 = 等价）
3. ✅ org_admin 不做 override 时本组织内 agent/workflow/kb/provider CRUD 行为与 5.30up 完全一致

**编辑生效**
4. ✅ super 在 Tab 1 给某 org_admin grant `kb.delete.org` → 该 admin 下次请求**立即**能删本组织 KB（无需重登）
5. ✅ super 在 Tab 2 把 `org_admin` 默认包里 `workflow.create.org` 删掉 → 所有 org_admin 立即不能创建工作流；但持有个人 grant 的 admin 仍可（override 优先于默认包）

**结构性约束不被绕过**
6. ✅ super 不能 override 给某 org_admin 操作**别的组织**资源的能力（tenant_code 归属在 hardcode 层）
7. ✅ super 不能给 system/org_admin grant `permission.*` 或 `setting.*`（API + UI 双层禁止）

**custom role 不破坏**
8. ✅ custom admin（v50 路径）所有 12 个 workflow keys 行为与 6.4up 一致；`requirePermission()` 不读 v52 两表

## 6. 主要风险（R1-R11）

| # | 风险 | 缓解 |
|---|---|---|
| **R1** | 80+ keys seed 写漏一条 → 某 system_admin 接口突然 403 | seed 用 `KEYS_FOR_ROLE_DEFAULT_SEED` 常量生成；`scripts/audit-permission-coverage.ts` 扫所有 `requireAccess()` 调用与 seed 取差集报警；ENFORCE 默认关 |
| **R2** | super 把自己 `permission.update.all` revoke → 自锁死 | UI + API + DB trigger 三层拒：override 写入校验 `target is super OR key starts permission.*` → reject |
| **R3** | scoped-access 五件套被 v2 公式绕过，org_admin 改别组织 KB | access-facade 强制顺序"先 `canWriteRow` 后 hasPermission"；ESLint custom rule 禁止 admin route 直接 import `hasPermission`，必须走 facade |
| **R4** | `?? "super_admin"` 历史兜底再次触发 | Phase F 全仓二扫；unit test：fake actor builtinRole=null → hasPermission 必拒 |
| **R5** | Tab 1 加载慢（100+ admin × 80 key = 8000 cell） | 列表只显示"override 条数"+"effective key 数"，详情 lazy load；effective 后端聚合接口，不在前端 N+1 |
| **R6** | 半开半关 flag 调试困难 | flag 改 resource 维度 CSV；`/api/admin/me` 返回 `enforceMap` 供前端调试 |
| **R7** | Tab 2 改默认包影响所有同角色 admin，超管误操作放大 | 二次确认对话框显示影响人数 + audit 记录 + "一键回滚到上次版本"按钮（读 audit_logs）|
| **R8** | 矩阵脚本扫漏一种 role gating pattern（如解构后 if 判定） | 脚本输出"未识别"路由清单，强制人工补；review 时对照清单逐条 ack |
| **R9** | 双通道隔离硬规则实际实现时漏掉某一处 | unit test：`buildPermissionActor` 假装 source='custom_admin' → 输出 effectivePermissions 必须 ∩ ADMIN_KEYS = ∅；反向同款 |
| **R10** | agent_draft 和 agent 两套 key 空间用户混淆——"我给了 agent.update.org 为啥还不能 publish 草稿" | UI Tab 1 矩阵展示时按资源分块；agent / agent_draft 各自一栏；hover tooltip 说明"草稿与已发布是独立权限"|
| **R11** | adapter 异步化后路由层 `await requireAccess` 与现有 5.30up 模板的并行调用导致 5xx 时差异行为 | facade 内部统一 `try/catch` 包装；任何 adapter throw → facade 返 500（不假装 403）；路由层只看返回值类型 |
