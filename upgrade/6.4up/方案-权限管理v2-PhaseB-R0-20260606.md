### C1 · 所有新 API super_admin only · `role` 严校

- 不复用 `/api/admin/audit-logs` 那种 org_admin 也可见的策略

### C2 · Tab 2 PUT 不用事务 · 改差量写 + 读后校验

Supabase JS service client 不提供多语句事务；本期不加 RPC / 新 migration，PUT 用以下顺序：

```
1. 读 before keys（SELECT WHERE role=:role）
2. 双护栏：confirmBeforeHash + confirmAffectedCount → 412
3. 算 diff（toAdd = new - before, toRemove = before - new）
4. 写新增（UPSERT toAdd，ON CONFLICT DO NOTHING）
5. 写移除（DELETE WHERE role=:role AND key IN toRemove）
6. 读后校验：再 SELECT WHERE role=:role，与期望集 strict equal
7. 校验失败 → 不写 audit，500 "写后校验失败，请刷新重试"
8. 校验通过 → 写 audit（detail 含 before / after / added / removed）
```

差量写避免一锅 DELETE+INSERT 的"分裂态被人看到"；读后校验兜底"两步之间有人写"。

### C3 · 并发护栏双条件

PUT body 必须含两个字段：
- `confirmAffectedCount: number` —— 防"admin 人数变化"
- `confirmBeforeHash: string` —— 防"模板被别人并发改"（hash = sha256 of sorted before keys, hex）

服务端独立重算两个值；任一不匹配 → 412 PRECONDITION_FAILED + 中文文案区分哪一项变了，前端弹窗"请刷新重试"。

### C4 · seed:diff 不用 bash `<(...)`

bash 进程替换语法在 Windows npm script 下会炸（PowerShell 不支持）。两种选择，本期采取后者：

- ❌ npm script 用 bash here-doc / 进程替换
- ✅ 新建 `scripts/check-permission-seed.ts` 跨平台：脚本内自己跑 `generate-permission-seed.ts` 输出 + 读 v52 文件 + extract 区间 + diff → 不匹配 process.exit(1)；`package.json` 加 `"seed:gen"` + `"seed:check"` 两个 script，后者直接 `tsx scripts/check-permission-seed.ts`

## API 新建清单

### B.1 · 管理员列表（Tab 1）

`GET /api/admin/builtin-admins`（**新建**）

返回所有 builtin admin（`admins` 表全集 ∪ `users WHERE role IN ('super_admin','system_admin','org_admin')`），每条：

```ts
{ id, source: "admin_table" | "user_admin", username, role, tenantCode, overrideCount }
```

- `overrideCount` 是 `admin_permission_overrides` 聚合 COUNT（按 R5 不在前端 N+1）
- 不在 list 返 effective set（避免 100 admin × 117 key = 11700 cell）
- super_admin 行用灰色显示并禁用"编辑"按钮（与 N1 校验对齐）

### B.2 · 单 admin effective set（Tab 1 详情）

复用 Phase A 已建 [`GET /api/admin/admin-overrides/[adminId]?source=...`](../../app/api/admin/admin-overrides/%5BadminId%5D/route.ts)。

新增聚合：`GET /api/admin/admin-effective/[adminId]?source=...`（**新建**）

返回：
```ts
{
  role: "system_admin" | "org_admin",
  defaultPackKeys: string[],      // builtin_role_permissions[role]
  overrides: { permission_key, effect, reason, created_at }[],
  effective: string[],            // 默认包 ∪ grant - revoke
}
```

详情面板在前端按 KEYS_BY_RESOURCE 分块渲染（R10：按资源分块，agent 与 agent_draft 各自一栏）。

### B.3 · 角色默认包编辑（Tab 2）

`GET /api/admin/role-permissions/[role]`（**新建**）→ `{ permissionKeys: string[] }`

`PUT /api/admin/role-permissions/[role]`（**新建**）：

```ts
body = { permissionKeys: string[], confirmAffectedCount: number }
```

- 请求体带 `confirmAffectedCount`（前端弹窗时算出的"影响 N 个 admin"）
- 服务端二次核算 `admins+users WHERE role=:role AND status='active'` 的 count，与 `confirmAffectedCount` 不一致 → 412 (`PRECONDITION_FAILED`) "权限模板被并发改动 / admin 数变化，请刷新重试"
- 一致 → DELETE all + INSERT new（事务），写 audit detail 含 before/after keys diff

### B.4 · 权限审计（Tab 4）

`GET /api/admin/permission-audit`（**新建**）→ list audit_logs 过滤：

- `resource_type IN ('builtin_role_permission','admin_override','custom_role')`
- 支持 query: `actor` / `from` / `to` / `resourceType` / `pageSize` / `cursor`

只读列表；点行展开 `detail` JSON。

### B.5 · 列出可选 permission_keys（Tab 1/2 矩阵展示用）

已有 [`GET /api/admin/permission-keys`](../../app/api/admin/permission-keys/route.ts)（Phase A 扩展过）返：
- `workflow`：12 keys（WORKFLOW set，custom 通道用）
- `admin`：117 keys（ADMIN set，本 Phase 用）
- `by_resource`：分组（本 Phase Tab 1 矩阵分块用）

**不动**。

## 关键设计决策（待小B 审 / 用户拍）

### D1 · Tab 1 列表 effective 是否 inline 算？

| 选项 | 描述 |
|---|---|
| **(a)** 列表只 select admin 元数据 + override COUNT；effective set 详情 lazy load（推荐） | R5 推荐路径，避免大量计算前置 |
| (b) 列表后端 join 完整 effective set | UX 直观但慢，违 R5 |

**我倾向 (a)** —— 列表显示 `override 3 条 / role 默认包 109 keys`，点详情才算完整 effective。

### D2 · Tab 2 写入颗粒度

| 选项 | 描述 |
|---|---|
| **(a)** 一次 PUT 整组 keys for role（推荐） | 易做并发护栏（前端送 confirmAffectedCount，服务端 412 拦截）；audit detail 含完整 before/after diff |
| (b) 单条 grant / 单条 revoke API（与 Tab 1 风格一致） | 每条单独 audit；二次确认弹窗每次问"影响 N 个 admin"过烦 |

**我倾向 (a)** —— Tab 2 改默认包是高危操作（R7），整组写 + audit diff 更易事后追溯；二次确认弹窗只出一次。

### D3 · 二次确认时机

| 选项 | 描述 |
|---|---|
| **(a)** Tab 2 改默认包前必弹确认（含影响人数）；Tab 1 改 override 直接生效（个人粒度只影响 1 人，audit 即可追溯）（推荐） | 与 R7 风险对齐 |
| (b) Tab 1/2 都弹确认 | 保险但烦 |
| (c) 都不弹 | 太激进，R7 拦不住 |

**我倾向 (a)**。

### D4 · effective 矩阵渲染形态

| 选项 | 描述 |
|---|---|
| **(a)** 按 resource 分块（卡片网格），每资源一组（workflow / agent / agent_draft / kb / provider / notice / user / tenant / category / dept / team / audit）（推荐） | R10 推荐路径；agent 与 agent_draft 分开避免混淆；卡片内每 key 一个 checkbox + grant/revoke/默认 三态 chip |

**我倾向 (a)**。

### D5 · Tab 顺序

| 选项 | 描述 |
|---|---|
| **(a)** 1-个人 / 2-模板 / 3-自定义 / 4-审计（方案原顺序）（推荐） | 从精细到粗粒度，再到审计；新人易理解 |
