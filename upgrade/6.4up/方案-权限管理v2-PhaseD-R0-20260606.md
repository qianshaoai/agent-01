Phase C 是**纯路由叠加**——adapter 早在 Phase A 就绪，路由只加一行 `requireAccess` / env-gated `hasPermission`。**Phase D 不是。**

探查发现：**4 个核心 adapter 至今是 Phase A 占位 stub，直接套用 `buildTenantOwnedAdapter`，对 enforce 不可用。** 它们文件头自己写着「Phase D enforce 启用前必须重写」。

| Adapter | 现状 | enforce 打开后的真实后果 |

| [`lib/adapters/access/workflow.ts`](../../lib/adapters/access/workflow.ts) | 套 generic，`loadDetail` 跑 `select("id, tenant_code")` | `workflows` 表**无 `tenant_code` 列**（已核 migration_v2）→ PostgREST 报错 → `data=null` → `requireAccess` 返 **404 资源不存在** → builtin admin 任何 workflow 写操作全 404 |

## 2. 关键现实校正 / Findings（F0–F8）

### F0 · 4 stub adapter 重写（见 §1，本期主线）

workflow / agent / agent_draft / user 四个 adapter 必须从 stub 改成真实归属逻辑（详细规格见 §5）。

### F1 · 结构性约束保留在路由层，requireAccess 是**叠加第二闸**

合并版 §1.5 / §3.4 的硬合约：**所有路由现有 5.30up 双闸（`requireWriteAccess` 角色白名单 + `canReadRow`/`canWriteRow` tenant 归属）+ `canActOnRole` 上下级 hierarchy 全部保留**，`requireAccess` 只在其后**叠加一道**。

含义：
- kb / provider 的 tenant 归属结构性判定**仍由路由现有 `canWriteRow` 兜**，adapter 不必复刻——adapter 只补「permission_key + scope」这层 v2 判定。
- 上下级 / 归属 hierarchy **各路由机制不同**（R0.1 / 见 §2 F8 真实清单）：workflow 用 `canActOnRole`、user 用 `canManageTarget`/`canAssignRole`、agent 用 org_admin 硬判；**workflow `duplicate` 是例外——本无任何结构闸，须 D-3 新增**（不能假设旧闸已兜）。
- 即「结构性优先于 permission」（验收 #17）靠的是**保留旧闸 + 新闸 fail-closed 叠加**，不是把结构性塞进 adapter。

→ 这条决定了 adapter 重写的**最小职责边界**：只做 scope 反查 + `hasPermission` 调用，不接管 hierarchy / tenant 归属。（除非 §5 某 adapter 明确需要，见各条。）

### F2 · generic `checkCreate` 的 `.all`/`.org` 双形态 bug（Phase C R1/R3 同型，本期必修）

[`_generic.buildTenantOwnedAdapter.checkCreate`](../../lib/adapters/access/_generic.ts#L71)：

```ts
async checkCreate(actor) {
  if (!actor.tenantCode) return false;                 // ← system_admin 无 tenantCode 直接 false
  const key = `${prefix}.create.org` as PermissionKey; // ← 只查 .org，无视 .all
  return await hasPermission(actor, key, [{ scope_type: "org", scope_id: actor.tenantCode }]);
}
```

Phase C 的 notice 撞了这个，当时走 **Lane A（路由层不走 facade，自己按 finalTenantCode 分支 + `.all` OR `.org`）** 临时绕过，并在 R1 注里写明「未来 Phase D/E 接 kb/provider 时若发现同类双形态，再统一抽 helper（YAGNI）」。

本期 **kb create**（system_admin 在 seed 里有 `kb.create.*`）会再次撞同一 bug：system_admin（`tenant_code=null`）建全局 KB 被误拒。

**到点了**——本期建议统一修 generic（决策 D2，§9）：`checkCreate` 改成与 HC2/R3 同款 `.all` 兜底 OR `.org` scope 模式，一处修复，notice 也能从 Lane A 收回 facade（可选）。

### F3 · workflow 是**双通道**资源，builtin 接入 requireAccess 必须不碰 custom_admin 通道

`workflows/*` 与 `workflow-steps/*` 已经在 6.4up 用 `getAdminAccessPayload()` + `hasPermission()` 服务 **custom_admin**（requirePermission 语义）。本期要接的是 **builtin admin 路径的 requireAccess**。

硬约束（合并版 §3.3 第 5 条）：
- **custom_admin 通道完全不受 v2 影响**——`requirePermission()` 只读 v50 三表，`requireAccess` 路径只对 `actor.source ∈ {admin_table, user_admin}` 生效。
- 设计：在 builtin 分支（`!isCustomAdminPayload`）里才插 `requireAccess(actor, "workflow", action, {...})`；custom 分支保持原样。**不能**在两个分支共用入口处插（否则 custom_admin 被 v2 双判）。
- workflow 的 enable / duplicate / delete 是 **ADMIN 通道独占 key**（`WORKFLOW_V2_NEW_KEYS`，custom 通道无）→ 这三个动作只对 builtin admin 接 requireAccess，custom_admin 本就不开放（6.4up R1.2 决策）。

### F4 · user PATCH 是**多 sub-action 单入口**，requireAccess 要按动作分发（验收 #18）

`PATCH /api/admin/users/[id]` 一个 handler 改 role / dept_id / team_id / tenant / password / enabled 多种字段。USER_KEYS 把它们拆成 18 个独立 key（`user.role.update.*` / `user.department.assign.*` / `user.team.assign.*` / `user.tenant.transfer.*` / `user.password.reset.*` / `user.enable.*` / `user.delete.*`）。

验收 #18 要求：grant `user.department.assign.org` 但不 grant `user.role.update.org` → 改 dept 成功、改 role 403。

→ 路由层要**按 body 实际改了哪些字段，逐 sub-action 调 requireAccess**（任一不过即 403）。user adapter 的 `checkWrite(actor, row, action)` 里 `action` 取值要支持 `role.update` / `department.assign` / … 这些复合 sub-action，并映射到对应 key。详见 §6。

### F5 · setting / permission **无 key、不接 requireAccess**，靠 super-only 硬锁

`ADMIN_PERMISSION_KEYS` 里**没有** `setting.*` / `permission.*`（admin.ts 注释明说：super_admin 硬全权由公式第 1 行覆盖；验收 #7 + R2「super 不能 revoke 自己 permission.*」）。

→ settings 路由、admin-overrides / custom-roles / permission-keys 路由**维持现有 `admin.role !== "super_admin"` 硬锁**，本期**不接 requireAccess**。F 收口只做一件事：admin-layout 里这两个菜单**硬锁 `SUPER_ONLY`**（现状已是，见 §8 确认不回退）。

### F6 · dept / team 有 key + adapter + seed，但从未进 enforce 排期 → 决策点

合并版 §3.3 的 enforce 顺序是 `notice → category → user → agent → workflow → kb → provider → tenant`，**没有 dept / team**；§4 的 D/E 资源清单也没有。但 `DEPT_KEYS`(8) / `TEAM_KEYS`(8) 已在 `ADMIN_PERMISSION_KEYS`、已注册 adapter、v52 seed 已含。

→ 「全收口」要不要把 dept / team 也开 enforce？决策 D5（§9）。倾向：**接**（它们是标准 tenant-owned，generic 可用，边际成本低；不接则这 16 个 seed key 永远不被 enforce 验证，留半成品）。

### F7 · agent 资源：key 缺 create，但路由**有 POST 创建入口**（R0.1 修正）

`AGENT_KEYS` 只有 `read / basic.update / reindex / enable / delete`，scope 仅 `.org`/`.all`（reindex 仅 `.all`），**没有 `agent.create.*`**。

但 [`agents/route.ts:125`](../../app/api/admin/agents/route.ts#L125) **存在 `POST` 创建 agent**（现状 `requireAdmin()` + `admin.role==='org_admin'` 硬拒；super/system 可建，平台级、建时不写归属，可见性后续由 `resource_permissions` 单独分配）。R0 误写"agent 无 POST"。

→ 「全收口」必须决定这个创建入口怎么纳管：**决策 D9**（§9）—— (a) 新增 `agent.create.{org,all}` key + seed 复刻现状，(b) 保留 legacy role-only 例外、agent POST 不接 v2。其余动作（`basic.update` / `reindex(.all)` / `enable` / `delete`）按 §5.2；`agents/[id] PATCH`（org_admin 现状被硬拒）enforce 后是否经 `agent.basic.update.org` 放权见决策 D6。

### F8 · `canActOnRole` 真实调用点 + duplicate 无结构闸（R0.1 修正）

`canActOnRole`（5.11up 上下级 snapshot 比较）的**真实调用点只有 3 个 workflow 文件**（已 grep 核实）：[workflows/[id]/route.ts:60](../../app/api/admin/workflows/%5Bid%5D/route.ts#L60)、[workflows/[id]/steps/route.ts:117,202](../../app/api/admin/workflows/%5Bid%5D/steps/route.ts#L117)、[workflow-steps/[id]/route.ts:54](../../app/api/admin/workflow-steps/%5Bid%5D/route.ts#L54)。承担**结构性 hierarchy** 约束，**v2 公式 `hasPermission` 并不编码它**。

R0 误写"duplicate / agent 路由也在用"——**都没有**：
- [`workflows/[id]/duplicate/route.ts`](../../app/api/admin/workflows/%5Bid%5D/duplicate/route.ts) 只有 `requireAdmin()`，**零 hierarchy 闸**（且第 28 行 `admin.role ?? "super_admin"`）。这是**现存潜在越权**：org_admin 现在能复制任意 workflow（含 super 建的）。D-3 接 `workflow.duplicate.*` 时**必须新增** source workflow 的结构性 + scope 闸，不能"假设旧闸已兜"。
- agent 路由用 `admin.role==='org_admin'` 直接硬判 / scoped 逻辑，不走 canActOnRole；user 路由用 `canManageTarget`/`canAssignRole`。

合并版 §4 Phase F 写「废 admin-permissions.ts canActOnRole」——直接删会**丢上下级语义**。→ 决策 D7（§9）。倾向：**本期不删，保留为结构性第一闸**；F 收口只做「全仓 `?? "super_admin"` 二扫」+「确认 canActOnRole 与 requireAccess 并存且 fail-closed」。

## 3.5 资源三命名空间权威映射表（R0.1 新增 · 小B 要求）

⚠️ 本系统存在**三个独立命名空间**，写错任意一个都会静默 no-op 或 500：
1. **resourceKind** = `registerAccessAdapter` 注册键 = **`PERMISSION_V2_ENFORCE_RESOURCES` env token** = `requireAccess(actor, kind, ...)` 第二参（[isResourceEnforced](../../lib/access-facade.ts#L74) 按它匹配）。
2. **permissionPrefix** = permission_key 前缀 = `KEYS_BY_RESOURCE` 键（[admin.ts:185](../../lib/permission-keys/admin.ts#L185)）。
3. **route path** = `app/api/admin/...` 目录名。

| 资源 | resourceKind ＝env token | permissionPrefix ＝key 前缀 | adapter | 路由 | 本期 enforce |
|---|---|---|---|---|---|
| 工作流 | `workflow` | `workflow` | stub→重写（resource_permissions） | `workflows` / `workflow-steps` | D-3 |
| 智能体 | `agent` | `agent` | stub→重写（resource_permissions） | `agents` | D-2 |
| 草稿 | `agent_draft` | `agent_draft` | stub→重写（created_by→users） | `agent-drafts` | D-2 |
| 用户 | `user` | `user` | stub→重写（sub-action） | `users` | D-1 |
| 知识库 | **`knowledge_base`** | **`kb`** | generic（tenant_code） | `knowledge-bases` | D-5 |
| API 管理 | **`model_provider`** | **`provider`** | generic（tenant_code） | `model-providers` | D-5 |
| 租户 | `tenant` | `tenant` | platform（.all） | `tenants` | D-4 |
| 部门 | `dept` | `dept` | generic | `departments` | D-4（决策 D5）|
| 小组 | `team` | `team` | generic | `teams` | D-4（决策 D5）|
| 公告 | `notice` | `notice` | generic | `notices` | ✅ Phase C |
| 分类 | `category` | `category` | platform | `categories` | ✅ Phase C |
| 审计 | `audit` | `audit` | generic | `audit-logs`（+analytics 复用） | ✅ Phase C |
| 设置 | `setting` | （无 key） | super-only 自定义 | `settings` | 不接（F5）|
| 权限 | （无 adapter） | （无 key） | — | `admin-overrides` / `custom-roles` / `permission-keys` | 不接（F5）|

> **核心坑**：只有 **`knowledge_base`(kb) 与 `model_provider`(provider)** 两个 resourceKind ≠ permissionPrefix；env CSV / `requireAccess` 第二参**必须用 resourceKind 列**（`knowledge_base,model_provider`），用 `kb,provider` 会让 `isResourceEnforced` 返 false（静默不 enforce）或 `getAccessAdapter` 撞空（500）。除这两个外，已进入 enforce 的业务资源 resourceKind 与 permissionPrefix 基本一致；`setting` / `permission` **不进入 env**（setting 是 super-only 自定义 adapter、permission 无 adapter）。

## 5. Adapter 重写规格（D-0 主线）

> 原则（F1）：adapter 只补「scope 反查 + `hasPermission`」这一层；**结构性 hierarchy / tenant 归属仍由路由旧闸兜**。所以以下 adapter 重写聚焦"算出该资源的 `ResourceScope[]`，喂给 `hasPermission`"。

### 5.1 workflow adapter

```
loadDetail(id):
  反查 resource_permissions WHERE resource_type='workflow' AND resource_id=id
  → 返回 { id, scopes: ResourceScope[] }（该 workflow 现有的所有 scope 行）
  注意：返回非空对象（即使 scopes=[]），避免 null→404 误判（与"workflow 不存在"区分：
       先 SELECT workflows.id 确认存在，再取 scopes）
checkRead(actor, row):  hasPermission(actor, "workflow.read.<suffix>", row.scopes) —— 任一 suffix 命中即可（OR over 持有的 read.*）
checkWrite(actor, row, action):
  action ∈ {update, enable, duplicate, delete} → key=`workflow.<action>.<suffix>`
  row.scopes 必须**全部**落在 actor 该 key 的范围内（hasPermission 已对多 scope 做 AND）
checkCreate(actor): 按"想建的 scope"——但 workflow create 的目标 scope 来自 body，
  建议走 Lane A（路由层按 body 选 suffix 调 hasPermission），不走 adapter.checkCreate
resolveCreateOwnership: 不在 adapter 注入；workflow 创建后写 resource_permissions 的逻辑保留在路由（现有 6.4up 逻辑）
```

> 关键：workflow 的 scope 来源是 `resource_permissions`，**不是** `tenant_code`。这正是 stub 套 generic 会 404 的根因。

### 5.2 agent adapter（R0.1 改写 · resource_permissions 反查）

```
loadDetail(id):
  SELECT agents.id 确认存在
  ★ 反查 resource_permissions WHERE resource_type='agent' AND resource_id=id
    → 返回 { id, scopes: ResourceScope[] }（org scope_id=tenant_code）
  R0.1 修正：归属源是 resource_permissions（与 agents/route.ts GET 列表口径同源），
    **不是** tenant_agents；agent 与 workflow 同型，不能套 generic tenant_code（agents 表无此列 → 否则 404）
checkRead/checkWrite(actor, row, action):
  hasPermission(actor, `agent.<action>.<suffix>`, row.scopes)
  AGENT_KEYS 只有 .org/.all；若 resource_permissions 含 dept/team scope 行 →
    granularity 不对齐，按 isScopeWithinOrg 收敛到 org（或 D-2 确认 agent 是否只用 org scope）
  action: read / basic.update / reindex(.all only) / enable / delete
  特例：reindex 只有 .all → 非超管 reindex 必须持 agent.reindex.all
agent POST 创建：见 §2 F7 + 决策 D9（无 create key，单独拍）
D-2 附加：确认 publish / agents/[id] PATCH 写可见性也走 resource_permissions（不再写 tenant_agents 造成分叉）
```

> 决策 D6：org_admin 对"分配本组织 + 同时分配别组织"的 agent（scopes 跨多组织）能否 update？倾向：**要求所有 org scope 全 ∈ 本组织才放行**（最严，避免跨组织副作用），否则 403。
