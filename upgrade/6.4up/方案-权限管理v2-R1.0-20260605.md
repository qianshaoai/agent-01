## 1. 核心模型 · 公式不变，但 keys 空间拆分

### 1.1 三层混合（R0 D 路线，不变）

```
hasPermission(actor, key, targetScopes):
  if actor.builtinRole == 'super_admin': return true
  if hasStructuralDeny(actor, key, targetScopes): return false
  finalKeys = roleDefaultPack(actor.builtinRole)
            ∪ adminGrantOverride(actor.actorId)
            − adminRevokeOverride(actor.actorId)
  return finalKeys.has(key) && scopeOk(actor, key, targetScopes)
```

**注意 R1 移除了 customRolePack(actor.customRoles)**——custom admin 走完全独立通道（见 §1.2）。

### 1.2 Key 空间拆分（P0-1 收口）

```ts
// lib/permission-keys/workflow.ts
export const WORKFLOW_PERMISSION_KEYS = [
  "workflow.read.team", ..., "workflow.update.all"  // 6.4up 原 12 个
] as const;

// lib/permission-keys/admin.ts
export const ADMIN_PERMISSION_KEYS = [
  // ~120-150 keys，覆盖 12 资源 × 拆分 sub-action × 各自 scope（见 §1.3）
] as const;

// lib/permission-keys/index.ts
export const PERMISSION_KEYS = [
  ...WORKFLOW_PERMISSION_KEYS,
  ...ADMIN_PERMISSION_KEYS,
] as const;  // 仅 type union / list 暴露用，不参与任何写入校验
```

**写入校验严格按 set 分流**：
- `custom-roles` POST/PATCH（6.4up 路径）→ 入参严校 `WORKFLOW_PERMISSION_KEYS`
- `admin-overrides` POST/PATCH（v2 新路径）→ 入参严校 `ADMIN_PERMISSION_KEYS`
- 两类 set 可有交集（如 `workflow.read.org` 两边都有），按调用方决定语义

**双通道隔离硬规则**：
- `requireAdmin()` builtin 通道不读 `user_custom_roles`（避免 custom workflow keys 误混入 ADMIN finalKeys）
- `requirePermission()` custom 通道不读 v52 两张新表（custom admin 完全不受 v2 影响）
- **role=user 晋升 builtin admin 时强制清 user_custom_roles**（不留双通道纠缠）

### 1.3 Sub-action 拆分（P1-1 收口）

R0 动作集 `read/create/update/delete/enable/test` 对 users / agents / workflows 太粗。R1 引入 sub-action：

**user（替代 R0 的 user.update.* 一个 key）**
```
user.basic.update.*              // nickname / profile
user.role.update.*               // 改 role（敏感但不加额外锁，见用户决策）
user.tenant.transfer.*           // 5.6up RPC change_user_tenant
user.department.assign.*         // 改 dept_id
user.team.assign.*               // 改 team_id
user.password.reset.*            // 重置密码
user.enable.* / user.delete.*    // 启停 / 软删
```

**agent**
```
agent.basic.update.*             // 名称 / 描述等基础字段
agent.publish.*                  // 草稿 → published
agent.duplicate.*                // 复制
agent.reindex.*                  // 触发重新索引 / 重新摄取
agent.enable.* / agent.delete.*
```

**workflow**
```
workflow.read.* / create.* / update.*  // 6.4up 原 12 keys（custom 通道独占）
workflow.enable.*                       // 启停
workflow.duplicate.*
workflow.delete.*
```

其他资源（kb / model_provider / notice / tenant / category / audit / setting / permission）保持 R0 动作集。

**Keys 总数修正**：R0 80~100 → R1 **120~150**。

### 1.4 Scope 分级（R0 不变）

| 资源 | scope 集 |
|---|---|
| workflow / agent | team / dept / org / all |
| kb / provider / notice / user | org / all |
| tenant / category / setting / permission / audit | all |

### 1.5 hasPermission 与 scoped-access 协同 — Resource Adapter（P0-3 收口）

R0 设的"统一 facade 内部调 canWriteRow / canReadRow"是错的——`scoped-access.ts` 只懂 `tenant_code` 资源。R1 改用**资源适配器模式**：

```ts
// lib/access-facade.ts
export interface ResourceAccessAdapter<TRow = unknown> {
  resourceKind: string;
  // list filter：返回 query modifier（如 listScopeFilter 字符串、或自定义 SQL where）
  listFilter(actor: PermissionActor): QueryModifier | null;
  // load detail：用 service_role 拉行（adapter 知道自己的 table 名 + select）
  loadDetail(id: string): Promise<TRow | null>;
  // 读权限判定（结构性 + permission）
  checkRead(actor: PermissionActor, row: TRow): boolean;
  // 写权限判定（结构性 + permission + sub-action）
  checkWrite(actor: PermissionActor, row: TRow, action: string): boolean;
  // 创建时的 ownership 注入（写入 patch 前调）
  resolveCreateOwnership(actor: PermissionActor, payload: Partial<TRow>): Partial<TRow>;
}

// 路由层调用模板
export async function requireAccess(
  actor: PermissionActor,
  resourceKind: string,
  action: 'read' | 'create' | 'update' | 'delete' | string,
  row?: unknown,
): Promise<Response | null>;
```

**各 resource adapter 落到 `lib/adapters/access/<kind>.ts`**：

| Adapter 文件 | 内部走 | 复用 |
|---|---|---|
| `model-provider.ts` | tenant_code ownership | 直调 `lib/scoped-access.ts` 五件套 |
| `knowledge-base.ts` | tenant_code ownership | 直调 `lib/scoped-access.ts` 五件套 |
| `workflow.ts` | resource_permissions 反查 | 已有 6.4up `getResourceTenantCode("workflow", id)` |
| `agent.ts` | tenant_agents + visibility_config | 已有 5.19up `app/api/admin/agents/route.ts` 逻辑抽出 |
| `user.ts` | users.tenant_code + dept/team 上下级 | `lib/admin-permissions.ts canActOnRole` |
| `tenant.ts` | 平台级（all scope only） | 无 |
| `category.ts` / `notice.ts` / etc. | 各自规则 | — |

**调用模板**（路由层）：
```ts
// 1. requireAdmin（已有）
const admin = await requireAdmin();
if (admin instanceof Response) return admin;

// 2. 构造 actor（已有 buildPermissionActor）
const actor = await buildPermissionActor(admin);

// 3. 角色白名单（保留 5.30up 双闸第一道——避免 system_admin 误进 API 管理写路径）
const gate = requireWriteAccess(admin, RESOURCE_WRITE_ROLES);
if (gate) return gate;

// 4. load row（adapter 提供）
const row = await adapter.loadDetail(id);
if (!row) return apiError("...", "NOT_FOUND");

// 5. 新增 R1 闸：access facade 综合判定（结构性 + permission + scope）
const accessErr = await requireAccess(actor, "model_provider", "update", row);
if (accessErr) return accessErr;

// 6. 业务逻辑
```

**绝对不允许**路由层直接 import `hasPermission`——ESLint custom rule 强制（见 R3 风险）。

## 2. DB · migration_v52_permission_v2.sql（R0 schema 不变 + seed 改矩阵驱动）

### 2.1 表 schema（R0 不变）

```sql
CREATE TABLE IF NOT EXISTS builtin_role_permissions (
  role           TEXT NOT NULL CHECK (role IN ('system_admin','org_admin')),
  permission_key TEXT NOT NULL,
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_by     UUID,
  PRIMARY KEY (role, permission_key)
);
CREATE INDEX idx_brp_role ON builtin_role_permissions(role);

CREATE TABLE IF NOT EXISTS admin_permission_overrides (
  admin_id       UUID NOT NULL,
  admin_source   TEXT NOT NULL CHECK (admin_source IN ('admin_table','user_admin')),
  permission_key TEXT NOT NULL,
  effect         TEXT NOT NULL CHECK (effect IN ('grant','revoke')),
  reason         TEXT,
  created_by     UUID NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (admin_id, permission_key)
);
CREATE INDEX idx_apo_admin ON admin_permission_overrides(admin_id);
```
