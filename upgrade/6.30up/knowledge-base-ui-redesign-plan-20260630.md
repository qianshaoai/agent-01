# 6.30up 知识库管理界面优化方案

## 结论

可行性高，建议推进。

这张原型不是在重新设计知识库底层能力，而是在把现有的「知识库列表页 + 知识库详情页」合并成一个更高效的管理工作台。当前代码已经具备核心数据与操作能力：知识库列表、文档上传、异步索引状态、分段数、字数、重建、删除、启停、编辑、智能体引用反查、权限灰显与归属控制。因此第一期不需要数据库大改，也不需要改 RAG 检索链路，主要是前端信息架构重组，配合少量 API 返回字段和分页优化。

推荐路线：先做 UI 工作台 MVP，再补批量操作与分页。不要在本轮混入 embedding、长记忆、召回策略等算法改造。

## 原型拆解

原型包含三层结构：

1. 后台全局侧边栏
   - 仍沿用现有 `AdminLayout`。
   - 当前「知识库管理」菜单已存在，不需要重做导航体系。

2. 知识库二级侧栏
   - 搜索知识库。
   - 新建知识库。
   - 知识库列表项显示名称、文档数、归属徽章。
   - 选中态清晰，适合频繁切换不同知识库。

3. 右侧详情工作区
   - 顶部知识库信息卡：名称、归属、描述、编辑、停用、删除。
   - 引用摘要：被几个智能体引用，支持查看详情。
   - 文档表：文件名、上传时间、分段数、字数、处理状态、重建、删除。
   - 上传文档按钮常驻在文档区右上角。
   - 底部分页与每页条数。

## 现有实现对照

### 已具备能力

现有页面：

- `app/admin/knowledge-bases/page.tsx`
  - 知识库列表。
  - 新建知识库。
  - 文档数量徽章。
  - 归属徽章：平台公共、本组织、指定组织。

- `app/admin/knowledge-bases/[id]/page.tsx`
  - 知识库详情。
  - 编辑名称/描述。
  - 启用/停用。
  - 删除知识库。
  - 上传文档。
  - 文档状态轮询。
  - 文档重建索引。
  - 文档删除。
  - 智能体引用反查。
  - 根据权限与归属灰显按钮。

现有 API：

- `GET /api/admin/knowledge-bases`
  - 返回知识库列表和 `document_count`。
  - 已做权限过滤与归属过滤。

- `POST /api/admin/knowledge-bases`
  - 新建知识库。
  - 写入 `tenant_code`、`created_by_role`、审计日志。

- `GET /api/admin/knowledge-bases/[id]`
  - 返回知识库详情、文档列表、引用智能体信息或引用数量。

- `PATCH /api/admin/knowledge-bases/[id]`
  - 更新名称、描述、状态、归属。

- `DELETE /api/admin/knowledge-bases/[id]`
  - 删除知识库，且会阻止删除仍被引用的知识库。

- `POST /api/admin/knowledge-bases/[id]/documents`
  - 上传文档并异步索引。
  - 支持 `pdf / doc / docx / txt / md / csv / xls / xlsx / pptx`。

- `POST /api/admin/knowledge-bases/[id]/documents/[docId]`
  - 重建索引。

- `DELETE /api/admin/knowledge-bases/[id]/documents/[docId]`
  - 删除文档。

现有数据字段：

- `knowledge_bases`
  - `name`
  - `description`
  - `status`
  - `tenant_code`
  - `created_by_role`
  - `embedding_model`

- `kb_documents`
  - `filename`
  - `file_type`
  - `status`
  - `chunk_count`
  - `total_chunks`
  - `char_count`
  - `error_msg`
  - `created_at`

- `agent_knowledge_bases`
  - 用于反查被哪些智能体引用。

### 与原型的差距

1. 当前是两页跳转，原型是单屏工作台。
2. 当前知识库列表是卡片网格，原型是左侧紧凑列表。
3. 当前文档列表是普通列表，原型是表格。
4. 当前没有文档分页。
5. 当前没有勾选框和批量操作。
6. 当前引用详情只是一行文字，没有独立详情入口。
7. 当前视觉上偏首页卡片风格，原型更像后台管理工具，信息密度更高。

## 方案目标

### 本期目标

把知识库管理从「卡片入口 + 详情页」升级为「左侧知识库列表 + 右侧详情工作台」。

用户应能在一个页面完成：

- 快速搜索知识库。
- 新建知识库。
- 切换知识库。
- 查看知识库基础信息。
- 编辑/停用/删除知识库。
- 查看引用情况。
- 上传文档。
- 查看文档索引状态。
- 重建或删除单个文档。

### 非目标

本期不做：

- 不改知识库召回算法。
- 不改 embedding 模型策略。
- 不改长记忆池、rerank、prompt 注入逻辑。
- 不改知识库和智能体绑定规则。
- 不改文件解析能力边界。
- 不新增复杂批量导入队列。

## 推荐实现路径

### 路由策略

推荐保留现有路由，同时抽一个共享工作台组件：

- 新建组件：`components/admin/knowledge-base-workbench.tsx`
- `/admin/knowledge-bases`
  - 渲染工作台。
  - 默认选中第一个知识库。
  - 支持搜索和新建。

- `/admin/knowledge-bases/[id]`
  - 也渲染同一个工作台。
  - 以 URL 中的 `id` 作为初始选中知识库。
  - 保留现有深链兼容，避免旧链接失效。

这样既能实现原型的单屏体验，又不会破坏现有入口。

### 前端结构

建议拆成以下组件：

- `KnowledgeBaseWorkbench`
  - 管理整体状态。
  - 负责加载知识库列表、选中知识库、加载详情。

- `KbSidebar`
  - 搜索框。
  - 新建按钮。
  - 知识库列表。
  - 空状态。
  - loading 骨架。

- `KbHeaderPanel`
  - 知识库图标。
  - 名称、归属、描述。
  - 编辑、启停、删除。
  - 引用摘要。

- `KbReferenceSummary`
  - super/system 显示引用智能体名称。
  - org/custom admin 仅显示引用数量，遵守现有防泄漏规则。
  - 「查看详情」可以第一期做成展开区，后续再做抽屉。

- `KbDocumentsTable`
  - 文档表格。
  - 状态徽章。
  - 分段数、字数、上传时间。
  - 重建、删除。
  - indexing/pending 时保留现有 3 秒静默轮询。

- `KbEditModal`
  - 复用现有编辑字段。

- `KbCreateModal`
  - 复用现有新建逻辑。

第一期也可以少拆组件，先在 `app/admin/knowledge-bases/page.tsx` 内完成，但不推荐。知识库详情逻辑已经较长，继续堆在单文件里会增加后续维护成本。

## API 调整建议

### 第一阶段：尽量不改 API

MVP 可直接复用：

- 进入页面：调用 `GET /api/admin/knowledge-bases`
- 选中知识库：调用 `GET /api/admin/knowledge-bases/[id]`
- 上传、编辑、停用、删除、重建：复用现有接口

这能最快落地原型主体。

### 第二阶段：补分页和轻量统计

当文档数量超过几十个后，建议调整：

1. `GET /api/admin/knowledge-bases/[id]/documents?page=1&pageSize=10`
   - 返回：
     - `data`
     - `pagination`

2. `GET /api/admin/knowledge-bases/[id]`
   - 保持返回知识库详情与引用信息。
   - 文档列表可只返回第一页，或不返回文档，改由 documents 接口负责。

3. `GET /api/admin/knowledge-bases`
   - 现在通过查询所有 `kb_documents.kb_id` 计算数量，小规模没问题。
   - 如果数据量上来，改成 SQL 聚合或 RPC，避免拉全量文档行计数。

### 第三阶段：批量操作

原型里有 checkbox。第一期可以只展示选择框但不做批量按钮，也可以暂不展示 checkbox。若要完整支持：

- 新增批量删除：
  - `POST /api/admin/knowledge-bases/[id]/documents/bulk-delete`

- 新增批量重建：
  - `POST /api/admin/knowledge-bases/[id]/documents/bulk-reindex`

注意批量重建必须避免对 `pending/indexing` 文档重复入队。

## 权限与安全要求

必须保留现有规则，不得因为 UI 合并而放松：

1. 列表可见性
   - super/system 可按现有规则看全局范围。
   - org/custom admin 只看平台公共和本组织范围。

2. 写操作灰显
   - 编辑、启停、删除、上传、重建、删除文档都必须继续使用现有 `useAdminPermissions` 和 ownership 判断。

3. 引用信息防泄漏
   - super/system 可显示引用智能体名称。
   - org/custom admin 只显示引用数量，不显示跨组织智能体名称。

4. 删除保护
   - 知识库被智能体或草稿引用时，仍由后端阻止删除。

5. 停用语义
   - 停用是「不参与检索」，不是删除，也不是解绑。
   - UI 文案必须继续说明这一点，避免误操作。

## 视觉设计落地建议

原型整体方向适合后台管理，但需要结合当前系统做几处收敛：

1. 降低装饰性
   - 当前知识库页有较多渐变和光晕。
   - 原型更适合工具型后台，应减少大面积装饰，提升表格可读性。

2. 采用三列布局
   - 左：现有 AdminLayout。
   - 中：知识库二级侧栏，宽度建议 260px 到 300px。
   - 右：详情区，自适应。

3. 表格密度
   - 文档表保留 72px 左右行高。
   - 文件名支持单行省略。
   - 上传时间作为二级信息。
   - 状态用小徽章，不用大面积色块。

4. 移动端策略
   - 管理后台主要面向桌面。
   - 低于 1024px 时可让二级侧栏折叠成顶部选择器，不强求三列并排。

5. 文案一致性
   - 「分段数」对应 `chunk_count`。
   - 「字数」对应 `char_count`。
   - 「已完成」对应 `done`。
   - 「索引中」对应 `indexing`。
   - 「等待索引」对应 `pending`。
   - 「失败」对应 `failed`。

## 分阶段实施

### Phase 1：工作台 MVP

目标：完成原型主体，不做批量操作和后端分页。

任务：

- 新增 `KnowledgeBaseWorkbench`。
- 列表页改为工作台布局。
- 详情页复用工作台并传入初始 `kbId`。
- 左侧知识库列表支持搜索。
- 选中知识库后加载详情。
- 顶部信息卡支持编辑、启停、删除。
- 文档区改成表格视图。
- 上传、重建、删除沿用现有接口。
- pending/indexing 状态沿用现有静默轮询。
- 保留原有错误提示、成功提示。
- 保留全部权限灰显。

验收：

- `/admin/knowledge-bases` 能展示左侧列表和右侧默认详情。
- `/admin/knowledge-bases/[id]` 仍可打开指定知识库。
- 搜索知识库不触发后端请求，先本地过滤即可。
- 上传文档后表格自动出现 pending/indexing/done 状态变化。
- 无写权限账号看得到内容，但写操作按钮灰显。

### Phase 2：文档分页与表格增强

目标：让大量文档场景可用。

任务：

- 文档表增加前端分页。
- 每页条数支持 10 / 20 / 50。
- 先使用当前全量文档数据做 client pagination。
- 如果真实数据量大，再切到服务端分页。
- 表头显示分段数说明 tooltip。
- 文档失败时显示失败原因 tooltip 或展开。

验收：

- 4 个文档、40 个文档、400 个文档的 UI 都不撑爆页面。
- 分页切换不丢失轮询状态。
- 索引中行不会因为轮询导致整页闪烁。

### Phase 3：引用详情与批量操作

目标：补齐原型里的「查看详情」和 checkbox 预期。

任务：

- 引用详情做展开面板或右侧抽屉。
- super/system 显示智能体名称、编号、是否启用。
- org/custom admin 仍只显示数量与权限提示。
- 支持勾选文档。
- 支持批量重建。
- 支持批量删除。

验收：

- 批量重建不会重复提交 indexing/pending 文档。
- 批量删除有二次确认。
- 删除后计数、分页、空状态正确更新。

## 风险点

1. 现有详情页逻辑较长
   - 风险：直接在原文件里改会越来越难维护。
   - 建议：抽工作台组件和子组件。

2. org/custom admin 引用信息不能照搬原型
   - 风险：原型展示引用智能体名称，但当前权限模型要求防止跨组织名称泄漏。
   - 建议：按角色区分显示，保留现有后端返回策略。

3. 文档分页可能影响轮询
   - 风险：只轮询当前页会让非当前页状态不更新；全量轮询又可能浪费。
   - 建议：Phase 1 继续全量详情轮询；Phase 2 服务端分页时只轮询当前页，同时侧栏文档数不作为索引完成状态依据。

4. 搜索和选中态要处理空结果
   - 风险：搜索后当前选中的知识库不在结果中，用户会迷惑。
   - 建议：右侧详情保持不变，左侧显示「当前结果中无此知识库」或自动选中搜索结果第一项，需产品口径统一。推荐保持右侧详情不变。

5. 视觉不能完全照抄
   - 风险：原型宽屏效果好，但在 1366 宽度下表格列可能挤压。
   - 建议：优先保证 1366 桌面可用，列宽用 `minmax` / 固定操作列 / 文件名弹性列。

## 推荐开发顺序

1. 抽 `KnowledgeBaseWorkbench`，先复用现有 load/create/edit/delete/upload/reindex 函数。
2. 做二级侧栏：搜索、新建、列表项、选中态、归属徽章。
3. 做右侧顶部信息卡：标题、描述、归属、按钮、引用摘要。
4. 把文档列表改表格，不做分页。
5. 接回上传、重建、删除、轮询。
6. 接回 `/admin/knowledge-bases/[id]` 深链。
7. 跑 `npm run ci:typecheck`。
8. 本地打开 `/admin/knowledge-bases`，用有写权限和无写权限账号各验一遍。
9. 再决定是否进入 Phase 2 分页。

## 验收清单

- 知识库列表加载正常。
- 新建知识库正常。
- 搜索知识库正常。
- 切换知识库正常。
- 详情区不会显示上一条知识库的脏数据。
- 编辑知识库正常。
- 停用和启用正常。
- 删除有引用的知识库会被后端阻止并显示原因。
- 上传文档正常。
- 文档 pending/indexing/done/failed 状态显示正确。
- 文档重建正常。
- 文档删除正常。
- 文档字数和分段数显示正确。
- super/system 与 org/custom admin 的引用信息展示符合权限边界。
- 没有写权限时所有写操作按钮灰显。
- 1366 宽度下表格不横向撑爆。
- `npm run ci:typecheck` 通过。

## 最终建议

推进，但按「UI 工作台重组」而不是「知识库系统重构」推进。

第一期不需要新表、不需要改检索、不需要碰 embedding，也不需要改聊天侧 KB 注入逻辑。只要把现有列表、详情、文档管理、权限控制组合成原型里的单屏工作台，投入产出比很高，线上风险也可控。
