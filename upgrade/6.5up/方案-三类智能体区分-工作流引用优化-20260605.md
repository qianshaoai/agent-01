## R1 收口 · 数据通路 + 搜索字段

### Finding 1 收口 · 推荐路线 A · 新建轻量 picker 接口

**方案对比**：

| 路线 | 改动 | 适用规模 | 选择 |
|---|---|---|---|
| A · 新建 `/api/admin/agents/picker` 极简全量接口（hard cap 2000） | 新 1 个接口 ~40 行；前端 fetch 改 1 行；返回 `{ data, totalCount, capped }` 让 UI 提示截断 | < 2000 个 agent | **✓ 推荐** |
| B · 全局 `MAX_PAGE_SIZE` 100 → 1000 | 1 行 env / config 改动；前端 fetch 改 `pageSize=1000` | 同上 | × 副作用：所有 `/api/admin/*` 列表都受影响（org_admin 拉用户列表也会变大包） |
| C · 服务端搜索接口 `/api/admin/agents?q=foo`（PostgreSQL ILIKE 多字段 OR）| 后端 ~50 行；前端搜索从 client filter 改成 debounced server fetch | > 2000 个 agent | 超过 2000 时切这条 |

**上线门槛**：路线 A 只承诺解决“几百到 2000 以内”的当前痛点。实施后若接口返回 `capped=true`，说明真实 agent 数已超过 2000，客户端搜索只能搜已返回的前 2000 条，不能搜到被截断的尾部数据；此时应把路线 C 作为下一轮必做，而不是把 `capped=true` 当成完整可用状态。

**路线 A 接口规格**：

```
GET /api/admin/agents/picker
返回 {
  data: Array<{
    id: string;
    agent_code: string;
    name: string;
    description: string;
    platform: string;
    agent_type: "chat" | "external";
    external_url: string;
    published_from_draft_id: string | null;
  }>;
  totalCount: number;     // DB 真实总数
  capped: boolean;        // totalCount > 2000 时为 true
}
```

实施细节：
- 服务端复用 `requireAdmin` + 现有 RBAC（admin 三类全可见，与 `/api/admin/agents` 一致）
- `select` 极简字段：去掉 `api_key_enc` / `api_endpoint` / `model_params` / `provider_id` —— picker 不需要，减传输负载
- 不查 `workflow_steps` 反向引用 / `resource_permissions` / `agent_categories` / `categories` —— 这些只在列表管理页用，picker 用不到
- `order by name asc`（picker 场景按名字排比按创建时间更顺手）
- Hard cap：`limit(2000)` + 同时跑 `select count(*)` 拿真实总数，前端比较 `data.length < totalCount` 判定截断
- 不写 audit log（读操作 + 高频）
- 路径独立 `/api/admin/agents/picker`，不与现有 `/api/admin/agents?mode=picker` 路径耦合（更清晰、更易演进到方案 C）

前端工作流页改动：
- [`workflows/page.tsx:213`](../../app/admin/workflows/page.tsx#L213) `fetch("/api/admin/agents?pageSize=100")` → `fetch("/api/admin/agents/picker")`
- 数据 shape：picker 返回 `{ data, totalCount, capped }`，需要把 `.then(d => d.data ?? d)` 适配为 `.then(d => ({ list: d.data ?? [], capped: !!d.capped, totalCount: d.totalCount ?? 0 }))`
- 新增 state `agentsCapped: boolean`、`agentsTotalCount: number`
- AgentBindPopover 标题区 / 搜索框下方提示文案：原来 `共 N 个可用智能体` → 截断时改成 `共 {totalCount} 个，仅显示前 2000；超出部分需升级服务端搜索后才能查找`
- 4.27up 阶段一的旧 comment（"> 100 智能体的场景作为已知短板，留待阶段二独立评估专用候选接口"）一并清理

风险：
- 2000 个 agent 单次拉传输量：每条 ~200 字节（精简字段）×2000 ≈ 400 KB → gzip 后 ~80 KB，可接受
- 数据库压力：`select count(*) from agents` 全表扫；当前 agent 表行数小（千级），无 hot path，可接受；如果以后 agent 表很大，把 count 改成 `head: true` 估算或加索引

## 三类智能体的数据钥匙

| 类别 | 判定条件 | 数据来源 |
|---|---|---|
| **外链** | `agent_type === "external"` | 已有，4.x 起 |
| **自建** | `agent_type === "chat"` && `published_from_draft_id IS NOT NULL` | 5.15up `migration_v36` 新增字段 |
| **外部接入** | `agent_type === "chat"` && `published_from_draft_id IS NULL` | 兜底，直连 coze/dify/zhipu/openai 等外部 API |

**`published_from_draft_id`**：从 `agent-builder` 草稿发布出来的正式智能体，会写这个反查字段。这是"自建"和"外部接入"的唯一明确区分。

`/api/admin/agents` 已经 select 这字段（[`route.ts:33`](../../app/api/admin/agents/route.ts#L33)），**前端 `type Agent` 漏声明**（[`workflows/page.tsx:41`](../../app/admin/workflows/page.tsx#L41)），改一行类型即可。

抽 helper 单点定义：

```ts
type AgentSource = "builtin" | "external_api" | "external_link";

function getAgentSource(a: Agent): AgentSource {
  if (a.agent_type === "external") return "external_link";
  if (a.published_from_draft_id) return "builtin";
  return "external_api";
}
```
