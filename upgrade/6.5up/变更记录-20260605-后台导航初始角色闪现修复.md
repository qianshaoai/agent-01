## 修复 1 · 工作流页假成功兜底

### 背景

`app/admin/workflows/page.tsx` 多个 mutating 操作 `await fetch(...)` 后未检查 `res.ok`，HTTP 失败时仍走 toast 成功提示，用户被误导以为操作生效。

### 涉及位置（7 处）

| 函数 | 行号 | 失败时旧行为 |
|---|---|---|
| `toggleWfEnabled` | 348 | 静默失败 → load() 状态回滚但无提示 |
| `duplicateWf` | 353 | **toast("工作流已复制") 谎报** |
| `deleteWf` | 365 | **toast("工作流已删除") 谎报** |
| `renumberSteps` insert 分支 Promise.all | 412 | 部分 PATCH 失败 → 序号乱 |
| `renumberSteps` 普通分支 Promise.all | 421 | 部分 PATCH 失败 → 序号乱 |
| `deleteStep` | 452 | **toast("步骤已删除") 谎报** |
| `toggleStepEnabled` | 463 | 静默失败 → load() 状态回滚但无提示 |

### 修复模式

仿照同文件已有的 `toast(d.error ?? "...")` 模式（line 611-616，5.x 拖拽排序已修过）：

```ts
const res = await fetch(...);
if (!res.ok) {
  const d = await res.json().catch(() => ({}));
  toast(d.error ?? "<action 中文> 失败，请重试");
  return; // mutating 操作直接退出，不再 toast 成功 / 不再 load
}
load(); toast("xxx 成功");
```

`renumberSteps` 两处 Promise.all 用 `fetch().then(r => { if (!r.ok) throw })` 包装单步骤 + 外层 try/catch 收口，toast "步骤序号重排可能未完全保存，请刷新确认"。提取出局部 `patchOrder` helper 避免两处重复。

### 不动的地方

- `toggleWfEnabled` / `toggleStepEnabled` 失败时仍调 `load()` —— 让 UI 回滚到 DB 真实状态，与 toast 并行；不是冲突逻辑
- 上下移按钮（line 511-578）原本就有 r1.ok / r2.ok / 补偿写回逻辑（4.27up 阶段三做的），不动
- 拖拽整盘排序 PATCH（line 605-616）原本就检查 res.ok，不动
- `load()` 内部 fetch 的 `r.json()` 不加守卫 —— 读类操作即使失败 fallback 到 mock-data 或空数组，不属于假成功类别

- `npm run ci:typecheck` ✅
- `npm run ci:lint` ✅（仅历史 hook deps warning）

## 修复 2 · 后台侧边栏导航初始角色闪现

### 背景

修复后台侧边栏导航初始角色闪现 — 低权限管理员首屏看到本不该见的菜单（如品牌设置）

## 背景

用户实测发现：登录 `system_admin` 或 `org_admin` 账号进入 `/admin/*` 后，前 几百毫秒侧边栏按超管渲染（包括 `SUPER_ONLY` 的"品牌设置"等菜单），等 `/api/admin/me` 回来后菜单才回收到该角色的实际可见集。半秒级闪现 = 权限边界感受不严密。

## 根因

[components/layout/admin-layout.tsx:112](../../components/layout/admin-layout.tsx#L112)：

```tsx
const [adminRole, setAdminRole] = useState<AdminRole>("super_admin");
```

初始值是字面 `"super_admin"`，而 [components/layout/admin-layout.tsx:146-148](../../components/layout/admin-layout.tsx#L146-L148) 的 `visibleNavGroups` 直接用 `adminRole` 过滤 — 在 `/api/admin/me` fetch 完成前，所有按 `allowedRoles` 收紧的菜单（`SUPER_ONLY`、`TAG_ADMIN_ROLES` 等）默认全亮。

> 不是真实越权（页面壳由 [middleware.ts:54-75](../../middleware.ts#L54-L75) + 各 API 的 `requireAdmin` 守住），只是视觉泄露 — 但视觉泄露在管理后台是体验/合规问题。

## 修复

[components/layout/admin-layout.tsx](../../components/layout/admin-layout.tsx)，三处改动：

1. **初始角色 = `null`，不再默认超管**
   ```diff
   - const [adminRole, setAdminRole] = useState<AdminRole>("super_admin");
   + const [adminRole, setAdminRole] = useState<AdminRole | null>(null);
   ```

2. **`visibleNavGroups` 在 `adminRole === null` 时返回空，由 nav 区域渲染骨架**
   ```diff
   - const visibleNavGroups = navGroups.map(...).filter(...);
   + const visibleNavGroups = adminRole === null
   +   ? []
   +   : navGroups.map(...).filter(...);
   ```

3. **nav 区域 ternary 渲染骨架**
   - `adminRole === null` → 3 组、每组 4~6 行白色半透明 `animate-pulse` 块占位（与正式菜单的分组节奏一致，避免拉伸抖动）
   - 角色拿到后无缝切换到真实菜单
   - `aria-hidden` 避免屏幕阅读器读骨架

4. **"当前登录"卡片守卫**
   - 原本 `{adminUsername && ...}` 内访问 `ROLE_LABEL[adminRole]`，`adminRole` 变 nullable 后类型上不安全
   - 改为 `{adminUsername && adminRole && ...}`（实际两者同一个 fetch 写入，运行时几乎同时为真）

## 不动的地方

- [middleware.ts](../../middleware.ts) 的 `validateAdminTokenFreshness` + `firstLogin` 闸门 — 与本修复正交，已在 5.28up R3 修过
- [lib/session.ts](../../lib/session.ts) 的 `requireAdmin` / `getActiveAdmin` — DB 实时角色校验是 API 层防线，本修复只解决前端视觉闪现

- localStorage `brand_settings_v1` 缓存逻辑（platform 名 / logo）不动

## 修复 3 · 工作流页 focus 跳转后目标卡片在折叠 section 里看不到

### 背景

用户实测：从智能体页点击 "引用工作流" chip → `router.push("/admin/workflows?focus=<wfId>...")` → 跳到工作流页后**看不到目标工作流**，需要手动展开分类 section 才能找到。

### 根因

工作流页有两个独立的折叠状态：

| 状态 | 含义 | 默认 |
|---|---|---|
| `expandedId` | 单卡是否展开步骤详情 | 收起 |
| `expandedWfSections` | 分类分区 tbody 是否展开（R1.7 加的） | **全收起** |

[`app/admin/workflows/page.tsx`](../../app/admin/workflows/page.tsx) 原 focus effect（line 240-276）只调了 `setExpandedId(target.id)` 展开**单卡详情**，没动 `expandedWfSections`。`scrollIntoView` 滚到的位置在折叠的 tbody 里，目标卡片不在视口里。

智能体页（[`app/admin/agents/page.tsx:295-308`](../../app/admin/agents/page.tsx#L295-L308)）在 6.3up 已经做过对称修复（`expandedAgentSections` add 进 `target.categoryIds`），工作流页漏了。

### 修复

[`app/admin/workflows/page.tsx`](../../app/admin/workflows/page.tsx) 在 focus 高亮 effect 后追加一个独立 effect（仿 agents 页 6.3up 同款语义）：

```tsx
useEffect(() => {
  if (!focusWfId) return;
  const target = workflows.find((w) => w.id === focusWfId);
  if (!target) return;
  const sectionIds: string[] = (target.categoryIds ?? []).length > 0
    ? target.categoryIds!
    : ["__uncategorized__"];
  setExpandedWfSections((prev) => {
    const next = new Set(prev);
    for (const sid of sectionIds) next.add(sid);
    return next;
  });
}, [focusWfId, workflows]);
```

语义选择：
- **只 add，不收别的 section** —— 让用户跳过来后还能向上 / 向下浏览原本展开的 section
- **不消耗 focusFiredRef** —— 单卡 ring/scroll 是一次性副作用，section 展开是状态变化，分开管理
- **fallback `__uncategorized__`** —— `categoryIds` 为空时落在 "未设置标签" 分区

### 滚动时机

`scrollIntoView` 仍在双 rAF 后执行（原 line 264-271 不动）。新加 effect 的 `setExpandedWfSections` 在 React 同一 render cycle 里和原 effect 的所有 setState 合并 commit，commit 完才轮到 rAF callback fire —— 滚动时 section 已经展开、DOM 高度正确。**不需要把展开逻辑塞进原 effect 强同步。**

### 智能体页（暂不动）

`/admin/agents` 的 6.3up 同款逻辑已经在 master2 上。用户报告"工作流跳智能体也同样问题"，怀疑是 Vercel 部署生效前的旧版本 / 浏览器缓存 / 目标 agent 的 `categoryIds` 数据为空（落在 "未设置标签" 但实际有分类）。本次先不动智能体页，留下次复现时再查。

### CI

- `npm run ci:typecheck` ✅
- `npm run ci:lint` ✅（仅历史 hook deps warning）

### 验证

1. 智能体页 → 某 agent 行的"引用工作流" chip → 跳到工作流页 → 目标工作流所在分类 section 自动展开，目标卡片 ring 1.5s
2. 工作流有多个 `categoryIds` → 每个分类的 section 都展开（同一工作流在多分区都有，全部展开）
3. 工作流 `categoryIds` 为空 → "未设置标签" section 自动展开

## 修复 6 · 三类智能体区分 + 工作流"引用智能体"换成可搜索分组 picker + agent-builder 列表排版加固
